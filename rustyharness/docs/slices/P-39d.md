# P-39d — harness-fetch: the HTTP-only fetcher crate, binary, and the `rh-fetch/1` frame codec

Implements the P-39d row of design note `docs/slices/P-39-web-airlock.md`
(§5, §5.1, §5.2, §4.4 budgets). NOTE: the task card title said "Streaming
confined stdio primitive (shared with P-37)"; the binding spec is the design
note §11 row, which is the fetcher + frame codec. That is what landed.

## What landed

- `crates/harness-core/src/fetch_frame.rs` (pure, no I/O names): the
  `rh-fetch/1` codec.
  - `MAGIC = "rh-fetch/1"`, `MAX_HEADER_BYTES = 16 KiB`.
  - `FrameHeader` carries exactly the nine wire keys: `status`, `reason`,
    `content_type`, `content_length`, `location`, `body_len`, `truncated`,
    `tls` (null or `{version, suite, cert_sha256}`), `error` (null or a
    typed kind string). `body_len` and `truncated` are required; the rest
    may be null.
  - `encode_frame` writes magic line, strict-JSON header line (keys sorted
    on the wire — serde_json's default map is a `BTreeMap`), then exactly
    `body_len` raw bytes.
  - `parse_frame(bytes, max_body)` re-derives everything: strict JSON via
    `harness_core::strict_json` (duplicate keys refused), unknown top-level
    keys AND unknown `tls` subkeys refused, `body_len > max_body` refused
    (`BodyOverCap`), and the tail must be exactly `body_len` bytes — shorter
    or longer both refused (`BodyLenMismatch`). Error enum `FrameError` with
    manual `Display` (crate style; no new deps).
- New workspace member `crates/harness-fetch` (lib + bin
  `rustyharness-fetch`); deps per brief: `harness-core` (path) and
  `serde_json` ONLY — no thiserror, no httparse, no TLS (INV-52: the
  whole-workspace TLS denylist still passes; `https` is refused with
  `error: tls_unavailable` before any dial until the `net` feature, P-39n).
  - `read_request(bytes) -> Result<Request, RequestError>`: strict JSON,
    exact 13-key schema (`v`, `proxy_port`, `token`, `scheme`, `host`,
    `port`, `target`, `accept`, `max_body`, `max_header_bytes`,
    `timeout_ms`, `user_agent`, `mode`), file capped at 16 KiB, `v == 1`,
    `max_body` ≤ 2 MiB, `max_header_bytes` ≤ 32 KiB, `timeout_ms` ≤ 60 s,
    port fields 1..=65535, and every header-bound value (token, host,
    target, accept, user_agent) is printable-ASCII-only so a hostile
    request file cannot inject into the CONNECT/GET heads (CRLF/space
    refused).
  - `fetch_over<S: Read + Write>(tunnel, req) -> Frame`: never returns
    `Err`; every failure becomes an error frame with a typed `error` kind.
    Proxy mode sends `CONNECT host:port HTTP/1.1` with
    `Proxy-Authorization: Bearer <token>` first and requires 200
    (else `connect_failed`); then one `GET` with Host, User-Agent, Accept,
    `Accept-Encoding: identity`, `Connection: close`. Own bounded HTTP/1.1
    parser: heads read one byte at a time (never over-consumes a body
    byte), head ≤ request's `max_header_bytes` and ≤ 100 headers
    (`too_large_headers`), 1xx skipped up to 5 times (6th → `http_parse`),
    `Content-Encoding` ≠ identity refused BEFORE the body is read
    (`encoding_refused`, INV-46 — no decompressor is linked at all),
    `Content-Length` xor chunked xor read-to-close, and the smuggling
    shapes (CL + TE together, TE codings ≠ exactly one `chunked`,
    duplicate CLs, unparseable CL) are all `http_parse` (§943). Chunk-size
    lines longer than 16 hex digits → `http_parse` (§937); chunk sums over
    `max_body` (and CL bodies over `max_body`) stop at the cap and mark
    `truncated: true` (§4.4). `Location` over 4 KiB →
    `too_large_headers`; redirects are reported, never followed (§5.2
    step 6). A short body for a claimed CL (origin lied or died) is
    `http_parse`, never a partial success.
  - `pub use harness_core::fetch_frame::{Frame, encode_frame, parse_frame}`
    per the note. `fetch_over_tls` is NOT here (that is P-39n behind the
    `net` feature).
  - `src/main.rs`: argv[1] is a PATH to the request file (never an inline
    payload, INV-23); dials `127.0.0.1:<proxy_port>` with a 5 s connect
    timeout; applies `timeout_ms` as socket read/write timeouts; runs
    `fetch_over`; writes one frame to stdout; exits 0 — on success AND on
    typed failure. Non-zero exit only if the frame cannot be WRITTEN
    (which the harness types as `ended: fetcher_failed`, as is a crash or
    a short frame). Failure kinds before the fetch proper:
    unreadable/invalid request file → `bad_request` frame; pump dial
    failure → `connect_failed` frame.
- `scripts/ci/purity.sh`: new dep-shape allowlist block for
  `harness-fetch` (exactly the reviewed harness-core tree plus
  `harness-fetch` itself; `serde_json` was already inside it, so no new
  registry crate), inserted after the harness-model-core block, with a
  comment noting that P-39n's `net` feature must extend the block with a
  review note when it lands (INV-52). `harness-fetch` is deliberately NOT
  on the pure-content scan (it dials the loopback pump by design).
- `Cargo.lock`: gained only the new workspace member (let cargo regenerate
  it; no `cargo update -w` was run).

## Tests

Frame codec (`crates/harness-core/src/fetch_frame.rs`):

- `frame_round_trips` — full header round-trips; keys land sorted; magic
  and body framing exact.
- `frame_with_short_or_long_body_refused` — one byte less and one byte
  more than `body_len` both give `BodyLenMismatch`.
- `frame_duplicate_key_refused` — duplicate `body_len` keys → `Header`
  refusal carrying strict_json's duplicate-key marker.
- `frame_unknown_key_refused`, `frame_missing_required_key_refused`,
  `frame_body_over_cap_refused`, `frame_empty_and_bad_magic_typed`,
  `frame_header_too_large_refused`, `frame_error_frame_round_trips`,

- `parses_content_length_body`, `parses_chunked_body_bounded`,
  `until_close_body_parsed` — the three framing modes, happy path.
- `chunk_size_line_over_16_hex_refused` — 17 hex digits → `http_parse`.
- `gzip_content_encoding_refused` (twice over inside the garbage corpus as
  `gzip`/`br`) — refusal happens BEFORE the body is read; body empty.
- `content_length_and_chunked_together_refused` — smuggling shape refused.
- `oversize_headers_refused` — head over the request's cap →

- `body_over_cap_truncated_and_marked`,
  `chunked_over_cap_truncated_and_marked` — both over-cap paths cut at

- `redirect_not_followed_location_reported` — 301 reported with Location,

- `https_without_net_is_tls_unavailable` — refused before any byte is sent.
- `informational_replies_are_skipped` — 100-Continue then the real reply.
- `garbage_response_is_typed_error_not_panic` — 26-case malformed corpus
  (empty, non-HTTP, bad version/status digits, status out of range,

- `request_round_trips_all_fields`, `request_rejects_unknown_key`,

## Interpretations and notes for the manager

- CARD/SPEC MISMATCH: the task card title ("Streaming confined stdio
  primitive (shared with P-37)") does not match the binding spec (design
  note §11 row P-39d: fetcher crate + binary + frame codec). Followed the
  note (fail-closed); the stdio primitive row does not exist in §11.
- LOOP RULES DO NOT APPLY to this slice: there is no journal kind here —
  the codec and fetcher are not loop-visible, same reasoning as P-37c's
  §4.x note. "Every egress is journaled before it happens" is harness-side
  (P-39f journals Egress before the pump dials, INV-43); this process only
  ever talks to the loopback port named in its own request, and the
  in-process tests use in-memory tunnels — nothing here dials the real
  network.
- Error kinds: the note names `tls_unavailable`, `connect_failed`,
  `http_parse`, `encoding_refused`, `too_large_headers` (plus
  `bad_request` harness-side). I/O failures outside the CONNECT phase
  (write or read errors mid-fetch) are reported as the additional kind
  `io_error` rather than crashing or being conflated with a parse error;
  CONNECT-phase I/O failures are `connect_failed`. Flagging in case the
  harness wants a fixed vocabulary in P-39f.
- `truncated` is set whenever the cap is hit, including read-to-close
  bodies that reach exactly `max_body` bytes before EOF (fail-closed: we
  cannot know the origin would not have sent more). CL bodies shorter
  than their claim are NOT truncated-but-success: they are `http_parse`.
- Chunk extensions after `;` are tolerated on the size line (hex part
  still capped at 16 digits) since the note caps the line, not the
  extension; anything longer than the 1 KiB line cap is `http_parse`.
- The head reader reads one byte at a time. This is deliberately slow-ish
  but exact: a buffered read would consume body bytes into the head
  buffer and break framing for chunked/CL bodies. Budgets (32 KiB head,
  100 headers) bound the cost; the loopback pump makes the syscall cost
  irrelevant. Exact-length body reads use `Read::take` so they also never
  consume past the declared length.
- `read_request` requires ALL 13 keys (harness writes them all), requires
  `accept`/`user_agent` to be present but allows empty (empty →
  `*/*` / `rustyharness-fetch` defaults on the wire), and enforces
  printable-ASCII on every value that lands in a request head so a hostile
  request file cannot inject headers (INV-23 spirit: the file is untrusted
  input, not a command).
- `status` in the frame header is validated as a wire-plausible u16
  (100..=599) at parse time; deeper re-validation (e.g. which statuses the
  harness accepts from the fetcher) belongs to the P-39f consumer.
- Purity gate: `harness-fetch` has a dep-shape block but is NOT added to
  the pure-content scan list (it uses `std::net`/`std::fs`/`std::env` by
  design). The INV-24 TLS denylist and INV-23 §2f/§5 scans pass unchanged.
