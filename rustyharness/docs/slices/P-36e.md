# P-36e — FileOps trait: built-in file tools behind one seam

From `docs/slices/P-36-background-processes.md` §7.4. Deps P-22, P-25 (merged).
**No behaviour change** — a pure refactor; every result, digest and error text
is byte-identical (ARCH decision for this slice: no, so no journal/audit
changes; a pure refactor adds nothing loop-visible to journal).

## What landed

- `harness-tools/src/file_ops/`:
  - `mod.rs` — `trait FileOps` (`lstat`, `canonicalize`, `list`, `read`,
    `create_dir`, `remove_dir`, `remove_file`, `write_atomic`, `ping`), the
    `Meta`/`Kind`/`Listed`/`Step`/`Next` value types, no `std::fs`.
  - `in_process.rs` — `InProcess`: today's code verbatim (symlink walk,
    bounded chunked read with the deadline check per chunk, the
    `O_EXCL` `.rh-edit-{pid}-{n}.tmp` atomic write).
- Holders gained `ops: Box<dyn FileOps>` + `with_file_ops(...)`:
  `ReadTools`, `EditEngine`, `PatchTools` (so `EditTools` too). P-36f's
  `Confined` impl plugs in there; the root check in each `new` runs
  against the installed impl only at construction time (P-36f note).
- `Walk` takes the impl (`Walk::new(ops, ...)`) and exposes `walk.ops()`
  for per-entry reads inside a walk (search bytes, outline, tree hashing).
- Free fns take `&mut dyn FileOps`: `canonical_root`, `resolve`,
  `read_bounded`, `hash_capped`, `create_parents`, `remove_dirs`,
  `check_new_parents`, `read_capped`; `atomic_write` became
  `FileOps::write_atomic(bytes, mode: Option<u32>)` (permission bits via
  `PermissionsExt`, unix only; elsewhere `None`).
- Public API kept source-compatible: `workspace_tree`, `workspace_facts`,
  `restore_file` unchanged (they install `InProcess`); new
  `workspace_tree_with`, `workspace_facts_with`, `restore_file_with`
  take the impl.
- `ReadTools::with_window/with_denied`, `EditTools::with_protected`,
  `PatchTools::with_protected` unchanged. `EditTools::preview` and the
  engine's apply methods are now `&mut self` (impl state is owned); no
  external callers were affected (checked `harness-run` and tests).

## Out of scope (left with direct `std::fs`, on purpose)

- `exec.rs` (program resolution, scratch setup) — the command runner is
  not a file tool; it only consumed `canonical_root`/`resolve`, now
  handed an `InProcess`.
- `protected.rs::overlay_dirs` — sandbox overlay setup, not a per-call
  file-tool op.

## Tests

- `tests/file_ops.rs::file_ops_in_process_results_byte_identical` —
  golden over a fixture tree (CRLF, non-UTF-8, symlink, `.git`, empty
  file/dir): 41 snapshots (status Debug + output text + digest) recorded
  pre-refactor and asserted after it. `delete`/`move` ride the real
  §5.3 approval flow (`approver_present` + minted/redeemed single-use
  token); `patch` script covers Add/Update/Delete unattended.
  `tests/file_ops.rs::restore_file_round_trips_an_after_image` — the
  P-22 restore over the new seam.
- `tests/source_scan.rs::tool_modules_touch_fs_only_through_file_ops` —
  no `fs` tokens in builtin/edit/patch/restore/search/outline (test
  sections stripped), none in `file_ops/mod.rs`, `std::fs` present in
  `file_ops/in_process.rs`.
- All pre-existing `cargo test -p harness-tools` suites unchanged and
  green (137 tests).

## Named residual

`Meta.mode` (permission bits) is unix-only; on other platforms a rewrite
skips `set_permissions` exactly as before (there was none). The
deadline inside `InProcess::read` is checked between chunks with the
facts walk's message, matching `hash_capped`'s old behaviour.
