# P-57: Windows spike S-W1 — build, refuse, read/edit

## What was built

S-W1 is the "does it even build, and does it refuse safely" spike for
`x86_64-pc-windows-msvc`. No loop behaviour changed: the loop-visible
gates (journal + audit + test + context bump) do not apply. What changed:

- **Cross check** (CI-script-free, recorded here per the slice card):
  the whole workspace builds for the MSVC target, tests included:

  ```sh
  PATH="$HOME/.cargo/bin:$PATH" RUSTUP_TOOLCHAIN=1.88.0 \
    cargo check --locked --workspace --all-targets \
    --target x86_64-pc-windows-msvc
  ```

  (`RUSTUP_TOOLCHAIN` because the PATH cargo on the dev host is a
  Homebrew build with no MSVC std; a CI runner with a rustup toolchain
  needs neither prefix.) Result: **0 errors**, before and after this
  slice's changes — the base already cross-compiled; this slice's job
  was the refusals and the tests that pin them. Remaining warnings are
  pre-existing dead-code in unix-only test helpers (`harness-run` tests
  `exec`, `hostile_session`, `run`; `harness-cli` test `schedule`), never
  in shipped code, and now recorded here rather than fixed (fixing them
  means `#[cfg]`-duplicating helpers, not worth the churn in a spike).

- **Sandbox stub** (`crates/harness-sandbox/src/windows.rs`): a
  `Windows` backend shaped exactly like `linux::Linux` — same trait, same
  `AppContainer` kind — that never mints a witness. `probe` refuses with
  `NotBuilt` and the facts (Win32 needs `unsafe`, the workspace forbids
  it); `spawn` refuses without running anything. `platform_probe` and
  `SystemConfinement::spawn` now route three ways (macOS → Seatbelt,
  Windows → this stub, other → Linux), so Windows gets the same
  fail-closed `refusing to execute: no confinement on this platform`
  message Linux gets today (via the missing conformance matrix row),
  instead of being handed the Linux backend.

- **Path handling** (`crates/harness-policy/src/path.rs`): no logic
  change was needed — the lexical rule already refuses everything the
  slice card names (drive letters and NTFS streams as `:`, `\` and the
  verbatim/UNC spellings, `.`/`..`, trailing dot/space, control bytes,
  device names case-insensitively with extensions and in any directory).
  Three named tests now pin the behaviour: `windows_path_normalisation_cases`
  (pure, runs everywhere), `unc_and_device_paths_refused` (lexical rule
  plus the locality classifier's `is_unc_shape` predicate),
  `reserved_names_refused` (every device stem, upper/lower, extended,
  nested; near-misses accepted). The matcher stays case-SENSITIVE on
  every OS (replay determinism); device names are the one
  ASCII-case-insensitive check, which is enough because they are pure
  ASCII.

- **Read/edit/search/outline**: no code change — the tools resolve paths
  component-at-a-time from the canonical root with `symlink_metadata`
  (no canonical-prefix string compares), so they are Windows-safe as
  built; `std::fs::rename` gives the edit atomic-rename on Windows.
  The new path tests are the spike's evidence.

- **`doctor`** (`crates/harness-cli/src/cmd_doctor.rs`): with no state
  root given on Windows, the state-root check is a **WARN** saying
  Windows has no default home and no volume query yet, so sessions stay
  off (the host's known shape, not a broken installation). An explicitly
  given root still goes through the locality check and **FAIL**s — the
  Windows probe is unmeasured (`…awaits spike S-W1` message from
  `harness-policy::locality`), and a root the run verbs will refuse must
  not be presented as fine.

- **Exec presets** (`crates/harness-cli/src/exec_presets.rs`): on
  Windows, `look_up` now also tries the `.exe` form of a name in each
  PATH directory (the name as spelled first, so a pinned path still means
  what was written). Without this, every doctor preset check would
  falsely report cargo/node/go missing — they sit on disk as `cargo.exe`.
  Only `.exe` is searched (not the rest of PATHEXT: a `.bat` is not a
  program this harness pins). Off Windows, only the name as spelled is
  tried, now pinned by a test.

## Reading taken (brief ambiguities)

- "`doctor` reporting it" is read as: the state-root WARN above plus the
  pre-existing sandbox WARN (which on Windows now comes from this
  slice's stub with the same `no conformance matrix row` refusal). No
  new check was invented; the two lines carry the whole story.
- Case-insensitivity: Win32 filenames are case-insensitive, but the
  policy matcher stays case-sensitive everywhere so a replay means the
  same bytes on every host; the card's "case-insensitivity" item is
  covered by the device-name check (the one place case matters
  security-wise, `CON` vs `con`) and is pinned in the tests.
- `\\?\C:\…` and `\??\C:\…` (verbatim DISK forms) are refused lexically
  (`\` and `:`), and `is_unc_shape` correctly reports them NOT UNC (they
  would go to the volume query, which refuses for lack of a Windows
  probe). `unc_and_device_paths_refused` pins both halves.

## Design question (for the owner)

The Windows locality probe and the real AppContainer backend both need
Win32 calls, and Win32 needs `unsafe`, which this workspace forbids
crate-wide (`forbid(unsafe_code)`). The policy doc expects an
`harness-sandbox-windows` crate. Decision needed: allow `unsafe` inside
that one audited crate (with a conformance suite as the bar), or keep
the prohibition and route through an external crate. Until then, Windows
stays read/edit-only by construction, which this slice makes honest and
tested rather than accidental.

## Residuals

- Exec stays refused on Windows until a conformance suite passes there
  (the stub's `spawn` is unreachable in practice: no witness can be
  minted). Presets resolve `.exe` now but remain unusable until
  confinement exists — doctor reports both facts.
- The `.exe` search covers only `.exe`, not PATHEXT's other extensions.
- No Windows CI runner exists yet; the cross check is a command in this
  note, and the cfg(windows) tests (`exec_refuses_without_confinement_on_windows`,
  `look_up_finds_the_exe_form`,
  `doctor_warns_that_windows_has_no_state_root_yet`) compile under the
  cross check and await a Windows host to run.
