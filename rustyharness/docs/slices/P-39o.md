# P-39o: user-proxy mode for the research web path

Card: `docs/ROADMAP-parity.md` "P-39o". Design: `docs/slices/P-39-web-airlock.md` section 5.5 and
decision #2 option A (owner question OQ-4). User doc: `docs/web-user-proxy.md`.

## What landed

- **Egress door (`harness-sandbox`).** `HopRequest` gains `delegate: Option<SocketAddr>`. With
  `mode: UserProxy` and `Some(proxy)`, `replay_hop` (the one decision function shared by `open_hop`
  and the audit) resolves and classifies nothing, checks only that the proxy is loopback, journals
  the allow BEFORE anything binds (INV-43), and returns the proxy's address as the pump's dial
  target and port. `EgressRecord` gains `delegated: bool`; a delegated allow has `ip: None,
  delegated: true, resolved: []`.
- **Journal (`harness-run`).** `JournalEgress` writes `ip: "delegated"` for a delegated record. The
  journal canon already accepted it (`harness-journal` `canon.rs`, P-39c), so no schema change.
- **Provider (`harness-tools`).** `WebTools::with_user_proxy(&Endpoint)` sets the proxy (a
  validated loopback `Endpoint`), forces `mode: UserProxy`, and REPLACES the egress connector with
  `LoopbackConnector`. Fetch hops carry `delegate`, write the request file with
  `mode: "user-proxy"`, and report no `ip` (the pump's `chosen` is the proxy, not the origin).
  Search hops are unaffected (`search-endpoint` mode).
- **Fetcher (`harness-fetch`).** `Mode::UserProxy` (`"user-proxy"` in the strict request schema):
  the pump handshake as in `proxy` mode, then one absolute-form `GET <scheme>://authority/target`
  in the clear, no TLS in this process even for `https` and even with `net`. The authority drops
  the scheme's default port; `Host` matches it.
- **Header (`harness-policy`, `harness-run`).** `WebGrant.user_proxy: bool`. The header's `web`
  digest adds `"mode": "user-proxy"` only when set, so every direct-mode journal keeps its digest.
- **Config (`harness-cli`).** The `web` section (`mode`, `user_proxy`, `user_proxy_ack`): strict,
  ack must be exactly `ip-checks-delegated`, proxy validated by the model endpoint's loopback rule
  and must be a bare `http://host:port`. `WebSetting::disclosure()` is the banner text.

### Non-vacuity (defence temporarily broken, test seen red, then restored)

- Ack: adding a catch-all arm that accepts any ack made `user_proxy_mode_requires_ack` FAIL.
- Loopback: bypassing the `Endpoint::parse` check in the config made `user_proxy_must_be_loopback`
  FAIL; disabling the `is_loopback()` check in `replay_hop` made
  `delegated_hop_refuses_a_non_loopback_proxy` FAIL.
- Allowlist: disabling the provider's first-URL check, and separately its redirect check, each made
  `allowlist_still_enforced_in_user_proxy_mode` FAIL.
- Connector override: removing the `LoopbackConnector` replacement made all four provider tests
  FAIL (the injected connector fails on use).

## Choices the card did not settle (fail-closed picks)

1. **The pump handshake stays.** "No CONNECT" is read as: no CONNECT to the origin through the
   user's proxy. The fetcher still does the pump's one authenticated `CONNECT <origin host:port>`
   (bearer token); the pump terminates it and then relays to the proxy. Dropping it would let any
   local process talk to the pump.
2. **Ack check first.** A `user-proxy` section with a wrong or missing ack is refused before the
   proxy URL is looked at; stray `user_proxy`/`user_proxy_ack` on `direct` are refused.
3. **Proxy refusal reuses `refuse:no-address`** (as the search-endpoint host check does), because
   the closed refusal vocabulary has no better word and the canon is unchanged.
4. **The hop `ip` is omitted** from the `ToolFinished` hop record in this mode (it would be the
   proxy's address, which is not the origin's).
5. **Strict `web` section is partial.** Only `mode`, `user_proxy`, `user_proxy_ack` are accepted;
   `fetcher`, `search_endpoint` and `budgets` are P-39k's CLI card and are refused as unknown keys
   for now. `mode: direct` is accepted only in a build with direct egress.
6. **`UserProxy` without a delegate keeps the old decision path** (resolve, classify). Existing
   provider and hostile tests use `EgressMode::UserProxy` as a label over that path, with a fake
   resolver, in a build with no `net`. Production wiring sets the delegate through
   `with_user_proxy`, which is the only supported way to get user-proxy behaviour.

## Review fixes (second pass)

- **F1 (HIGH, fail-open): fixed in the pump.** The first version relayed raw bytes to the user's
  proxy after the handshake, so an exploited fetcher could send `GET http://169.254.169.254/...`, an
  RFC1918 URL or pipelined requests through it. Now `replay_hop` derives the one allowed request from
  the journalled hop URL (`DelegatedRequest`), and `pump_run` reads the fetcher's request, checks it
  strictly (`delegated_request_ok`: exact request line, exact `Host`, only the plain fetcher headers,
  each once, `Connection: close` only), writes only those bytes to the proxy, and treats any byte the
  fetcher sends afterwards as a violation. Failures reply 403 and end the hop `refused`; the bytes
  never reach the proxy. A hop URL that is not plain `http(s)` is refused before anything binds. The
  parser is small, bounded (the existing 8 KiB head cap) and has no unwrap or panic. Test:
  `delegated_pump_forwards_only_the_journalled_request` (`harness-sandbox`) drives the pump as a
  hostile fetcher against a recording loopback proxy: metadata IP, RFC1918, another host, mismatched
  `Host`, another path, origin form, `CONNECT`, `Upgrade`, a POST body, a pipelined request in the
  same write and a second request in a later write. Seen RED with the check and the second-request
  guard disabled (the metadata request was relayed), GREEN with them. Disclosure was added anyway: a
  proxy still resolves the allowlisted NAME, so the proxy ACL denying private, loopback, link-local
  and metadata ranges stays recommended (design 2 item 4 and 5.5, `docs/web-user-proxy.md`, the
  banner in `harness-cli` `disclosure()`).
- **F4 (LOW): confirmed no relabel.** Search hops build their `HopRequest` and hop record with a
  literal `EgressMode::SearchEndpoint`; only fetch hops use `egress.mode`. Test
  `search_hops_keep_search_endpoint_label_in_user_proxy_mode` (`harness-tools/tests/web_tools.rs`).
- **F3 (LOW), noted only:** a non-loopback proxy is journalled as `refuse:no-address`, which is a
  misleading reason (the address is the proxy's, not the origin's). The journal canon is unchanged on
  purpose; the vocabulary is closed. Same reuse for a hop URL the pump cannot turn into a request.
- **F2 (MED), deferred and recorded.** `WebSetting`, `disclosure()` and `web` in `harness-cli` are
  still `#[allow(dead_code)]`, and nothing outside tests calls `WebTools::with_user_proxy` or sets
  `WebGrant.user_proxy`. So, deferred to the P-39k CLI card: (1) the CLI wiring that reads the `web`
  config, builds the provider with `with_user_proxy` and sets `WebGrant.user_proxy`; (2) printing the
  banner at session start; (3) the offline audit of delegated hops from a real user-proxy journal
  (the replay is proved only at the provider seam through `WebTools::new_replaying`). There is no
  seam today at which "a `user_proxy` grant without the acked config is refused" can be tested: the
  ack is checked only when the config loads (`user_proxy_mode_requires_ack`), and `WebGrant` is a
  plain flag that does not carry or re-check it. Until the wiring lands, the banner never prints.

## Not done / honest limits

- The proxy's own behaviour is **UNVERIFIED**: nothing here ran against a real Squid or any real
  proxy; the tests use a scripted loopback fixture.
- There is no CLI research verb, no chat banner call site and no live wiring of `WebSources` yet
  (they are P-39k's CLI card; `WebSources` in `harness-run/src/driver/research.rs` is still never
  constructed). The banner text and the config are in place and tested; the session-level audit is
  proved at the provider seam (`WebTools::new_replaying`), as `hostile_web_audit_offline` does, not
  through `audit_session`.
