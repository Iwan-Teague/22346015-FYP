# P-36c — `rh-fileop/1` pure codec (`harness-sandbox/src/fileop/proto.rs`)

## What landed

- `crates/harness-sandbox/src/fileop/mod.rs` (new) — module doc and
  re-exports; built unconditionally because the codec is pure and
  backend-neutral (the Linux backend reuses the protocol, design §8.4).
- `crates/harness-sandbox/src/fileop/proto.rs` (new) — the whole
  `rh-fileop/1` codec per design §7.3: no I/O, no clock, no process, no new
  dependency (hand-rolled byte framing; `harness-sandbox` has no serde).
  - `Request` — one enum arm per §7.3 operation (`lstat`, `read`, `list`,
    `tree`, `create`, `replace`, `unlink`, `move`, `rmdir`, `ping`), in
    §7.3's argument order. Paths are `WorkspacePath`; digests are
    `harness_core::Digest` (64 lowercase hex on the wire, `FromStr` on
    decode); numeric arguments are `u32`.
  - `Reply` — `Ok { items }` with the items kept as opaque `Vec<Vec<u8>>`
    (the wire reply carries no operation name, so only the caller that sent
    the request can interpret the items), or `Err { code }` with
    `ErrorCode` covering the eleven §7.3 codes (`noent`, `symlink`,
    `notdir`, `isdir`, `exists`, `toobig`, `changed`, `denied`, `nlink`,
    `io`, `badreq`).
  - Framing identical to the domain stub's frame in
    `confine_spawn.rs`: `<op>\n<n>\n` then n items of `<len>\n<bytes>`
    glued back to back (bodies are raw, so an item's length line abuts the
    previous body; lengths are known, so parsing stays unambiguous);
    replies `ok <n>\n` + items or `err <code>\n`.
  - Bounds (§7.3): a request is refused over `MAX_REQUEST_BYTES` (8 MiB),
    a reply over `MAX_RESPONSE_BYTES` (8 MiB + 64 B of framing), checked
    before any allocation on encode and before any parsing on decode.
    Item lengths and counts are `^[0-9]{1,8}$` (`0` allowed for lengths,
    never for a request count since every operation has arguments); every
    line is refused over 64 bytes, matching the stub's `rl` reader.
  - Decode is fail-closed and reads ahead of no allocation: a length is
    checked against the bytes actually present before anything is copied,
    the frame must be consumed exactly (no trailing bytes), and nothing is
    allocated for a count until the items are actually present (a huge
    claimed count just runs out of frame and is refused `BadFrame`).
  - Paths get the codec's own component re-check (`check_components`)
    before the harness-policy lexical check: the raw item is re-split on
    `/` and refused for empty, `.` or `..` components, so a frame can
    never carry one even if a `WorkspacePath` invariant ever loosened
    (defence in depth, §7.3). `""` (the root spelling) is refused here
    because `workspace_path` refuses it too (`PathRefused::Empty`).
  - `ping`'s probe path is the one argument that is deliberately *not* a
    `WorkspacePath` — it exists to be refused by the helper — so it is
    carried as raw text, refused only if empty or holding a NUL/control
    character (`BadProbePath`).
- Numbers as items: design §7.3 gives `rh-fileop/1` no inline-number
  syntax, so `max`, `max_entries`, `depth`, `mode`, `max_new_dirs` and
  `timeout_ms` travel as items holding decimal text — the uniform item
  frame, nothing new. Encode always emits the canonical shortest decimal
  (`420` for `0o644`); decode accepts any digits-only text that fits
  `u32` (form is strict, value range stays the helper's business).

## Tests (`cargo test --locked -p harness-sandbox`)

Six, all named per the card, all in `proto.rs`'s `#[cfg(test)] mod tests`:

- `fileop_frame_round_trip_every_op` — every §7.3 operation encodes,
  decodes back equal, and stays inside the request bound.
- `fileop_frame_refuses_oversize_item` — a nine-digit length line, a
  length that outruns the bytes present, a request over 8 MiB, and a
  reply over its bound are all refused.
- `fileop_frame_refuses_bad_count_and_non_decimal_length` — counts and
  lengths that are not 1-8 digit decimals (empty, signed, suffixed, nine
  digits) and the zero request count are refused; the zero reply count is
  legal (`rmdir` answers `ok 0`).
- `fileop_response_error_codes_round_trip` — all eleven codes round-trip;
  `ok` items come back byte-identical (empty, newline-bearing);
  unknown codes, foreign heads, truncation and trailing bytes are
  refused.
- `fileop_path_must_be_workspace_relative_without_dot_components` —
  absolute, parent, current-dir, empty-component, backslash and control
  character paths are refused with `BadPath`/`PathComponent`.
- `fileop_codec_is_deterministic` — every operation (and a sample reply)
  encodes to identical bytes twice, and re-encoding the decoded request
  reproduces the original bytes.

Gates: `cargo fmt --all`, `cargo clippy --locked --workspace
--all-targets -- -D warnings`, `cargo test --locked -p harness-sandbox`
(49 + 32 + 1 green).

## Decisions worth keeping

- `take_item` mirrors the stub exactly: length line via a 64-byte-bounded
  line read, `^[0-9]{1,8}$`, body of exactly `len` bytes glued after the
  newline, empty item for `0`. The stub's `rl`/`rn`/`item` (see
  `confine_spawn.rs` lines 127-129) are the reference implementation.
- Decode refuses with typed `CodecError`s (thiserror) rather than one
  opaque "bad frame", so the P-36f helper surface can map them onto
  `err badreq` without re-parsing strings. `PathRefused` has `Display`
  but no `std::error::Error` impl, so `CodecError::BadPath` carries it as
  a plain field (no `#[from]`).
- `WorkspacePath` and `Digest` travel as their canonical renderings
  (`as_str` bytes, 64 lowercase hex), so round-tripping is byte-stable —
  the determinism test pins this.
