## D4 — The agent loop ends only by calling `harness.task.submit`; the loop re-prompts until then; grading happens outside the harness

**1. Restate.** D4 makes a single always-granted `harness.task.submit` tool the only way the loop ends as a *submission*; stop causes (Budget, Loop, FormatErrors, ContextExhausted) still trigger checks on whatever the workspace holds; the harness never scores — rustybenchmark grades the deliverable in its own slot, and infrastructure failures (ModelUnavailable, SandboxLost, Cancelled, JournalUnavailable) are retried and never charged to the model.

**2. Prior art.**
- **mini-SWE-agent** (the SWE-bench bash-only reference agent, ~100 lines, no tool-calling interface): submission is an exact shell command — `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt` — run as its own step, after which the model *cannot* continue (https://mini-swe-agent.com/latest/usage/swebench/). Its default agent config raises `LimitsExceeded`/`TimeExceeded` with an **empty** submission string, which scores zero; there is no salvage of a half-finished patch (https://github.com/SWE-agent/mini-swe-agent, `src/minisweagent/agents/default.py`; verified this session via zread). The docs position it as "a baseline system... that puts the language model rather than the agent scaffold in the middle of our attention" (https://mini-swe-agent.com/latest/).
- **SWE-agent** (the predecessor) treats submit as a special batched command and, on limit exhaustion, extracts the working diff as the final patch — a salvage mechanism mini-SWE-agent v2 dropped. The salvage detail is from memory of the v1 run scripts: UNVERIFIED this session.
- **Terminal-Bench / Harbor**: agents have no submit obligation at all. When the agent hits its timeout, execution stops and **tests still run on the final container state** — partial work is graded (https://github.com/laude-institute/terminal-bench docs, verified via zread this session; https://www.tbench.ai/). Terminus-2 adds a `task_complete` confirmation tool, i.e., submit-as-signal rather than submit-as-gate (https://www.tbench.ai/docs/agents/terminus-2 — toolset specifics UNVERIFIED).
- **OpenHands** uses a `finish` action and grades the produced patch afterwards; evaluation is a separate pipeline (https://docs.all-hands.dev/ — specifics UNVERIFIED).
- **Aider** has no agent loop at all: the harness drives two attempts and grades the collected diff; aider never grades itself (https://aider.chat/docs/leaderboards/).
- **Claude Code / Codex CLI / opencode** are general-purpose tools wrapped headlessly by benchmarks; there is no submit tool, and benchmarks grade the workspace diff after session end (https://docs.anthropic.com/en/docs/claude-code, https://github.com/openai/codex, https://opencode.ai — wrap conventions UNVERIFIED).

The field, in short, splits into "submit is a hard gate, miss it and you score zero" (mini-SWE-agent) and "grade the final state no matter how the run ended" (Terminal-Bench). D4 is deliberately the union: submit ends the loop cleanly, but every non-infra stop still gets graded.

**3. Attack.**
(a) *Protocol compliance is silently billed to the model.* The re-prompt-until-submit loop means a model that does the work but is slow to learn the sentinel keeps getting nudged until Budget, burning model time that D14 then divides out of the headline. Cross-model comparisons therefore bundle "can solve tasks" with "can follow one instruction"; small models lose twice. mini-SWE-agent has the same property (empty patch on limits → 0) but at least records `exit_status` per run so the reader can decompose it; Terminal-Bench avoids it entirely by not requiring submission.
(b) *The score taxonomy hides this.* measurement-plan §4.2 keeps the failure class but nothing in the headline exposes it. Aider publishes "malformed" counts and mini publishes exit_status; without an equivalent column, a submit-compliance effect is invisible.
(c) *Premature submit.* Because submit is unconditionally granted and terminal, a trigger-happy model locks in. This is acceptable precisely because grading is on workspace state either way — a strength worth defending loudly, since it makes submit a *control-flow* device, not a *scoring* device.
(d) *Grading is not as deterministic as advertised.* AQ-218 (action-queue.md:271, confirmed): a miri timeout is excluded as "indeterminate," which a model can exploit by looping until the timeout to dodge a failure that would score 0 under AQ-208 r3's rule that every other breach/timeout scores 0. The older AQ-202 rule leaves a gameable hole directly inside the "grading outside the harness" story. An examiner will find this in one read; the exclusion is indistinguishable in kind from the harness deciding outcomes.
(e) *Infrastructure/verdict separation is correct and matches the field* (mini's exit_status vs submission; TB's agent-vs-tests split). No attack there; the attack is that one row of the grader (miri) contradicts it.

**4. Better.** Keep the submit sentinel and keep grading on state (it dominates both prior-art poles). Add three cheap things: (1) publish an exit-status/failure-class breakdown next to every headline number (mini-SWE-agent precedent), so submit-compliance cost is measurable per model; (2) run one pilot subset in a **no-submit control arm** — grade-on-state only, no sentinel — to quantify how many points the protocol itself costs small models; if it is large, report both numbers; (3) close AQ-218 by scoring a miri timeout as **0 with a named flag** and loud counts, matching AQ-208 r3's own logic that "an excluded row can be gamed." Trade-offs: the control arm costs ~a pilot's worth of compute against one model (a day-scale hit, affordable for an owner not afraid of work, and it protects the mid-Nov Level-1 milestone because it is a subset); the miri change makes numbers look marginally worse but removes the only score-affecting discretion in the grader. Long-term soundness and security both improve; project speed is essentially unchanged.

**5. Verdict.** **MODIFY** — high confidence. Keep submit + external grading; add exit-status reporting, a no-submit control, and the miri fix.

## D14 — Headline metric is "correct tasks per hour of model time"; toolchain time is recorded but not scored

**1. Restate.** D14 excludes toolchain (build/test) time from the headline capability-per-time number, credits remote runs to the inference host, and records a full timing split (queue+prefill to first non-empty delta, reasoning, answer) with server-native timings where available.

**2. Prior art.**
- **Aider** reports, per model, percent correct **plus cost in dollars and seconds per case** on the polyglot leaderboard (225 Exercism exercises across five languages incl. Rust) (https://aider.chat/docs/leaderboards/). Its time column is case wall time, not sanitized model time.
- **mini-SWE-agent / SWE-bench**: the batch runner records `instance_cost` and `api_calls` per instance; leaderboards are dominated by resolution rate with cost as a secondary axis (https://mini-swe-agent.com/latest/; https://github.com/SWE-agent/mini-swe-agent). There is no model-hour metric; end-to-end cost is the convention.
- **Terminal-Bench**: leaderboards report mean resolution rate with per-agent k-sample error bars (±~1.2 pt at k=5 per the 2.0 paper, https://arxiv.org/abs/2601.11868) and cost; wall-clock is incidental, not headline (https://www.tbench.ai/).
- **METR's time-horizon work** (Kwa et al., "Measuring AI Ability to Complete Long Software Tasks," NeurIPS 2025, https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/) deliberately normalizes capability to *human* task length, not model time — a different but instructive choice: they treat time as the unit of difficulty, not of efficiency.
- **Systems benchmarking** splits the very thing D14 merges: llama-bench reports prompt-processing and generation throughput as separate columns (https://github.com/ggml-org/llama.cpp); Artificial Analysis reports output tok/s and TTFT latency as axes independent of quality (https://artificialanalysis.ai/); MLPerf Inference famously conditions throughput scores on meeting an accuracy target, i.e., speed only counts when quality holds (https://mlcommons.org/benchmark/inference/ — exact division rules UNVERIFIED this session).

**3. Attack.**
(a) *Prefill dominance makes "model time" definitionally fragile.* The measurement plan itself notes KV-cache reuse means per-turn prefill covers only new tokens and that queue+prefill is lumped into time-to-first-delta. With long stable prefixes (context rebuilt every turn, stable-prefix prompt caching is a design goal, design v0.1 §2.3), a model's "hour" can be 60%+ prompt processing whose cost depends on the server's caching behavior, not the model. Llama.cpp, Ollama, and any remote engine will report cached vs processed tokens differently; the tags (server/client/estimated/unavailable) are honest, but a headline that silently mixes them is not comparable across engines. llama-bench and Artificial Analysis keep prefill and decode visibly separate for exactly this reason.
(b) *Thermal/swap coupling.* Big cargo builds swap and heat the machine *while the model is still resident*, inflating measured model time (the plan flags this but doesn't gate on it). Charter OI-33 (decision-log.md:116, confirmed) already established per-device calibration with a baseline band for wait-time budgets; the same physics applies to the benchmark loop, yet D14's headline has no quiesced-host precondition. Two runs of the same model on the same laptop a week apart can differ by thermal state alone.
(c) *The exclusion is right for the question but oversold as "the" number.* Excluding toolchain time answers "which model is more capable per unit of inference," which is the scientifically interesting cross-model comparison. But it cannot answer "how much does this setup deliver per day," which is what a supervisor or examiner asks first, and what Aider/mini/TB all report instead. Worse, the exclusion creates a mild incentive blind spot: a model that triggers rebuild loops pays nothing in the headline; the score-by-turn curve partially catches it, but only if published per task.
(d) *"Done on a DGX Spark" crediting* is honest but makes epochs engine- and device-dependent (see D16): tok/s differs enough between a laptop and a Spark that model-hour numbers are not portable without the timing table.

**4. Better.** Keep model-hour as headline but make it a **pre-registered formula**, not a convention: model time = Σ per call (queue+prefill, with processed-vs-cached token accounting per server-native timings) + decode + reasoning, toolchain excluded; publish the per-run timing table. Add two co-primary columns, Aider-style: **wall-clock per task including toolchain** and **cost (hosted) or tok/s (local)**. Report **prefill share of model time** explicitly; if it exceeds a threshold (say 40%), also report a decode-only variant so readers can see how much of the "efficiency" story is caching. Extend OI-33's law to benchmark runs: quiesced-host precondition + baseline band + swap/thermal recording, with throttled runs flagged or redone. Trade-offs: co-primary columns dilute the headline's punch but cost nothing to produce since the data is already recorded; the quiesced-host gate adds scheduling friction on a shared laptop, which is exactly the friction the qa-engine timing-gate law already accepts elsewhere. This is the single highest examiner-leverage fix in the theme: "correct tasks per hour" with no wall-clock, no prefill share, and no thermal gate invites the question "whose hour?"

**5. Verdict.** **MODIFY** — medium-high confidence. Keep the exclusion; co-report wall-clock and cost; pre-register the formula; gate on host state.

## D16 — One pinned rustyharness version produces one results epoch; a new harness version starts a new epoch

**1. Restate.** D16 pins exactly one harness version for a block of results; changing the harness invalidates comparability and opens a new epoch rather than mixing numbers.

**2. Prior art.**
- **Terminal-Bench** pins the dataset as a package version (`terminal-bench-core==0.1.1`) in run commands and labels leaderboard rows with agent + model + dataset version; Terminal-Bench 2.0 (89 tasks, top models under 65%) is itself an epoch break from 1.x (https://arxiv.org/abs/2601.11868; https://www.tbench.ai/; dataset-pin example verified via zread of laude-institute/terminal-bench docs).
- **SWE-bench Verified** is the canonical epoch analog: a frozen 500-instance subset blessed by OpenAI human filtering, permanently separable from the live leaderboard (https://openai.com/index/introducing-swe-bench-verified/ — UNVERIFIED this session; the practice is well documented on https://www.swebench.com/). The bash-only leaderboard explicitly re-evaluates everything with one reference agent (mini-SWE-agent) rather than mixing scaffold generations (https://mini-swe-agent.com/latest/).
- **Aider** does per-row versioning instead of epochs: every leaderboard row records aider version, model version, and commit hash (https://aider.chat/docs/leaderboards/).
- **LiveCodeBench** publishes versioned snapshots (problems frozen at v1..v6) precisely so capability-over-time and contamination can be reasoned about (https://livecodebench.github.io/; paper https://arxiv.org/abs/2403.07974 — snapshot naming UNVERIFIED this session).

**3. Attack.**
(a) *The epoch is under-specified.* "Harness version" alone does not pin the thing being measured. The run header already carries digests (contract §2: header carries harness version + digests), but the *inference engine* is declared a variable (contract §5: engine is a variable, llama.cpp primary), and llama.cpp changes numerics between builds (Metal/CUDA kernel updates shift per-token sampling). A pinned harness over a moving engine is a half-pinned epoch — the exact complaint D16 exists to prevent. Same for the task set: a suite that grows from 108 to 272 families across an epoch quietly changes the mean.
(b) *Epoch churn vs the calendar.* At the plan's own cost estimate (~44.5 h/model/machine for deep L1, ×2–5 for agent mode), a gratuitous harness fix mid-sweep is a multi-day re-run. The rule needs a release-class notion or it will be violated in practice by its owner under deadline (Level-1 results due mid-Nov, Level-2 pilot 23 Dec).

**4. Better.** Keep D16, but define an epoch as a **hash tuple**: (rustyharness version, profile digest, toolset hash, task-set hash, engine + build ID, calibration band). Publish an epoch manifest with every results file; header digests (already designed, DD-11's `toolset_sha256` pattern extended) make this nearly free. Add release classes: docs-only or CLI-only changes are epoch-preserving and documented as such; anything touching the loop, grading interface, profiles, or tool registry is epoch-breaking. Trade-offs: slightly more bookkeeping now (a manifest generator, an hour of work) versus large insurance against the "which build produced this number" question at viva time. No meaningful hit to UX or speed; it directly serves long-term soundness, the owner's top criterion.

**5. Verdict.** **KEEP** (with the hash-tuple definition added) — high confidence.

## D17 — Grading and measuring live in rustybenchmark, never in rustyharness; the harness verdict is a secondary signal, never the score

**1. Restate.** D17 assigns all scoring and timing measurement to the embedding benchmark application; the harness produces a workspace state plus a verdict signal whose only sanctioned use is diagnostics.

**2. Prior art.** This separation is the load-bearing wall of every major agentic benchmark:
- **SWE-bench**: the agent runner (mini-SWE-agent) emits `preds.json` with a patch; evaluation is a *different* pipeline (`swebench.harness.run_evaluation` locally or sb-cli in the cloud) run in fresh containers (https://mini-swe-agent.com/latest/usage/swebench/).
- **Terminal-Bench/Harbor**: the agent finishes (or times out); a separate test phase runs the task's tests on the final container state; the agent never sees pass/fail unless the task exposes it (https://github.com/laude-institute/terminal-bench; https://arxiv.org/abs/2601.11868). The repo's task validation even requires a NOP agent that must pass zero tasks — grading structure is validated independently of any model (zread doc, verified this session).
- **Aider**: the benchmark runner is external to aider; aider cannot grade itself (https://aider.chat/docs/leaderboards/).
- **OpenHands** keeps agent runtime and evaluation harness as separate codebases/pipelines (https://docs.all-hands.dev/ — UNVERIFIED specifics).
- Commercial agents (Devin, Claude Code, Codex CLI) are graded externally via produced PRs/diffs; none carries a scorer (https://devin.ai/, https://docs.anthropic.com/en/docs/claude-code, https://github.com/openai/codex — grading conventions UNVERIFIED).

**3. Attack.** The design is right, so the attacks are about the *seams*:
(a) *Reconstruction drift.* Grading on a fresh clone with restored `.cargo/config.toml` and `rust-toolchain.toml`, single-commit repo, diff audit (contract §4, design §7.6) means two codebases must agree on what "the deliverable" is. If harness-side snapshot semantics and grader-side clone semantics drift (e.g., untracked files, ignored-but-needed files), scores silently change. This is a bug-class risk, not a design flaw, but it needs a test: **the same terminal workspace state must grade identically whether produced by a model or by a scripted fixture.** Golden grader tests would close it.
(b) *Stop-cause coupling.* D17 keeps the stop-cause taxonomy in the harness while D4's scoring interpretation lives in rustybenchmark. The enum is API; if it grows informally, the grader's mapping (§4.2) breaks quietly. The gate-outcome crate split (P9) is the right place to freeze and version this contract.
(c) *The one discretionary row.* AQ-218's miri-timeout exclusion (see D4) is the single place where the grader, not the deliverable, decides an outcome category that a model can steer into. Every other timeout is 0 under AQ-208 r3; the miri row is the seam an examiner will poke.

**4. Better.** Keep the separation. Add: grader golden/property tests (fixture-workspace == model-workspace ⇒ identical score); a versioned score schema published per epoch (ties into D16's manifest); the miri fix from D4. Trade-offs: a day or two of test infrastructure; protects the 23 Dec pilot from a silent regrading bug discovered after a multi-day sweep — at 4–9 days/model/machine, one regrading incident costs more than the tests by an order of magnitude.

**5. Verdict.** **KEEP** — high confidence.

## D18 — rustyharness stands alone as an in-the-wild harness (opencode/Cline-like); benchmark mode is configuration through the embedding API; the benchmark supplies its own instrumented ModelBackend

**1. Restate.** D18 (with OD-2/OD-3, design v0.1) forbids app-specific code in the harness — embedding apps configure it via the policy/registry/profile API, the registry can never be empty (submit always granted), and rustybenchmark measures through its own ModelBackend that observes the same wire bytes.

**2. Prior art.**
- **Terminal-Bench/Harbor** is the direct analog: a standard agent interface with pluggable agents (oracle, Terminus, a NOP validation agent, and container-installed third-party agents like Claude Code), where the benchmark drives whatever agent through one API (https://www.tbench.ai/docs/agents — pluggability verified via zread; the full agent list UNVERIFIED).
- **mini-SWE-agent** embodies the same philosophy from the other side: a general-purpose minimal agent positioned as the benchmark's fixed reference scaffold (https://mini-swe-agent.com/latest/).
- **OpenHands** structures agents as configurable `Agent` classes that benchmarks embed (https://docs.all-hands.dev/ — UNVERIFIED specifics).
- **Aider** is the anti-case: it is both agent and de-facto harness, which is why its per-model edit formats (D24 below) leak into its leaderboard rather than living in a benchmark-supplied backend (https://aider.chat/docs/leaderboards/).
- **Claude Code headless mode, `codex exec`, opencode non-interactive runs** are the in-the-wild wrapper pattern D18 aspires to: general tools driven by config, graded externally (https://docs.anthropic.com/en/docs/claude-code, https://github.com/openai/codex, https://opencode.ai — flag specifics UNVERIFIED).
- The harness-sensitivity literature is the reason this matters: DeepSWE (Datacurve) rebuilt its benchmark around original tasks and hand-written verifiers precisely because inherited scaffolds and tests produced unstable signals (1.4% judge disagreement vs 32.4% for inherited SWE-Bench Pro tests; https://arxiv.org/abs/2607.07946; https://deepswe.datacurve.ai/). Claims that scaffold swaps move SWE-bench scores by ~10 points circulate in that write-up's ecosystem but I could not re-verify the specific number this session: UNVERIFIED.

**3. Attack.**
(a) *The anti-hacking rule is correct but under-enforced.* "No app-specific code" prevents the harness from containing suite shortcuts, but benchmark validity now lives in *configuration*: policy, registry, profile. If config isn't fully captured, a subtle registry difference between runs is invisible. The header digest scheme (confinement digest, toolset hash — od5-delta-v2 §3.4, DD-11) covers this, provided audit/resume actually compare all of it (they are specified to).
(b) *Instrumentation must be provably non-perturbing.* "Same wire bytes" is the right invariant; it needs a test, not an assertion: record the byte stream with instrumentation on and off on a replay corpus and require byte equality, and require that timing tags never alter request shape (llama.cpp `timings`, Ollama durations, `/props` probes — contract §5). Since the engine is a declared variable, the timing schema differs per engine; the server/client/estimated/unavailable tags are the honest handling, but the headline (D14) must say which tag class fed it.
(c) *Scope ambition vs calendar.* The in-the-wild goal (OD-1) is a product goal, not a benchmark requirement; nothing in T6's scope forces it before mid-Nov. The risk is effort leakage from H2/H3 (confinement, evidence) into polish. OD-6 (no VMs/no external container runtimes) and the measured macOS facts (loopback bind rules can't be kept port-scoped; `setsid()` escapes process-group kill) make H2 the schedule-critical path; D18 itself is not, and should not be allowed to become, that path.
(d) *Config-only benchmark mode can be weakened.* The embedding app owns the limits; P15 (embedder may only tighten, never loosen, limits) is the correct invariant and should be a tested property of the embedding API, not a convention.

**4. Better.** Keep D18 as is. Add: wire-byte equality test; config-digest golden files per epoch; a property test that embedding APIs can only lower limits; keep OD-3 (grading stays in the embedder) as the public anti-collusion argument — a harness that cannot score cannot be accused of score-shaping. Trade-offs: a few days of test work, all front-loadable before the sweep; improves the security criterion directly (the harness's trust position shrinks) and the soundness criterion (auditable config).

**5. Verdict.** **KEEP** — high confidence.

## D24 — Tool packaging scales with model size: per-model profile, `max_active_tools` default 6 under 30B (range 5–8), merged tools for smaller models, identical capability set, packaging recorded per run, pilot ablation on one model

**1. Restate.** D24 gives every model the same capabilities but different *presentation*: bigger models get more, finer-grained active tools; smaller models get merged tools; the profile records tool count and `toolset_sha256`; a pilot ablation on one model checks the packaging effect.

**2. Prior art.**
- **Aider** is the strongest precedent *for* per-model packaging: it selects an edit format per model (diff, diff-fenced, whole, architect with editor-model pairing), reports "Correct edit format %" and "percent cases well formed" as separate columns from correctness, and shows malformed rates per row (https://aider.chat/docs/leaderboards/). Aider survives as credible science because the packaging choice is *measured and published*, not because it is uniform.
- **mini-SWE-agent** is the strongest precedent *against*: one bash-only action space for every model, explicitly so that comparisons isolate the model (https://mini-swe-agent.com/latest/). Its 74%+ Verified results via the SWE-bench bash-only leaderboard demonstrate a uniform minimal action space does not bottleneck strong models.
- **Terminal-Bench's Terminus-2** sits in between: a single fixed tool interface (shell + `task_complete`) for all models regardless of size (https://www.tbench.ai/ — toolset specifics UNVERIFIED).
- **SWE-agent's** original contribution was precisely that interface design (the agent-computer interface) moves scores substantially — their ablations showed large gains from tool/format choices at fixed model (https://arxiv.org/abs/2405.15793). This is the key citation: packaging is not a second-order knob.
- **DeepSWE** shows the confound matters enough that a benchmark rebuilt its whole task/verifier layer to escape scaffold noise (https://arxiv.org/abs/2607.07946).
- Rust-specific: **RustEvo²** evaluates Rust API-evolution capability with a uniform harness per model (https://arxiv.org/abs/2503.16922); no size-scaled packaging precedent found in the Rust harness landscape.

**3. Attack.**
(a) *Fairness inversion.* The stated goal is identical capabilities; the delivered product is identical capabilities *plus different error surfaces*. Merged tools change tool-call grammar, format-error rates, and planning depth; SWE-agent proved interface moves scores at fixed model. Cross-size comparisons under D24 are therefore bundles of (model + its tailor-made scaffold) — exactly what mini-SWE-agent's philosophy exists to prevent. The design's own honesty devices (packaging recorded, toolset hash in header, profile_validated flag, ≥80% exact-tool-call smoke gate) document the confound but do not remove it.
(b) *The ablation is underpowered.* One model cannot defuse a confound that varies across the size spectrum — the whole point of size-scaling is that the effect differs by size. A 3-point packaging effect on a 27B tells you little about its effect on an 8B. CF-27 (od5-delta-v2) sharpens this: Level-2's ten-capability set exceeds the 5–8 tool cap, so merged-tool decisions become substantive design choices with model-dependent consequences, chosen by the designer, not the model.
(c) *The measurement plan already concedes the tension.* "Protocol per-model vs text-for-all" is listed OPEN (§4.3, §12). D24 is the same question wearing a different hat; deciding one without the other re-opens the fight later, mid-sweep, at 4–9 days/model/machine.
(d) *The defense exists and is cheap.* Aider's pattern — per-model packaging allowed, packaging compliance reported as its own column — converts the confound from hidden to quantified. D24 currently records packaging but plans no per-row *behavioral* packaging metric (format-error rate, tool-call parse rate).

**4. Better.** Restructure the arms: (1) **Headline arm = one fixed packaging for all models** (conservative text protocol, merged tools, K and caps fixed — the "text-for-all" option already under consideration). This is the examiner-proof number and matches mini/TB convention. (2) **Per-model packaging = secondary arm**: size-scaled profiles run on 2–3 models spanning the size bands (not one), reported side by side with their format-error-rate columns, as an ablation on "how much does tailored packaging buy." Pre-register both arms and the analysis before the sweep. (3) Add a **format-error-rate column** to every results row regardless of arm (aider precedent). Cost: the ablation arm adds roughly two model-sweeps' worth of partial runs; given the owner's stated appetite for work and the pre-pilot buffer before mid-Nov, this fits — and if it must be cut, cut the ablation, never the fixed headline arm. The one-model pilot from D24 becomes the pilot *within* the ablation arm, not the arm itself.

**5. Verdict.** **MODIFY** — medium-high confidence. Keep capability equality, recording, and hashing; flip the headline to fixed packaging for all; promote packaging-scaling to a measured, multi-model ablation.

## Top changes I'd make

1. **Score miri timeout as 0 with a named flag** (close AQ-218, align with AQ-208 r3). One-line grader change; removes the only gameable discretion in the pipeline before any results exist.
2. **Pre-register the D14 metric formula and add co-primary columns**: model-hour headline stays, but publish wall-clock-per-task including toolchain and cost/tok/s alongside; report prefill share of model time (with cached-token accounting) and a decode-only variant when prefill dominates; extend OI-33's quiesced-host baseline-band law to benchmark runs, flagging or redoing thermally compromised runs.
3. **Redefine the epoch as a hash tuple** — harness version, profile digest, toolset hash, task-set hash, engine + build ID, calibration band — published as a manifest with results; docs-only changes declared epoch-preserving.
4. **Flip D24's arms**: fixed packaging for all models becomes the headline; size-scaled packaging becomes a secondary ablation on 2–3 models across size bands, with per-row format-error-rate and tool-call parse-rate columns (aider's "well formed %" precedent). Decide the twin OPEN question (protocol per-model vs text-for-all) the same way, in one pre-registered document, before the sweep.
5. **Add exit-status transparency and a no-submit control**: publish Submitted/Budget/Loop breakdowns next to every headline (mini's exit_status precedent), and grade one pilot subset with no submit sentinel to quantify what the protocol itself costs small models.
6. **Add a bash-only reference harness as a control**: a mini-SWE-agent-style minimal runner over a task subset, run once per epoch, to measure how much of the headline is harness-sensitive (the DeepSWE/SWE-agent lesson quantified on this suite).
7. **Golden grader tests + wire-byte equality tests**: same terminal state must grade identically regardless of producer; instrumentation on/off must produce byte-identical request streams; embedding API provably cannot loosen limits (P15 as property test).
