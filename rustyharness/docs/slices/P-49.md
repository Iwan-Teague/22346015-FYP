# P-49 — `rustyharness schedule`: a timed, unattended run

Slice card: `schedule add --name N --task T [--daily HH:MM | --every Nh]`
installs a user-level launchd plist (macOS) or systemd user service+timer
(other unix) whose command runs the validated bundle unattended, plus
`schedule list`, `schedule remove`, and `schedule run-now`. Crates
touched: `harness-cli` only. Deps: P-07 (config/state root), P-14
(bundles and their digest habits), P-18 (the input seam).

## What landed

- **Storage** — `<state-root>/schedules/<name>/` (0700 dir, 0600 files):
  `task.json`, `profile.json`, `policy.json` (only when a policy file was
  given) are byte-exact copies of the files `add` validated, and
  `schedule.json` records the cadence, the absolutized workspace and
  state root, the endpoint, the three input digests (the same digests the
  run header journals), `"policy"` (`policy.json` or `default`), the
  `no-default-denies` setting and the creation time. All private (0600).
- **add** refuses before anything else: `--allow-exec`, `--preset`,
  `--shell` (usage error); an existing schedule with the same name
  (unreadable input); and — before any other validation — a task without
  an explicit `budget` section (`steps` or `wall_secs`). Then the full
  `run` validation runs, the exact launcher file and manifest are printed
  to stdout, and nothing is written until the input feed answers `y` /
  `yes` (anything else, or end of input, leaves the disk untouched and
  still exits 0: declining is not failing).
- **Launchers** — macOS: `~/Library/LaunchAgents/com.rustyharness
  .schedule.<name>.plist`; other unix:
  `~/.config/systemd/user/rustyharness-<name>.{service,timer}`; written
  0600, created 0700 on the way. The binary never loads them; the exact
  `launchctl load` / `systemctl --user daemon-reload && enable --now`
  commands are printed instead. `$RUSTYHARNESS_SCHEDULE_HOME` (absolute,
  or refused) moves the launcher directory for tests and sandboxes.
- **run-now** is a gate child under the `rustyharness.schedule` gate id:
  it reloads `schedule.json`, re-digests the stored inputs (task text
  sha256, profile content digest, policy under the recorded overlay
  setting — the same spellings the run bundle self-check uses), re-checks
  the explicit budget, rebuilds the option map the run pipeline expects,
  and calls the ordinary `run` path with the approver forced to nobody.
  The last stdout line is its `GateReport`.
- **list / remove** are plain verbs: sorted rows
  (`name=… cadence=… installed=… next=… workspace=… endpoint=…`, an
  `UNREADABLE (why)` row for a manifest that does not parse), and a
  confirm-then-delete that touches only the named bundle directory and
  its own launcher files, refusing anything that is not a plain
  directory/file.

## Decisions

- **The launcher runs `schedule run-now --name <name>`** and nothing
  else. An earlier sketch put the full `run` invocation (bundle paths,
  endpoint) in the launcher argv; that would have copied the endpoint —
  and anything else the launcher renders — into `~/Library/LaunchAgents`,
  which is not 0600 by default and is not the user's private state. With
  `run-now`, the launcher carries only the binary path and the schedule
  name; every input, the endpoint and the workspace live in the 0600
  bundle, and every fire re-checks the digests before anything runs.
  This also makes the launcher trivially secret-free (`plist_has_no_
  secrets` holds canaries against it).
- **Unattended means approver `None` unconditionally.** `run` asks at a
  real terminal (§5.3); `schedule run-now` previews a run no person will
  watch, so its approver is nobody even when launched from a terminal —
  every ask is denied and journaled as `PolicyDecided … "no_approver"`
  (`run_or_resume_unattended` forces what a non-tty stdin gives `run`).
- **`next=` is a UTC estimate.** launchd and systemd fire daily schedules
  at *local* HH:MM; the journal's `rfc3339_utc` and this binary have no
  timezone database (reading local time would need libc `localtime`, and
  `unsafe` is forbidden). So `list` computes the next occurrence of
  HH:MM on the UTC clock and the usage text says it is an estimate. The
  `--every` rows print `next=-`: a steady interval has no next wall-clock
  slot the binary can name.
- **Names are stricter than run ids' `plain_name`**: 1..=64 of ASCII
  alphanumerics, `-`, `_`, starting alphanumeric. The name becomes part
  of a launchd label and a systemd unit file name, where dots and `+`
  would invite confusion with other units (and `remove` treats the name
  as a path component, so anything else is refused).
- **The confirmation reuses `Cx.input`** (the `chat` REPL's seam): the
  first `Given` line, else one line of this process's stdin, `y`/`yes`
  trimmed case-insensitive. No new plumbing, and tests inject lines the
  same way they inject chat input.
- **The journal and the audit are untouched**: a scheduled run is an
  ordinary run (its own run id, header, blobs, session row), so
  `sessions`, `events` and `replay` need no changes and no new
  `EventKind`s exist.

## Deviations from the sketch

- Launcher argv is `run-now` (above), not the full `run` command.
- `--allow-exec`/`--preset`/`--shell` are refused outright by `add`
  (usage error), not merely unsupported: a timed run executes only what
  the task file's own `exec` section pins.
- Windows: `schedule add` refuses (no launcher location; the same
  posture as `state_root` there). `list`/`remove` still work on their
  state-root side.
