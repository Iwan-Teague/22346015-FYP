# P-37d — `harness-mcp-fixture`: the fake MCP server in Rust (design note §14)

## What landed

- `crates/harness-mcp-fixture/` (new, `publish = false`): the test-double
  MCP server of the P-37 design note §14. `std + serde_json` only, no
  other dependency, `#![forbid(unsafe_code)]`.
  - `src/lib.rs` — `serve(mode, input, output)` over newline-framed
    JSON-RPC 2.0 (§3.1): one message per `\n`-terminated UTF-8 line,
    flushed after every write so pipe-driven tests never stall. Reads are
    permissive (a real server is, too); writes are deterministic. The
    panic-set lints ratchet production code; the test module is allowed
    looser asserts.
  - `src/mode.rs` — `Mode::parse`/`Mode::as_str` for every hostile mode
    listed in §14 (`drift-description`, `drift-schema`,
    `rug-pull-after:<n>`, `vanish-after:<n>`, `list-changed-spam`,
    `malformed`, `huge-frame`, `slow-loris`, `wrong-id`, `string-id`,
    `double-response`, `result-and-error`, `flood`, `sampling`, `roots`,
    `elicit`, `ping`, `request-flood`, `batch`, `version:<v>`,
    `no-tools-capability`, `dup-tool-name`, `paginate:<pages>`,
    `instructions-injection`, `result-injection`, `exit-midcall`,
    `stderr-spam`, `hang`, `confinement-probe`) plus the benign `ok`.
    Unknown mode strings are a parse error, never a fallback.
  - `src/tools.rs` — the `ok` mode's two tools (`echo`, `add`), their
    descriptions/schemas as constants, and `ok_pins()`: the exact pin
    inputs a client must compute. No SHA-256 here — digests stay
    `harness-manifest`'s job (P-37a).
  - `src/probe.rs` — the `confinement-probe` tool: fixed + argument-named
    attempts at everything a confined server must never manage (write
    into HOME, read a planted canary, write into cwd, TCP connect, ...),
    one report line per attempt, all bounded (≤8 extras per kind, ≤200
    bytes per path).
  - `src/main.rs` — the `rh-mcp-fixture` bin: `--mode <m>` over real
    stdin/stdout; unknown or missing mode is a usage error (exit 2), so a
    typo'd test fails loudly instead of serving `ok`.
  - `src/tests.rs` — unit tests over in-memory pipes.
  - `tests/bin.rs` — end-to-end tests spawning the real binary via
    `CARGO_BIN_EXE_rh-mcp-fixture`, std pipes only.
  - `rh-fixture-workspace-canary` — a marker file in the crate dir the
    `confinement-probe`'s fixed cwd-write attempt collides with in
    end-to-end runs (cwd is the server's scratch dir, never the
    workspace).
- `Cargo.lock` — regenerated (`cargo update -w` style), per H-F.

## Hostile modes fire where a test can reach them

`initialize` is answered normally unless the mode exists specifically to
spoil it, so a hostile mode is observable over a normal connect with the
client's own deadlines/caps doing the catching (e.g. `slow-loris` is one
byte per 100 ms and is caught by the client's deadline, not by the
fixture refusing to start).

## Tests (all named in the slice card)

- `fixture_ok_mode_answers_initialize_list_call` — the `ok` baseline.
- `fixture_every_mode_parses` — `Mode::parse` round-trips every §14 mode
  string and rejects junk.
- `fixture_rug_pull_changes_description_after_n_calls` — the
  `rug-pull-after:<n>` list flip.
- `fixture_bin_speaks_newline_json` — the real binary over real pipes.
- `fixture_pins_helper_matches_ok_mode` — `ok_pins()` matches what the
  `ok` mode actually lists.

Plus the per-mode coverage the card's "every hostile mode" implies

## Notes / decisions

- The fixture is deliberately NOT pure harness code: it reads loosely and
  is only honest about output. The crate doc says this in so many words
  so a reviewer does not "fix" it.
- No journal/audit interaction: the fixture is a test double that no
  production code depends on (`harness-mcp` dev-depends on it), so
  nothing loop-visible happens here and `context_format` is untouched.
- Pins are inputs, not digests: `tools.rs` gives the exact bytes and
  `harness-manifest::pins` (P-37a) computes digests, so the fixture
  cannot drift from the reviewed descriptions.
