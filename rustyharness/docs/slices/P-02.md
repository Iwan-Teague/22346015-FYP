# P-02 — Built-in tool registry: one module + manifest fragment per tool

Splits the built-in tool declaration trio (hotspot H-C) so that adding a
built-in tool (P-24, P-25) adds files and table entries, not scattered
hunks. Behaviour is identical; the manifest bytes are pinned by a test
because the manifest sha is in every journal header (a drift would make
every old journal "another build").

## What changed

- `harness-manifest`: `BUILTIN_MANIFEST_JSON` is now
  `concat!(include_str!(...))` over `src/builtin/head.json`, one fragment
  per capability (`fs_read.json`, `fs_search.json`, `fs_glob.json`,
  `fs_list.json`, `edit_replace.json`, `edit_write.json`,
  `edit_multi.json`, `exec_run.json`, `task_todo.json`,
  `task_submit.json`) and `tail.json`, in manifest order. The fragments
  were cut mechanically from the former single literal; the concatenation
  is byte-identical (8452 bytes, sha256
  `7409f4604c8b93b94514fcff8b4bb43d733223c43fe2b7e5ca852baf4b789780`).
  A new capability is one fragment file plus one `include_str!` line.
- `harness-policy`: new `src/builtin.rs` moves the id constants, rule
  constants and the §4.8 labels predicates out of `lib.rs`, and adds a
  per-tool registration table: `BUILTIN_TOOLS: &[BuiltinTool]` with
  `{id, kind: ToolKind, labels: fn(&Capability) -> bool}`, in manifest
  order, plus `registration(id)`. Planning consults the table by id:
  the no-workspace refusal is `registration(id).needs_workspace()`
  (`ToolKind::Fs | Edit | Exec`), and the out-of-scope refusal is
  "non-read class with no matching table entry". The previously public
  constants stay public at the crate root via re-export, so nothing
  outside the crate changed.
- `harness-tools`: new `src/registry.rs` — the dispatch table
  `BUILTIN_TOOLS: &[BuiltinTool]` with `{id, ctor: ProviderCtor}`, in
  manifest order, plus `entry(id)` and `build(id, root)`.
  `ProviderCtor::Workspace(fn(&Path) -> Result<Box<dyn ToolProvider>,
  RootRefused>)` covers the read and edit tools; `Exec` names the
  command runner (it also needs the run's witnesses, which the run
  driver owns); `RunLoop` names the checklist and the submit sentinel
  (run-loop state, not providers).

## Equivalence argument

The policy table is consulted by id, where the old code used a prefix
check (`harness.fs.*`), a list (`EDIT_IDS`) and id equality (`EXEC_ID`)
for the workspace refusal, and four label predicates for the
out-of-scope refusal. The `harness` namespace is reserved (§4.3): only
the compiled-in manifest may use it, so the only `harness.*` ids
planning can ever see are the ten in the table. For those ten ids the
table reproduces the old checks exactly: the same four ids
(`needs_workspace`), and the same four label predicates (`labels`), with
the fs tools carrying `no_labels` so a non-read class under an fs id
stays out of scope. The `fs_tool` active flag (read window, path
checks) is unchanged: still the id-prefix + namespace check, not a
table lookup. `decide()` is untouched.

## Follow-up

`harness-run`'s driver still builds its three providers directly and
dispatches by `serves()`. Moving the driver onto
`harness_tools::registry` is deliberately out of scope here (P-02 does
not touch `harness-run`); the table is additive public API until then.

## Adding a built-in tool after P-02 (P-24/P-25 recipe)

1. One manifest fragment file + one `include_str!` line
   (`harness-manifest/src/builtin.rs`) — bytes change deliberately, and
   `builtin_manifest_bytes_unchanged` is updated with the new pinned sha.
2. One policy registration entry (`harness-policy/src/builtin.rs`), with
   kind and labels predicate (and rule constants if it has a named
   default rule).
3. One dispatch entry (`harness-tools/src/registry.rs`), with the ctor
   variant (or a new one if it needs run state beyond today's three).
4. The agreement test `builtin_registry_lists_ten_tools_in_order`
   (manifest == policy == tools, in order) fails until all three agree.

## Tests

- `harness-manifest`: `builtin_manifest_bytes_unchanged` pins the sha256
  of `BUILTIN_MANIFEST_JSON` to the pre-split value.
- `harness-policy`: `policy_default_table_unchanged` plans each of the
  ten tools alone and asserts the same decision under four policies:
  the default table (read allowed, edits and exec ask, todo and submit
  allowed by their rules), a user deny (`harness.*`), a user ask and a
  user allow.
- `harness-tools`: `builtin_registry_lists_ten_tools_in_order` asserts
  manifest, policy and tools tables list the same ten ids in the same
  order, that workspace entries build a provider serving their id over a
  real root, and that exec/todo/submit name their state.
- Full `cargo test --workspace` green; clippy `-D warnings` clean.
