# P-37c — MCP wire codec (frames, classification, encoders)

## What landed

- New crate `crates/harness-mcp` (publish=false, the workspace inherits it),
  deps per the purity registry only: `harness-core` (path, for the shared
  strict JSON reader), `serde_json`, `thiserror`. This slice is the pure
  wire codec of design note §3.1-§3.4 (`docs/slices/P-37-mcp-client.md`);
  the client state machine (P-37d), the provider and the confined
  connector (P-37e) and the renderer (P-37f) are later slices.
- `crates/harness-mcp/src/wire.rs`:
  - **Framing (§3.1).** `FrameReader` is fed the server's stdout bytes as
    they arrive (`feed(&mut self, &[u8]) -> Result<Vec<Frame>, WireFault>`),
    in any split, and returns every frame those bytes complete, in order;
    `finish()` refuses a stream that ends with a partial line buffered
    (`EofMidLine`). It is a push reader — like `harness-model-core`'s
    `SseReader` — so it never names `std::io`: the transport owns the pipe
    and the deadlines. `FRAME_MAX` = 1 MiB: the `OverCap` fault is raised
    exactly when one more byte would pass the cap, and the rest of the
    line is never buffered (a test feeds byte-by-byte and checks the fault
    lands at the cap, not at the newline). One JSON-RPC message per line;
    a trailing `\r` is refused (`TrailingCr`), not stripped — a server
    that writes CRLF is not speaking the tested transport — while a `\r`
    between tokens stays ordinary JSON whitespace (RFC 8259).
  - **Parsing.** Through `harness_core::strict_json::parse_typed`, so
    duplicate keys are refused at every depth (INV-22) and a non-object
    top level — a JSON-RPC batch array (removed in protocol
    `2025-06-18`) or a scalar — is refused (`NotAnObject`).
  - **Classification (§3.1).** `Incoming`: `Response` (`jsonrpc: "2.0"`,
    an id, exactly one of `result`/`error`), `ServerRequest` (id+method),
    `Notification` (method, no id); anything else is `BadMessage` — wrong
    or missing `jsonrpc`, a non-string `method`, both or neither of
    `result`/`error`, an `error` object without an integer `code` and a
    string `message`. `ResponsePayload::Error` reads `code`/`message`
    strictly and keeps `data` as untrusted `Option<Value>`. The raw line
    rides in the `Frame` (`frame.line`), which is what the journal keeps
    for `mcp_response` (§11), so audit re-renders from exactly what the
    server sent (§12).
  - **Ids (§3.2, §3.5).** `PeerId` is a string or an i64-range integer.
    `null`, floats, booleans and containers are refused; a fractionless
    float such as `2.0` arrives as a float and is refused too (tested).
    JSON-RPC 2.0 recommends ids of at most 2^53-1; larger integers are
    refused with the rest of the non-i64 range. Matching an id against the
    one outstanding request is the client's job (P-37e); the codec accepts
    every well-typed id.
  - **Encoding (§3.3, §3.4).** Compact JSON, keys sorted (serde_json's
    default `Map` = `BTreeMap`; no `preserve_order` anywhere in the
    workspace), bytes returned WITHOUT the trailing newline (the newline
    is transport framing). `encode_initialize` sends the negotiated
    protocol version, EMPTY capabilities (D3: no sampling, no roots, no
    elicitation) and `clientInfo` name `CLIENT_NAME` = `"rustyharness"` +
    the harness version passed in; `encode_initialized`;
    `encode_list` (`tools/list`; cursor pagination deferred to P-37e with
    the client that drives the pages); `encode_call` (`tools/call`, the
    name and arguments already validated against the manifest's schema,
    §6.1); `encode_method_not_found` — the only reply a server-initiated
    request ever gets (§3.5, D3), `-32601` / `"not supported"`, echoing
    the server's id as received. The bytes are a pure function of the
    encoder's arguments, so the journal's `mcp_request` digest (§11) is
    recomputable at audit (§12).
  - `WireFault` is `Copy` and every variant is a protocol violation (§4):
    the client kills the server and quarantines the provider; none is
    recoverable in place.
- `scripts/ci/purity.sh`: §2 content scan list gains
  `crates/harness-mcp` (rust_files) and its two files in the must-be-
  present checklist, with a comment noting P-37f adds the renderer. No
  facility carve-out was needed: the push-fed reader never names an I/O
  facility, so the full facility list applies unchanged (stricter than
  the design note's fs/net/process/env/path minimum). `purity.sh` passes
  with the crate scanned.

## Tests

`cargo test --locked -p harness-mcp`: 12 passed. The card's ten:

- `codec_refuses_malformed_json_line` — truncated, broken, trailing
  content, empty line.
- `codec_refuses_duplicate_keys` — top level and inside a `result`
  (every depth, INV-22).
- `codec_refuses_frame_over_cap_without_buffering_it` — byte-by-byte feed
  faults exactly at the cap (not at the newline); one-chunk feed faults
  the same; a line of exactly `FRAME_MAX` fails as JSON, not as over-cap.
- `codec_refuses_non_utf8` — bare and inside a string.
- `codec_refuses_trailing_cr` — CRLF refused on a scalar and on a
  would-classify line; mid-token `\r` is whitespace.
- `codec_refuses_batch_array` — batch array, number, string, `null`.
- `codec_classifies_request_notification_response` — result/error
  responses (string and integer ids, error with `data`), server request,
  notification, plus the `BadMessage` shapes: neither/both of
  result+error, `jsonrpc` "1.0" or absent, non-integer error `code`,
  missing error `message`, non-string `method`, no method and no id.
- `codec_refuses_null_or_float_id` — `null`, `1.5`, `2.0` (fractionless
  float), `true`, on both a response and a server request.
- `encode_call_is_deterministic_and_sorted` — same bytes twice; exact
  sorted string asserted.
- `encode_initialize_has_empty_capabilities` — exact string, version
  parameterised.

Plus two:

- `encode_initialized_list_and_32601_are_exact` — the notification, the
  list request, and the `-32601` reply echoing integer and string ids.
- `reader_yields_every_frame_and_finishes_clean_at_eof` — frames split
  mid-chunk; the partial line yields nothing until completed;
  `finish()` refuses mid-line and passes at a frame boundary; the raw
  line is preserved on the frame.

## Interpretations and notes for the manager

- **Push-fed reader.** The card said "fed bytes"; implemented as the
  `SseReader` shape (`feed`/`finish`, no `std::io` named). This keeps the
  file under the purity gate's full facility list with no carve-out, and
  keeps the transport (pipe, deadlines, kill) entirely in P-37e's hands.
- **Id range.** Accepted ids are strings and i64 integers (the wider of
  the two serde-backed choices); `null`/floats refused per §3.5. Ids
  above 2^53-1 are refused with them; if the manager wants a 2^53 cap
  enforced in the codec instead, it is a one-line narrowing in
  `peer_id`.
- **Unknown top-level keys are ignored**, and `params` is passed through
  unchecked: classification keys only on the fields §3.1 names; anything
  else is untrusted data this codec never reads. The renderer (P-37f)
  reads response payloads as untrusted; the client (P-37e) reads `params`
  if any shape needs it.
- **Cursor pagination** (`tools/list` `cursor` param, `nextCursor`) is
  deferred to P-37e with the paging client; `encode_list` sends no
  cursor, which matches the first page's shape exactly.
- **render.rs scan-list addition deferred to P-37f** with the renderer
  itself (comment left in purity.sh).
- 4.x loop rules (journal event, `audit` recomputation,
  `assert_audit_clean`, `context_format`) do not apply: the codec is not
  loop-visible — it is called by the client slice, which journals.
