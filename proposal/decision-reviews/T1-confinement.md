## D10 — No VMs, no external container runtimes; native OS sandboxing only

**Restate.** Every run executes under native per-OS primitives (Linux namespaces+Landlock+seccomp, macOS Seatbelt, Windows AppContainer+Job); no Docker/Podman/VM, because a VM reserves RAM the local model needs and containers are not how people run coding agents.

**Prior art.** OpenHands (https://github.com/All-Hands-AI/OpenHands) — Docker runtime is the default execution environment; Gemini CLI (https://github.com/google-gemini/gemini-cli) — Docker/Podman/macOS Seatbelt/gVisor `runsc`; note it closed a Docker-socket sandbox escape in v0.58.0-preview (PR #28935, per mindpattern.ai — secondhand, UNVERIFIED), a concrete cost of the container path; Devin (https://docs.devin.ai) — per-session cloud container/VM (third-party summaries, UNVERIFIED); Codex CLI (https://developers.openai.com/codex/sandboxing; repo https://github.com/openai/codex) — macOS `sandbox-exec`, Linux bubblewrap **or** bundled helper requiring unprivileged userns, i.e. external helper dependency; Anthropic sandbox-runtime "srt" (https://github.com/anthropics/sandbox-runtime) — `sandbox-exec`/bubblewrap + proxies; Bazel (https://bazel.build/docs/sandboxing) — the strongest precedent **for** the design: Bazel built its own `linux-sandbox` (namespaces) and `darwin-sandbox` rather than depend on a container runtime; Cursor — native Seatbelt/Landlock agent sandbox (arXiv paper "Don't Let AI Agents YOLO Your Files", Apr 2026); Goose (https://github.com/block/goose), opencode (https://opencode.ai/docs/permissions), Cline (https://github.com/cline/cline, UNVERIFIED), Aider (https://aider.chat, UNVERIFIED) — no OS sandbox at all, approval prompts only.

**Attack.** (1) The two Linux leaders (Codex, srt) both shell out to bwrap; D10 forbids that, so the design must rebuild mount/table logic Codex gets for free — a real speed cost, mitigated by the S-L1 trio needing no mounts at all. (2) The AppArmor fact cuts both ways: D10's "native namespaces" claim fails unprivileged on stock Ubuntu 24.04, so on the canonical downloaders' distro the only working native shape is the namespace-less trio; D10 survives, D29 does not (below). (3) Scope: OI-24 keeps the suite's own agent fleet pointed at VM/container as the target for unattended-at-scale runs; D10 must stay explicitly scoped to rustyharness standalone (design OD-6 already says suite OI-24 untouched — keep it that way in all prose). (4) The RAM argument is strongest exactly on the owner's MacBook (model on loopback, D12) and weakens on a 32 GB Linux box — but the portability win of "same primitives everywhere" still favors D10.

**Better.** Nothing materially better for these criteria. Add explicit revisit triggers so "no containers" never silently rots: host without systemd user session (breaks the S-L1 trio), a need for UDP/raw networking tiers, or Windows-native shapes that only work via WSL2 (Codex offers WSL2 as the strong Windows path).

**Verdict: KEEP.** Confidence: high.

## D21 — macOS cleanup: corrected sandbox_check membership sweep in H2; dated fallback (~1 Nov) to process-group kill for exec.run only

**Restate.** Orphan-kill on macOS is done by enumerating all user processes and killing exactly those that are sandboxed AND allowed a per-run marker AND refuse a sibling deny-marker (freeze-then-kill, ~26 ms/pass measured); if not built by ~1 Nov, accept process-group kill in writing for exec.run only.

**Prior art.** Codex (repo https://github.com/openai/codex, `codex-rs/sandboxing/src/seatbelt.rs`) — Seatbelt via `sandbox-exec`, no published orphan-recovery mechanism beyond process groups; Claude Code/srt (https://github.com/anthropics/sandbox-runtime) — sandbox-exec profiles + violation-log monitoring, no membership sweep; Bazel `darwin-sandbox` (https://bazel.build/docs/sandboxing) — sandbox-exec plus process-wrapper signaling; Bazel solves tree-kill reliably only on Linux via PID namespaces, implicitly conceding the macOS gap; Gemini CLI — container/Seatbelt, no kill story published; Cursor agent sandbox (Seatbelt) — no tree-kill claims (UNVERIFIED). Conclusion: **no surveyed harness has a robust macOS orphan-kill**; the setsid escape (M-4/M-5, confirmed on this MacBook) is an open industry gap, and the sweep is the first measured answer I can find.

**Attack.** (1) Novelty is risk: the sweep rests on `sandbox_check`, which is not in the SDK header (only `sandbox_init`/`sandbox_free_error` are declared, both deprecated) — the same private-API class as `sandbox-exec` that Q8 already worries about. Apple could break both at once. The design's own answer (probe → refuse) is the right hedge; add it explicitly to the sweep, not just to execution. (2) The sweep's correctness lives or dies on the negative controls: M-2 showed the drafted discriminator matched 121 of 757 bystander processes; the corrected three-part test matched exactly one. FT-37..40 negative controls and INV-50 are therefore not nice-to-haves, they are the mechanism. (3) The fallback is the quiet danger: a dated written acceptance is honest, but "exec.run only" still lets a double-forked grandchild of a Level-1 run survive with the run marked Passed unless the taint machinery (DD-14) already lands — sequence DD-14 before any fallback use. (4) The alternative that closes the gap structurally — run the sandbox under a dedicated OS account and kill by uid (F-2 option B) — is exactly what the industry converged on elsewhere: srt's Windows alpha uses a dedicated `srt-sandbox` local user + WFP fence keyed on the SID; Codex Windows "elevated" uses "dedicated lower-privilege sandbox users" (https://developers.openai.com/codex/windows/windows-sandbox); the suite itself just accepted this shape on Linux (OI-38). On macOS it costs an admin setup step, one concurrent run per account, and kills the standalone zero-setup UX — right for the suite tier (OI-24 fleet), wrong as the default here.

**Better.** Keep sweep-in-H2, but: couple it to P5 so there is exactly one audited private-API surface on macOS; require the live self-probe to include a planted setsid escape (the exact M-5 scenario) so regression is caught by the conformance mint, not by review; and pre-write the OI-38-style account option as the suite-tier upgrade path so the standalone/suite split stays clean.

**Verdict: KEEP.** Confidence: high (mechanism measured; risk is API longevity, handled by existing probe posture).

## D22 — Every test including network runs on Linux AND macOS for anyone who downloads the app; Linux first

**Restate.** The platform claim is two-OS symmetric including the network family; Windows is explicitly long-term-not-now; ordering may be Linux-first as a temporary pilot matter only.

**Prior art.** Codex — macOS/Linux/Windows all sandboxed natively today (Windows: elevated/unelevated modes; WSL2 alternative), the only surveyed harness with three working native backends; Claude Code/srt — macOS + Linux production, Windows alpha behind a one-time install; Gemini CLI — cross-platform but leans on Docker/Podman for Linux, Seatbelt on macOS; OpenHands — cross-platform via Docker (different trade); opencode/Cline/Aider — cross-platform precisely by *not* sandboxing, which is the counterfactual D22 refuses; Cursor — shipped macOS sandboxing first, Linux later per arXiv survey (UNVERIFIED ordering), i.e. even a well-resourced team staged OS parity.

**Attack.** (1) The macOS network family is the least-measured surface in the entire program: M-7's residuals (0.0.0.0/LAN reach of a `localhost:P` rule, wildcard-vs-specific, [::1]) are explicitly UNVERIFIED and were correctly deferred to S-M1/S-N1 on a disposable runner. Committing to "network tests green on macOS" before those results exist is the one way D22 can burn the mid-Nov date. (2) The builtin asymmetry the draft already conceded (macOS needs "normal server code" via the interposer, §5.4) means macOS network tests test *the interposer* too — a second failure surface Linux doesn't have; the FT set must name interposer-behavior cases separately from Seatbelt-behavior cases, or a red CI row won't localize. (3) Practical scope honesty: "anyone who downloads the app" today is graders and peers on PolyForm-licensed source; the bar is right for reproducible results (D16/D18 ethos) but should not be used to force Windows parity — and it isn't. (4) Counter-consideration: dropping macOS network (the reviewer-drafted "network tasks Linux only" end state) would have silently made the owner's primary machine second-class for the FYP's headline demo; D22 correctly rejected that.

**Better.** Keep D22 as the end-state contract, and make the ordering rule concrete: Linux first is not merely "allowed", it is the plan (13.4), and macOS network exit is gated on S-M1/S-N1 results, not on the calendar. That converts D22 from a promise into a dependency chain, which is what a two-eyes review can actually check.

**Verdict: KEEP.** Confidence: high.

## D27 — One shared confinement library for rustyharness + rustybenchmark, staged inside rustyharness during H2, moved to its own repo before the benchmark uses it

**Restate.** The confinement backends become one library with neutral names (`confine-*`, `CONFINE_*`), developed inside rustyharness during H2 and extracted before the benchmark consumes it — reversing OD-4's "two implementations" lean.

**Prior art.** srt (https://github.com/anthropics/sandbox-runtime) — literally this shape: a standalone, reusable sandbox library+CLI extracted from Claude Code's needs, consumed by an embedding agent; Codex (https://github.com/openai/codex) — `codex-linux-sandbox` exists as a standalone executable, and `bwrap.rs`/`landlock.rs` as separable modules — staging-inside-then-extracting is exactly their layout; Bazel's `linux-sandbox` (https://bazel.build/docs/sandboxing) — a standalone binary others reuse as a primitive; Gemini CLI's SandboxManager — kept in-repo, which is what D27 avoids post-extraction; bubblewrap itself — proof that a narrow sandbox primitive survives as an independent project. The benchmark's own AQ-208 backend is today the counter-example: a separate implementation, reviewed SOUND and green (r1435, 44 backend tests) — D27's job is to converge them without regressing either.

**Attack.** (1) Documentation coherence: OD-4 in the design still records the opposite lean as OPEN (open-questions item 4); D27 must be written back into the design, or the two-eyes trail contradicts itself. (2) The staging period is an API-freeze hazard: H2 churns the fastest exactly when the benchmark would start binding to the crate; "moved before benchmark uses it" is the guard, but give it teeth — the extracted crate gets its own version pin per results epoch (D16 analog) and the benchmark never tracks `main` (ADR-026 gives the branch discipline to do this). (3) Double-review cost: CF-28 already accepts two new audited unsafe crates plus a cdylib; the shared-library decision is what *justifies* that cost (one audit serves two consumers) — but only if the benchmark's AQ-208 Linux shape and the harness Linux backend actually converge (see D29). If they diverge, D27 degrades into a shared name over two behaviors, the worst outcome. (4) Sequencing risk: the pieces the harness needs first (sweep FFI, interposer) are not the pieces the benchmark needs first (Linux backend). Extract the Linux backend first.

**Better.** Keep the decision; add two clauses: (a) extraction order = Linux backend first (benchmark-ready, already SOUND), macOS pieces follow once S-M2 proves the sweep; (b) the library's conformance FT suite is the shared artifact — both consumers run the same FT data (design §6.6 already commits to "as data + per-OS matrix"), which is the strongest technical argument for sharing and should be stated in the ADR.

**Verdict: KEEP.** Confidence: medium-high (hinges on the D29 convergence actually happening).

## D29 — Linux: one private network namespace per run (not per spawn) in H2

**Restate.** H2 builds a per-run supervisor that sets up one private netns (loopback down) for the whole run, nested PID ns per spawn for kill, ports enabled later by bringing loopback up.

**Prior art.** Codex (https://developers.openai.com/codex/sandboxing; repo) — bwrap with network namespace where "the only route to the outside is through the proxy", falling back to a helper needing unprivileged userns; srt (https://github.com/anthropics/sandbox-runtime) — goes further: the sandbox's network namespace is **removed entirely**, proxies reached over a bind-mounted unix socket; Bazel `linux-sandbox` (https://bazel.build/docs/sandboxing) — namespaces incl. netns optional, PID ns chosen specifically "to reliably kill all processes (even daemons spawned by the action)" — the exact job D29's kill domain does; OpenHands — Docker (netns included); Gemini CLI — Docker/Podman/runsc on Linux; Bazel also documents the failure class D29 hits: "on some platforms … user namespaces are deactivated by default" and it **falls back** to a weaker strategy rather than refusing.

**Attack.** This is the decision the charter facts move most. (1) **Availability on the canonical distro:** S-L1 proved stock Ubuntu 24.04 (the owner's Linux test box runs 24.04.4 / kernel 6.8.0-139) blocks `CLONE_NEWUSER` host-wide (AppArmor `kernel.apparmor_restrict_unprivileged_userns=1`); netns requires userns first. So D29's backend **refuses on stock Ubuntu 24.04** — the distro D22 names for "anyone who downloads the app" — unless an admin profile is installed first (A-1 concedes this, UNVERIFIED per distro). Codex ships exactly this workaround: a `bwrap-userns-restrict` AppArmor profile (bundled in Ubuntu 25.04's `apparmor` package; on 24.04 users must copy it from extra-profiles and `apparmor_parser -r`), and still documents warning-and-failure modes on 24.04. That is the single biggest install-friction item in Codex's Linux story; adopting it voluntarily, in a solo FYP, buys little. (2) **A second Linux backend already exists and won:** AQ-208's namespace-less trio (Landlock ABI 4 files+TCP with `HardRequirement`/`FullyEnforced` asserted, seccomp deny list incl. `socket()` and now the mandated `clone(CLONE_NEW*)` rule, systemd user scope with MemoryMax/TasksMax, cgroup tree-kill via `systemctl --user stop` proven in-spike) is accepted (OI-41), independently reviewed SOUND, implemented and green (r1435). It needs no privilege, no profile, no supervisor process with CAP_SYS_ADMIN in a userns — which also deletes F-15's entire supervisor-mechanics finding (PDEATHSIG threading, init-in-namespace confusion, unfiltered supervisor). (3) **The same-user signal residual that netns was partly covering is being closed anyway** by OI-38's dedicated grading user (accepted; closes kill-others and the freeze attack from the AQ-208 review F-1). (4) **What is genuinely lost without netns:** host loopback becomes reachable, so the model server's port and the harness's own ports must be denied *explicitly* — but Landlock CONNECT_TCP/BIND_TCP grants (ABI 4, kernel 6.7+) do exactly that in-kernel, the spike proved TCP/UDP/DNS all blocked with `socket()` denied, and the planted-AF_UNIX leak (FT-9) is closed by deny-`socket()` (normal offline cargo control passed). Newer kernels blunt the remaining edges further: ABI 6 scopes abstract-UNIX-sockets + signals (kernel 6.12, matching the charter's "signal scoping needs 6.12"), ABI 9 adds `FS_RESOLVE_UNIX` for pathname sockets, ABI 10 adds UDP port rules, and Landlock's own docs confirm a **port-0 bind rule grants a kernel-assigned ephemeral port** — which maps one-to-one onto DD-6's anonymous pool. None of that existed when the design chose netns; most of it exists on the owner's 6.8 box. (5) Counterpoint in netns's favor that must be recorded honestly: netns makes "any port" safe (D33) and makes loopback isolation unconditional rather than rule-mediated; srt chose *no* network stack at all — stronger than both. As an opt-in tier for hosts where userns works, per-run netns remains strictly better isolation and should not be deleted.

**Better (MODIFY).** Invert the default, keep the enhancement: default Linux backend = the S-L1 trio (no namespaces), identical to the benchmark's accepted backend, so D27's shared crate converges on one Linux behavior, stock Ubuntu works with zero admin steps, H2 speed improves (no per-run supervisor to build), and the kill story is cgroup tree-kill (proven) instead of nested-PID-ns mechanics. Ports on the trio: Landlock-granted only (ABI 4), port 0 = ephemeral grant, kernels <6.7 → ports fail-closed (see D33). Per-run netns becomes an opt-in capability tier, probed at runtime and recorded in the header's host facts (already designed: "confinement_roots/env/cargo/network incl loopback kind"), enabled deliberately via the AppArmor-profile route where wanted. Trade-offs: security — rule-mediated loopback instead of namespace isolation; mitigations above; the residual "inherited fds bypass Landlock" (kernel docs: pre-open files/fds are not subject to Landlock) is shared by both shapes and already handled by never passing listeners into the sandbox. Performance — systemd-run user scope adds milliseconds; fine. UX — dramatically better (no admin prompt, no profile dance). Speed — reusing a reviewed SOUND backend is the fastest credible route to H2 exit; writing the netns supervisor in parallel is exactly the duplicate work D27 exists to prevent. Long-term soundness — systemd user session becomes an availability requirement (fail-closed on non-systemd distros: acceptable, must be a documented verb result, not a crash). The AppArmor-profile idea from the brief then lands in its right place: **not** a rescue for the default backend, but the opt-in switch that enables the stronger netns tier.

**Verdict: MODIFY.** Confidence: high on direction (charter facts are measured and accepted); medium on timing (H2 must re-baseline §6.3/D-architecture, which is real work — but less than building the supervisor).

## D33 — Linux kernels < 6.7 (no Landlock network rules): allow any port inside the per-run private namespace

**Restate.** Where Landlock TCP rules are unavailable, ports are unrestricted because the per-run netns already guarantees nothing outside the run is reachable.

**Prior art.** Bazel (https://bazel.build/docs/sandboxing) — netns-optional design with explicit capability fallback (`processwrapper-sandbox`), the pattern of "degrade by capability, say so"; srt — refuses to pretend: no netns ⇒ no network path at all (proxies only), i.e. capability matrix, not one rule; Codex — documents per-surface requirements (bwrap vs helper vs userns) instead of a single kernel cliff; kernel Landlock docs (https://docs.kernel.org/userspace-api/landlock.html) — ABI 4 = TCP bind/connect (6.7+), ABI 10 = UDP, plus an **errata** mechanism (e.g. Erratum 1: non-TCP stream sockets like MPTCP/SMC/SCTP were wrongly caught by TCP rules on unfixed kernels) that a port-discipline backend should consult or consciously ignore.

**Attack.** (1) Under D29-as-written the clause is coherent; under the recommended namespace-less default it is unreachable and misleading — worse, its inverse would be dangerous: "any port" without a netns on a <6.7 kernel means the sandbox can bind the model server's port on the host. There is no world where D33's generosity survives losing the namespace; the decision must be re-anchored to the capability that actually provides the safety (netns), not to the kernel version. (2) The 6.7 cliff is aging well (6.7 = Jan 2024; Ubuntu 24.04 ships 6.8), but Debian 12 (6.1) exists and is the plausible second distro — UNVERIFIED whether Debian backports Landlock TCP; if it doesn't, ports must refuse there, and D33-as-written would look like the design promising ports it can't deliver. (3) The "any port" clause also interacts with DD-13 (fresh/exclusive listeners): inside a private netns, port collision detection is meaningless across runs (each netns has its own loopback) — the exclusivity property silently changes meaning per backend; the header's host-facts record must carry the backend so audit reads the right semantics.

**Better (MODIFY).** Replace the single rule with a capability-matrix verb result recorded per run: {netns available? Landlock ABI (4/6/9/10)? systemd user scope?} → ports: `none` / `granted-only` / `any-in-private-netns`; refuse with a precise reason otherwise (the Unavailable pattern already in the design, and the AQ-208 principle "grading refuses where the backend can't fully set up"). Fold in the errata check as a recorded host fact (consult, don't gate). Trade-offs: more paths to test; mitigated because the FT data is already per-OS-per-capability shaped.

**Verdict: MODIFY (reframe as capability matrix with fail-closed default).** Confidence: high.

## P5 — Build the direct `sandbox_init` FFI path now, in the audited macOS crate already needed for the sweep

**Restate.** Stop depending on the deprecated `/usr/bin/sandbox-exec` binary; load profiles via FFI from the same audited unsafe crate the D21 sweep requires.

**Prior art.** Codex (repo `seatbelt.rs`) — still invokes `/usr/bin/sandbox-exec` with compiled SBPL; srt (https://github.com/anthropics/sandbox-runtime) — `sandbox-exec` with dynamically generated profiles; Bazel `darwin-sandbox` — `sandbox-exec`, and documents that nesting fails and triggers fallback; Gemini CLI — `sandbox-exec` per survey references. Every surveyed macOS sandboxing harness rides the deprecated binary; none ships an `sandbox_init` FFI path (UNVERIFIED beyond these six). The design would be first — which is both the opportunity and the risk. The measurement trail adds: `sandbox-exec` execs in place (M-9), profiles are generated to a temp dir, and `sandbox_check` is not in the SDK header at all (F-1) — the private/deprecated surface is one family.

**Attack.** (1) "Now" is doing work it shouldn't: while `sandbox-exec` loads profiles fine, the FFI buys nothing user-visible; Apple deprecations of this API have been pending for a decade. The honest scheduling unit is "same crate, same review, sequenced right after the sweep proves out (S-M2)", not "now, before the sweep". (2) FFI changes failure modes: a malformed profile under `sandbox-exec` yields a clean exit; a malformed profile under `sandbox_init` yields a NULL + error string or, worse, a crash inside the harness process — the audit/crash story must be written (wrap init in the child pre-exec, treat init failure as Unavailable, never fall back to unsandboxed). (3) Doing both `sandbox_check` and `sandbox_init` in one crate is right (one threat-model, one review), but note the asymmetry: check is process-enumeration logic the harness itself runs; init must run **outside** the confinement it creates. Test both orderings (FFI-init then spawn; spawn then FFI-check) in the FT set.

**Better.** Keep the direction, adjust the trigger: build the audited macOS crate for the sweep first; land `sandbox_init` in the same crate immediately after S-M2 is green; keep a `sandbox-exec`-removal probe in CI as the canary that justifies the whole path. Trade-offs: a few weeks of exposure to deprecation risk vs concentrated review effort — the owner's stated preference (do it properly now) supports compressing both into one reviewed unit; that's compatible with sequencing inside the unit.

**Verdict: KEEP.** Confidence: high.

## P6 — Windows: run the S-W1 AppContainer spike during H2; ship the backend after Linux+macOS

**Restate.** Spike whether cargo/rustc run inside an AppContainer with network capabilities absent; ship a Windows execution backend only if it passes; otherwise Windows stays read-only.

**Prior art.** Codex (https://developers.openai.com/codex/windows/windows-sandbox) — shipped **two native modes**: `elevated` (dedicated lower-privilege sandbox **users**, filesystem permission boundaries, firewall rules, private desktop by default) and `unelevated` (restricted token derived from the current user + ACL boundaries + environment-level offline controls, "weaker but useful"), with enterprise admins able to force `allowed_sandbox_implementations`; earlier history judged AppContainer insufficient (the design's own §6.3 note; corroborated by the salvaged leads' Windows post, codex.danielvaughan.com, UNVERIFIED detail); Anthropic srt Windows alpha (https://github.com/anthropics/sandbox-runtime) — one-elevated-step `windows-install` creates a dedicated `srt-sandbox` local user, WFP egress fence keyed on that SID + per-session ACEs, job object, and explicitly claims this "structurally closes the surrogate-spawn class of escape (Task Scheduler, `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, BITS, out-of-process COM)"; Claude Code — Windows via srt alpha; Gemini CLI/OpenHands — no native Windows sandbox (containers/WSL); opencode/Cline/Aider — no OS sandbox on Windows either. Clear industry convergence: **dedicated account + WFP/firewall fence**, with restricted-token+ACL as the no-admin fallback — not AppContainer-first.

**Attack.** (1) S-W1 as scoped ("AppContainer") spikes the mechanism both leaders retreated from; the design's own §6.3 already records Codex's judgment. Running a spike whose likeliest result is "insufficient" spends scarce H2 time to confirm a known lean. (2) The design's Job Object analysis ("not a boundary, only resource + tree-kill") is right, but the pairing worth testing is job + **WFP fence keyed on a SID**, because WFP closes network at the kernel for *any* process the child spawns — including the surrogate-spawn escapes F-18 names for Windows (Task Scheduler/WMI). (3) OI-42 defers Windows to an "S-W1 volume-query spike" while the harness's S-W1 is the AppContainer exec spike — one label, two scopes; a two-eyes reviewer cannot tell which gate opens Windows execution. Rename one. (4) UX: the winning shape costs one UAC prompt at install (srt precedent) — acceptable, but it must be opt-in at install, never required for the read-only mode (Q4/OI-42 stance preserved).

**Better (MODIFY).** Re-scope S-W1 as a three-way comparison on one question — "can cargo/rustc run with writes confined, network kernel-blocked, and orphans tree-killed?" — across (a) AppContainer + Job (as planned), (b) restricted token + ACLs + job (Codex `unelevated` analog; no admin), (c) dedicated local user + WFP + job (srt/Codex `elevated` analog; one admin step, aligns with OI-38's install pattern). Keep ship-after-Linux+macOS and read-only-until-proven exactly as is. Trade-offs: a broader spike costs more H2 hours; mitigate by testing (c) first (highest prior), (a) only if (c) fails in the owner's environment. Confidence in the prior is high because both shippers converged on it independently.

**Verdict: MODIFY (spike scope; phasing unchanged).** Confidence: medium (Windows facts are well-sourced but unverified on this machine).

## P7 — Raise MSRV 1.85 → 1.89 for std file locks (journal single-writer lock, per-endpoint run limit, gc run lock)

**Restate.** Use `std::fs::File::{lock, try_lock}` (stable since 1.89) instead of a locking crate; bump `rust-version` from 1.85 accordingly.

**Prior art.** Rust 1.89.0 (Aug 2025) stabilized `File::lock/lock_shared/try_lock/try_lock_shared/unlock` (release notes, blog.rust-lang.org; corroborated by public repos recording that they dropped `fs4` once 1.89 landed). MSRV practice: libraries routinely hold older MSRVs for downstream compat; end-user applications and tools do not — ripgrep and cargo effectively track recent stable (UNVERIFIED exact policies); Codex (https://github.com/openai/codex) is a Rust agent harness shipping native binaries with current toolchains (UNVERIFIED MSRV declaration); opencode similarly ships binaries, not a lib.

**Attack.** (1) The only real cost is a hypothetical distro-packaged rustc older than 1.89 (Debian stable rustc versions lag; UNVERIFIED which version Debian 13 ships). The project isn't targeting distro packaging; D16's pinned-toolchain ethos makes this moot for results reproducibility — the journal pins the harness version, not the OS rustc. (2) The alternative — keep 1.85 and add `fs4`/`fd-lock` — contradicts the design's own supply-chain discipline (each dependency is audit surface; CF-28 already concedes two unsafe crates it cannot avoid; this one it *can*). (3) Correctness pressure is real: journal single-writer locking and gc-vs-run exclusion are exactly where flock-via-crate half-measures (PID files, O_EXCL) reintroduce the TOCTOU class the design elsewhere killed with `O_NOFOLLOW`/identity re-checks (§4.3, M-19). Std flocks are advisory, survive crash cleanly, and need no cleanup logic — gc collecting stale lock *files* (DD-15) becomes trivial because there are none.

**Better.** Keep the bump; write the MSRV policy down (e.g. "latest stable at the start of each phase, bumps allowed at phase boundaries only") so 1.89 doesn't become 1.92 by drift mid-H2; assert `rust-version` in CI (cargo already enforces it).

**Verdict: KEEP.** Confidence: high.

## P15 — Windows ports stay off until spikes pass; embedders may only lower limits, never raise

**Restate.** Windows port grants/background processes are refused (asserted in CI) until S-W1+S-W2 pass; configuration can tighten the harness's limits but never loosen them beyond harness constants.

**Prior art.** Codex (https://developers.openai.com/codex/windows/windows-sandbox) — `requirements.toml` with `allowed_sandbox_implementations` lets an administrator *forbid the weaker* Windows sandbox — the same asymmetry ("choose among what the harness allows, only downward") at org scale; Goose (https://github.com/block/goose) — its permission inspectors "can only tighten permissions, never relax them" (asymmetric override, verified in repo-derived docs); srt (https://github.com/anthropics/sandbox-runtime) — warns that `allowAppleEvents`/trustd options "open exfiltration vectors" and must be sourced **only from trusted user-level configuration, never project-local files** — the embedder trust-boundary doctrine P15 encodes; opencode (https://opencode.ai/docs/permissions) — allow/ask/deny per tool with no raise path (trivially compliant since it has no sandbox to raise).

**Attack.** (1) "Never raise" needs a defined ceiling or it erodes: DD-6 caps (16 named/32 anonymous ports), DD-3 root caps (16/32/8), DD-11 tool_groups — every one must be a harness constant, not a config default; the moment a cap is "just a default", a config layer above it (A-12's precedence: `--config` > env > files) becomes a raise vector. Audit the precedence surface: policy-bearing keys should not be env-settable at all. (2) The enforcement test is missing: add a conformance case that a fully attacker-controlled config file (writable root, project-local) cannot express any raising delta — this is FT-able and belongs in the §6.6 corpus. (3) The Windows-off half is right and consistent with OQ-3 (refusals asserted in CI), and with the fact that even Codex gates its *strongest* Windows mode behind admin setup — "off until proven" is stricter but correct for a confinement platform whose brand is fail-closed.

**Better.** Keep as is; add (a) the raise-vector FT case, (b) journal the effective policy digest (extend the existing `confinement`/`tools` header keys with `policy`) so audit can see which ceiling applied.

**Verdict: KEEP.** Confidence: high.

## Ideas from the brief, evaluated

**Seccomp user notification + `SECCOMP_IOCTL_NOTIF_ADDFD` as a Linux analogue of D32's socket swap** (supervisor binds 127.0.0.1 itself, injects the listener fd into the sandboxed process's `bind()`). Facts (seccomp_unotify(2), https://man7.org/linux/man-pages/man2/seccomp_unotify.2.html): NOTIF_RECV since 5.0; `CONTINUE` 5.5; ADDFD 5.9; `SECCOMP_ADDFD_FLAG_SEND` (atomic addfd+respond) 5.14 — every kernel in scope (6.8, even 6.1) qualifies. The kernel text is blunt: the mechanism "must not be used to make security policy"; argument-reading races (TID reuse → `NOTIF_ID_VALID` between every read; signal-interrupted syscalls may abandon their arguments; SA_RESTART re-notifies repeatedly); writes into target memory are never safe. For `bind()` emulation specifically the shape is the *intended* use (supervisor performs the privileged action, spoofed return, ADDFD; kernel never executes the target's bind), so the residual risk is "which bytes did the supervisor read", not escape — but a sibling thread inside the target can rewrite the sockaddr between reads, so the implementation needs double-read+VALID discipline. **Verdict: do not build.** Under the netns tier it is unnecessary (binding inside a private netns touches no host state). Under the namespace-less default, Landlock ABI 4 does granted-port enforcement **in-kernel** with none of this machinery — and where Landlock TCP is missing (<6.7) the correct answer per D33-as-modified is to refuse ports, not to grow an unsandboxed supervisor thread with TOCTOU-hardened memory reads to serve a kernel population of one old Debian. Record it as a rejected alternative with its kernel-version precondition, so the next reviewer doesn't reopen it blind.

**One-time admin AppArmor profile allowing userns for the harness binary (to rescue D29).** Precedented and real: Codex ships exactly this (`bwrap-userns-restrict`; bundled in Ubuntu 25.04's apparmor package; manual copy + `apparmor_parser -r` on 24.04), and srt's README names the same remedy ("add an AppArmor profile that grants `userns` to the relevant binaries"). Costs: one admin step at install (OI-38 shows the owner accepts those at install time); a path-keyed profile that permanently widens userns creation for whatever binary sits at that path — so the helper must live on a root-owned path and the trust-base rules (§6.4) must treat path-swap as tampering. But note the inversion: with the D29-MODIFY default (namespace-less trio) this profile is **not needed for the product to work**; it becomes the opt-in switch that enables the stronger netns tier on hosts that want it. That is the right home for it: documented, optional, never load-bearing.
