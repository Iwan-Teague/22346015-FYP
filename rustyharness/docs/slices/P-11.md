# P-11: exec presets, PATH pinning and `--shell`

## What was built

A task that grants `harness.exec.run` no longer needs hand-written absolute
paths. For a task **without** an `exec` section, three new options build one
at startup, in the trust base (`crates/harness-cli/src/exec_presets.rs`,
wired into `inputs.rs`, so `run`, `resume` and `replay` all take them):

- `--allow-exec <name[,name]>` (or `exec_programs: ["cargo", ...]` in the
  user config) resolves each plain name against **this process's own PATH at
  startup**, refuses a non-absolute PATH entry when the search reaches it,
  canonicalises what it finds to one absolute real path, and refuses anything
  that does not resolve to an existing regular file (a broken symlink, a
  directory). First directory on the PATH wins.
- `--preset <rust|node|python|go>` adds the read-only root derived from the
  preset's anchor program (`rust`→`cargo`, `node`→`node`, `python`→`python3`,
  `go`→`go`): the binary's directory, or the toolchain root above a `bin`
  directory (`…/toolchains/1.88/bin/cargo` pins `…/toolchains/1.88`); the
  filesystem root is never a root. Rust's preset sets
  `CARGO_NET_OFFLINE=true`; `CARGO_TARGET_DIR`/`CARGO_HOME` scratch handling
  was already built (H2d). Limits are the §6.2 defaults for every preset
  today — the table is data, ready to tune. A preset whose anchor is not on
  `--allow-exec` is refused.
- `--shell` appends `sh`, resolved like any name; the header stamps
  `shell_enabled: true` from the name alone (harness-tools, §4.8).

Every program is printed before the run starts
(`will allow: sh -> /bin/sh`), with the preset's roots and variables.

Fail-closed rules (all unreadable input, exit 4, nothing runs or journals):
any of the flags combined with a task file that **has** an `exec` section
(that file already pins its programs); the flags without the
`harness.exec.run` grant; an unknown preset; a bad or duplicate name; more
than `MAX_PROGRAMS`; a name not on PATH; a relative PATH entry reached by the
search. Without the flags, a task without an exec section behaves exactly as
before.

## Header / audit

The resolved section is an ordinary `ExecSpec`, so the journal header's exec
input and `shell_enabled` stamp are the pre-existing machinery — no new event
kind, no context change (`rh-context/5` stands). `replay` and `resume` take
the same flags and re-resolve, so the audit compares like with like; a
replay without the flags diverges by name
("the exec allowlist given differs from the recorded header"), which the
`shell_flag_sets_shell_enabled_in_header` test asserts on both sides.

## Reading taken (brief ambiguity)

"Resolved task is written as JSON (feeds P-14)" is read as: the resolution
produces exactly the task file's `exec` form — `resolved_exec_matches_task_file_form`
asserts the built `ExecSpec` equals what the same `exec` JSON section builds —
so P-14 can store and re-feed it as a task file. No new file is written; the
header already records the digest. If the manager wants a written
`*.resolved.json` artifact, it is a small follow-up on this base.

Also: preset roots/env/limits are the preset's whole contribution (the brief
ties roots to presets), and `exec_programs` in the config conflicts with an
exec-bearing task file exactly like the flag does (a config must not silently
re-pin a task that pins itself). An empty `exec_programs` list means no
allowlist.

## Out of scope here

No `bash`/`zsh` preset (only `--shell`'s `sh`, per design §4.8); no
prefix/argv rules (that is P-08); no background processes (P-36). The
macOS-only header test mirrors the file's other run-that-executes tests: the
journal is written only past the witness (INV-6).
