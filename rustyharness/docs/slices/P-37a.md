# P-37a — Manifest pins, MCP version set, admission gate lift for (pinned, mcp-stdio)

## What landed

- `crates/harness-manifest/src/pins.rs` (new module) — the pure half of
  the pin story (P-37 design note §6.1, §3.3, D2, D5, D9):
  - `SUPPORTED_MCP_PROTOCOLS: &[&str] = &["2025-06-18"]` — the dialects
    this build speaks; adding one is a reviewed code change that brings
    its wire tests.
  - `negotiate(declared) -> Result<&'static str, NegotiateError>` — the
    highest entry of `SUPPORTED_MCP_PROTOCOLS ∩ declared` (D2; the
    fixed-width `YYYY-MM-DD` dates make "highest" the lexicographic
    maximum). None in common is a `NegotiateError`.
  - `description_digest(&str)` — SHA-256 over the exact UTF-8 bytes; a
    tool with no description hashes `""` (§6.1). The text is never
    inspected, only hashed byte-exact (D5).
  - `schema_digest(&Value)` — SHA-256 over the canonical JSON: compact,
    object keys sorted at every depth (`serde_json::Value` without
    `preserve_order` is a sorted map), numbers as `serde_json` prints
    them. `Display` cannot fail, so no encoding fault can sneak a
    fallback past a pin. The same parsed form is hashed at admission
    (reviewed manifest) and at connect (server `tools/list`).
  - `PresentedTool` — the server's untrusted `tools/list` claim for one
    tool, built by the caller; compared here, never shown to the model.
  - `PinStatus` (`ok` / `description` / `schema` / `missing` — the
    journal's `McpConnected.pins` spellings), `PinReport` (status per
    capability id, `dropped` count, `is_clean()`).
  - `compare(manifest, presented) -> Result<PinReport, CompareError>`:
    a presented name appearing twice is refused before anything is
    compared (D9; "first wins" would let a rug-pull hide behind the
    duplicate); every manifest capability gets a status; presented tools
    the manifest does not name are dropped and counted, never an error
    and never surfaced; either drift quarantines the capability
    (description checked first); an absent pin refuses as drift (the
    fail-closed reading of "required for non-builtin transports").
    Defined for mcp-stdio manifests only (`NotMcpStdio` otherwise).
- `crates/harness-manifest/src/lib.rs`: `pub mod pins;`.
- `crates/harness-manifest/src/admission.rs` — the phase gate lifts for
  exactly the (pinned, mcp-stdio) pair (§6.3):
  - `Registry::admit` now admits a `pinned` manifest over `mcp-stdio`,
    provided `pins::negotiate(m.mcp_protocols())` succeeds — none in
    common refuses AT ADMISSION, not hopefully at connect.
  - New `AdmissionError::ProtocolUnsupported { provider, supported,
    declared }` for the none-in-common refusal.
  - Still refused, unchanged: `signed` (signature verification, H4),
    pinned + in-process (the tier data rule stands: in-process is
    builtin or signed only), secret handles (H2). Defensive refusals
    cover transport/tier pairs a parsed manifest cannot produce, so a
    future parse regression refuses rather than trusts.
- `crates/harness-cli/src/cmd_manifest.rs`: the comment above the
  admission preview no longer claims H1 always refuses; the output
  already handled both outcomes dynamically, so `manifest check` on a
  pin-able mcp-stdio manifest now reports "this build would admit it".

## Required consequence (not a weakening)

- `crates/harness-cli/tests/cli.rs::
  inv_1_manifest_check_is_the_v1_admission_parser` asserted the example
  manifest (mcp-stdio, protocol `2025-06-18`) prints "would refuse it" /
  "arrives in H4". P-37a makes that manifest admit when pinned, so the
  two assertions became one: "this build would admit it". The refusal
  rows in the same test (v0, reserved namespace, duplicate keys,
  non-JSON, oversize, missing) are untouched.

## Ambiguity readings

- "none in common refuses" refuses at admission (§3.3), so a protocol
  the build does not speak never reaches a connect attempt.
- An absent pin in a manifest capability is drift, not a bypass: it
  cannot prove a match, and the manifest schema already requires pins
  for non-builtin transports.
- The gate lifts only for (pinned, mcp-stdio); a `signed` mcp-stdio
  manifest still waits for H4 signature verification, so tiers stay
  meaningful on the way to H4.
- `connect`/`McpConnected`/quarantine behaviour is P-37b+; this slice
  ships only the pure comparison and the admission-side refusal.
