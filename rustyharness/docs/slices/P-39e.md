# P-39e — Seatbelt `Network::Proxy{port}` and the airlock conformance cases

## What landed

- `crates/harness-sandbox/src/spec.rs`:
  - `Network::Proxy` becomes `Proxy { port: u16 }`; the never-used
    `allowlist_id` field is gone.
  - `Context` gains `proxy: bool` — whether the backend can express the
    loopback-only outbound allow. `validate` accepts `Proxy { port }`
    only with a nonzero port AND `cx.proxy`; anything else is refused
    (`SpecError::Limit("proxy port must not be 0")` for the zero port,
    `SpecError::Unsupported("a proxy network grant (Seatbelt only; §5.3)")`
    where the backend cannot grant it). Every other backend/phase keeps
    refusing proxy specs exactly as before.
  - `Validated` is UNCHANGED (see the pin note below): the caller renders
    the port from the same spec validate accepted.
- `crates/harness-sandbox/src/profile.rs`:
  - `render(v, proxy_port)` appends, after `(deny network*)`, exactly one
    rule when a port is granted:
    `(allow network-outbound (remote ip "localhost:<port>"))`. With
    `None` the profile is byte-identical to the old deny-all form (the
    P-36 convention), so the live probe digest and every existing exec
    is untouched.
- `crates/harness-sandbox/src/seatbelt.rs`: `start` derives
  `proxy_port` from `spec.network` after `validate` accepted it and
  passes it to `render`; its `Context` sets `proxy: true` (the Seatbelt
  profile can express the allow). No other file changed.
- `crates/harness-sandbox/src/conformance.rs`: new cases `Ft13P`
  (`FT-13-proxy`), `Ft15P` (`FT-15-proxy`), `Ft19` (`FT-19`), `Ft20`
  (`FT-20`) and `pub const AIRLOCK_CASES` = `H2_EXIT_CASES` + those four
  (spelled out; a `const` slice cannot concatenate). They are
  deliberately NOT in `H2_EXIT_CASES` or the matrix row: plain execution
  must not demand proxy behaviour; airlock consumers (P-39i/j) demand
  `AIRLOCK_CASES` via `Conformed::covers` (INV-46).
- `crates/harness-sandbox/tests/conformance_macos.rs`: the six proxy
  tests below, plus the INV-6 update (a real port now spawns; a zero
  port is refused before start).

## The SBPL spelling, measured on this host (the slice's first task)

Experiments with `/usr/bin/sandbox-exec`, macOS 26.5.1 (25F80) arm64,
profile = the real rendered base + the candidate allow after
`(deny network*)`:

- `(allow network-outbound (remote ip "localhost:PORT"))` — CONFIRMED:
  connect to `127.0.0.1:PORT` (a listener held by the test process)
  CONNECTS and exchanges bytes; any OTHER loopback port (with its own
  listener standing in for the model server), `::1` on the granted
  port, and TEST-NET `192.0.2.1:80` are all refused; bind (TCP and UDP
  on loopback) is refused. `deny network*` first, allow second (E6's
  later-rules-override) is required: the base alone refuses everything.
- `(remote ip "127.0.0.1:PORT")` — refused at profile COMPILE time:
  `sandbox-exec: host must be * or localhost in network address`. So
  the design's `localhost` spelling is the only parseable one.
- `localhost:PORT` matches IPv4 loopback only here; `::1` to the same
  port stays denied. The fetcher dials `127.0.0.1:<port>` (§5.2), so
  this is sufficient and strictly tighter. The test suite pins this
  behaviour (`ft19_other_loopback_port_refused` covers a different
  port; `granted_port_connects` covers the granted one end to end).
- No `system-socket` allow is needed: socket(2) creation is not gated
  beyond the network filters on this host (connect returns EACCES/EPERM
  under `deny network*`).

## Interpretations and notes for the manager

- **Pin kept, not moved.** The card says "does not touch
  `confine_spawn.rs` or `capture.rs`: no purity pin moves". My first
  design put the port in `Validated`, which forces a fixture edit in
  `confine_spawn.rs`'s test module (its `limits_spec()` literal) and so
  a pin move. To honour the card I kept `Validated` unchanged and gave
  `profile::render` a second parameter instead; `seatbelt.rs` derives
  the port from the same spec validate accepted, so an unvalidated
  port cannot reach render. If the manager prefers the port inside
  `Validated` (type-level pairing at the cost of one pin move, which
  purity.sh's own failure message sanctions), that is a small
  follow-up.
- `Context.proxy` is the fail-closed gate: a future backend that
  cannot spell the allow simply constructs `Context` with `proxy:
  false` and keeps refusing, with no code path changes.
- AIRLOCK_CASES consumption (a research session refuses to plan unless
  the witness covers it, lib.rs `require`/`covers` path) is P-39i/j's
  job per the design note; this slice only defines the set.
- 4.1's loop rules (journal event, audit recompute, `assert_audit_
  clean`, `context_format`) do not apply: nothing loop-visible changes
  (no proxy spec is produced by any caller yet; `Network::None` renders
  byte-identically).
- The stale-profile risk the design note names (§14): if a spelling had
  not passed, the slice would keep refusing `Proxy`; it passed, so the
  refusal message changed shape only in the new `Context.proxy` gate.
