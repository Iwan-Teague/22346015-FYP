# P-08 — policy argument matchers

## What

`UserPolicy` rules can now carry a `match` object that narrows a selector
to the calls whose canonical arguments satisfy it (design §4.8, R1 §3.1's
Codex-style rules): `allow cargo test` but `ask git push`, `allow` edits
under `src/**`, deny `.env`. The §5.1 order never moves — deny > ask >
allow > default deny, first match within a list, an allow never lowers a
floor — only what each rule reaches.

## Format

A policy file (v2) is still `{"deny": …, "ask": …, "allow": …}`. A rule
is a v1 selector string, or an object:

```json
{"capability": "harness.exec.run",
 "match": {"argv_prefix": ["cargo", "test"]},
 "examples": [{"args": {"argv": ["cargo", "test"]}, "expect": "match"}]}
```

`match` conditions: `path_glob` (the string at `path` against the pure
glob), `argv_prefix`, `argv_not_prefix`. Every present condition must
hold; a condition whose argument is absent or mis-shaped never holds
(fail-closed — a matcher does not guess). Unknown keys, empty prefixes,
empty `match` objects and globs the matcher refuses reject the whole file;
the same selector with different matchers is two rules, the same rule
twice is refused as before. A rule's `examples` are checked at load and a
failing one refuses the file. v1 files parse identically and digest
identically (a matcher rule appends its canonical JSON after a TAB on its
digest line, so old journals stay verifiable).

## Semantics

- A deny matcher denies only the calls it covers, then falls through.
- An ask matcher asks only about the calls it covers and does NOT raise
  the capability's confirmation floor; an unconditional ask rule does, as
  before. The user rule is credited only at exactly `user_confirm`.
- An allow matcher allows only the calls it covers; a class-derived floor
  (e.g. `personal`) still asks.
