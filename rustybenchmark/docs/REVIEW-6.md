### `signtest-null-false-by-construction` — The precomputation detector's sign test has a null hypothesis that is false by construction, and fires on ~100% of honest runs

**SEVERE** · *verifier lowered severity* · surface: `bench-stats` · docs: `docs/adr/0009-paired-core-and-fresh-probe-seeds.md`, `docs/10-integrity.md`, `docs/07-statistics.md`, `docs/14-roadmap.md`

**Defect.** ADR-0009 and 10-integrity.md specify `precompute_signal = sign_test(family-paired core-vs-probe discordance)` and justify it with "Under honest execution the discordance is symmetric." The test needs one bit per family from core and one from probe. But `deep` runs FOUR core seeds per family against ONE probe seed (1088 core / 163 probe), and `standard` runs TWO against one. No document anywhere says how the k core seeds collapse to the single bit, and no document defines a pass predicate on the continuous `task_score` in the first place. The stated symmetry holds ONLY at k=1. For every k>1 the imbalance is structural, not evidential.

**Failure scenario.** An honest submitter completes a `deep` run. The server collapses the family's 4 core seeds with the most natural rule and compares against the 1 probe seed. Simulation (163 probed families, ICC 0.3, layered-oracle score model): false-accusation rate is 100.0% for the `any` rule at every threshold tested (1e-9, 0.3, 0.5, 0.7, 0.9), 99.9-100% for `all`, 24.9-100% for `mean>=thr`, and 5.9-88.4% for `majority`. Only `first seed` (k=1, discarding 3 of 4 core seeds) is calibrated, at 2.8-4.5%. An independent analytic model with no oracle simulation at all (family pass-prob ~ Beta(1.2,2.0), k core seeds vs 1 probe seed) agrees: E[b]/E[c] = 8.54 and sign-test |z| = 6.7 for `any` at k=4; 0.07 and |z| = 6.4 for `all`; |z| = 3.7 at k=2 for both. |z| = 0.0 only at k=1. Two differently-shaped models, same conclusion.

**Evidence.** Simulation scratchpad/signtest.py; independent analytic cross-check scratchpad/analytic.py. Spec text: docs/adr/0009-paired-core-and-fresh-probe-seeds.md:36-38 ("Count families where core passed and probe failed against the reverse"), docs/10-integrity.md:63-66.

**Resolution.** Three things must be written down before bench-stats is built. (1) A pass predicate on `task_score`, stated once and used everywhere. (2) The core-seed collapse rule -- and the only one that preserves the sign test's null is one core seed against one probe seed, drawn at a pre-registered index, which discards 3/4 of the available core evidence. (3) If that cost is unacceptable, replace the sign test with a test whose null survives unequal k: a paired comparison of the family's mean core score against its probe score (Wilcoxon signed-rank or a cluster bootstrap of the mean difference), which uses all seeds and is symmetric under honest execution by construction. Note that R3-S3's published ~5.2-point sensitivity was necessarily computed at k=1 and does not transfer to any k>1 rule.

**Verifier.** CONFIRMED mathematically and by a third model shape. I derived the exact identity E[b]-E[c] = E[P(B=1|p)] - E[p] for family pass-prob p, k core seeds vs 1 probe seed: the sign test's null holds iff the collapsed core bit is marginally calibrated to a single seed. Every deterministic k>1 collapse breaks it. Logistic random-effects MC over 163 families, 2000 honest runs: any k=4 100%, all k=4 100%, majority k=4 53.7%, mean>=0.5 k=4 51.2%, pick-one 4.2%; at k=2 (standard) 96-98% for all rules but pick-one (3.3%). Spec text verified verbatim: ADR-0009:36-39 and 10-integrity.md:63-66 assert 'honest execution is symmetric' with no collapse rule and no pass predicate. NOT covered by rounds 1-5. Severity lowered to moderate on three reachability grounds the finding does not account for. (1) The failure is LOUD, not silent - a 100% flag rate on honest runs is discovered on the first test run, and no leaderboard number depends on the detector. (2) REVIEW-4.md:29 already names the baseline collapse in-repo: 'Family-aggregate pairing (compare all 4 core seeds against the probe rather than one designated seed...)' - the parenthetical establishes 'one designated seed' (k=1, calibrated) as the default reading. (3) docs/14-roadmap.md:106-107 already schedules 'Estimate baseline core-vs-probe discordance per family, which the sign-test detector needs in order to be calibrated', so a calibration step exists before deployment. It remains a real spec gap because the two normative documents state a symmetry that is only true at k=1 and never say so.

**Verifier correction.** Drop the absolute claim 'No document anywhere says how the k core seeds collapse to the single bit'. REVIEW-4.md:29 does say it ('rather than one designated seed'). The accurate statement is that neither NORMATIVE document (ADR-0009, 10-integrity.md) states the rule, and the symmetry both publish is valid only at k=1. Add the closed-form result, which is stronger than any simulation: under honest execution E[b]-E[c] = E[P(B=1|p)] - E[p], so the sign-test null survives exactly those collapse rules whose output is marginally distributed as a single seed - 'pick a pre-registered index' and randomised selection, nothing else. Also note that REVIEW-4.md:29's own family-aggregate simulation reported 0% detection at 20% precomputation, which is not reproducible under an uncalibrated k=4 sign test (it would fire on 100% of cells including the honest one), so R4-S1's family-aggregate row is itself suspect and should be re-run.

### `mcnemar-applied-to-continuous-task-score` — McNemar is specified for model comparison but `task_score` is continuous, no pass predicate exists anywhere, and three published metrics are therefore uncomputable

**SEVERE** · surface: `bench-stats` · docs: `docs/07-statistics.md`, `docs/03-oracle.md`, `docs/12-schemas.md`, `docs/00-overview.md`, `docs/05-hardware-and-calibration.md`, `docs/adr/0009-paired-core-and-fresh-probe-seeds.md`

**Defect.** docs/07-statistics.md:294 "Model comparisons use McNemar on the shared seed set, and state the discordant-pair count." McNemar is a test for paired BINARY outcomes. docs/03-oracle.md:14 defines `task_score = w_b*behavior + w_c*constraint + w_q*quality`, continuous on [0,1] -- behavior is itself a weighted mean of a unit-test fraction and two sub-oracles, constraint a weighted mean of five gates, quality a mixture including a continuous mutation score. A full-repo grep finds no definition of a pass/fail predicate on `task_score` anywhere in 25 documents. Three published metrics depend on that missing predicate: `throughput_score` ("tasks passed per wall-clock hour", 00-overview.md:37; `tasks_passed / wall_clock_hour`, 05-hardware.md:84; `"unit": "units_passed_per_hour"`, 12-schemas.md:188) and `time_to_first_pass_s`. This is orthogonal to R5's `ttfp-undefined-in-repair`, which is about which repair attempt counts, not about what "pass" means on a continuous score.

**Failure scenario.** Simulating the layered oracle at the documented default weights (200k units): `task_score` takes 97,838 distinct values, P(score = 0) = 47.5% (the L0/L1 gate), P(score = 1.0) = 0.0%, and 52.5% of units land strictly between. `throughput_score` therefore reads either 0 units/hour (if "passed" means score = 1.0, which never happens) or an arbitrary number set by an unwritten cut. On the comparison itself, at a true 5-point gap over a 40-family core category with rho = 0.25, the paired cluster bootstrap on the continuous score reaches 41.4% power; McNemar dichotomised reaches 28.2% at the best cut (0.5), 21.7-27.3% at other cuts, 18.7% at "compiled", and 0.0% at "perfect". The design's headline "free 2-4x power" from pairing is real -- measured 2.39x at rho=0, 2.34x at rho=0.25, 1.93x at rho=0.5 -- but ONLY on the continuous outcome with a cluster bootstrap. The estimator the design actually names throws away ~1.5x of it.

**Evidence.** scratchpad/mcnemar.py (distribution, power table) and shop.py part (d) (pairing gain). Grep confirming no pass predicate: no match for a task_score threshold in docs/*.md or docs/adr/*.md.

**Resolution.** Delete McNemar from the design. The correct paired estimator for a continuous bounded outcome is already specified elsewhere in the same document: the cluster bootstrap of the paired mean difference (07-statistics.md:278). Make that the sole model-comparison test, drop "state the discordant-pair count" (undefined for continuous data) in favour of reporting the paired mean difference with its cluster-bootstrap CI, and replace it in 07:294, ADR-0009:9/31, and 10-integrity.md:58. Separately, `throughput_score` and `time_to_first_pass` need either an explicit, pre-registered pass predicate written into 12-schemas.md, or redefinition on the continuous score (e.g. score-mass per hour), because as written they cannot be computed.

**Verifier.** CONFIRMED on the text and on the power claim. 07-statistics.md:294 reads exactly 'Model comparisons use McNemar on the shared seed set, and state the discordant-pair count.' 03-oracle.md:14-17 defines task_score as a continuous [0,1] composite ('Grading produces a vector, not a bit', 03:3). An exhaustive regex sweep of all 34 docs (score>=, 'counts as a pass', 'successful if', threshold-on-score) returns nothing: there is no pass predicate anywhere. Three published metrics depend on it - throughput_score (00:37, 05:84, 12-schemas:188 'units_passed_per_hour'), efficiency_score (00:44), time_to_first_pass (00:46) - and throughput is one of the two numbers the README's whole thesis names, so a headline metric is uncomputable as written. Independent power sim (compile gate + 24-test binomial behavior + 5-gate constraint + beta quality, 40 families x 4 seeds, rho 0.6, 1500 trials): continuous paired cluster bootstrap 45.8% power vs McNemar 26.9% at the best cut, ratio 1.70x (reviewer measured 1.47x - same direction, same order). Not covered by rounds 1-5: REVIEW.md M1 noted the binomial CI on a continuous score and closed it as a conservative bound; nothing addresses McNemar or the missing predicate.

**Verifier correction.** Two fixes and one addition. (1) 'P(score = 1.0) = 0.0%' is an artifact of the reviewer's generative model, not a property of the design - 03-oracle.md permits behavior = constraint = quality = 1.0, so task_score = 1.0 is attainable. Drop the 'throughput_score reads 0 units/hour' branch and rest the claim solely on the predicate being undefined. (2) The scope is wider than the finding states: pass@5 (07:253), 'Full trajectory required for passing units' / 'T1 rejects passing units without them' (10-integrity:165), and 15-profiles' verdict_agreement and 'paired oracle-verdict flips' (15:36, 15:560, 15:126) all consume the same missing predicate. (3) ADD a second, independent defect on the same line: McNemar as specified treats the 160 units of a core category as independent pairs and has no clustering term at all, while 07:278 says paired comparisons must resample families. So 07 specifies two mutually inconsistent model-comparison estimators - the cluster bootstrap of the paired difference (07:240-241, 07:278) and unclustered McNemar (07:294) - and the second would inflate type-I error even if the predicate existed.

### `dichotomisation-threshold-shopping` — With no dichotomisation cut specified, an analyst sweeping plausible cuts gets 23.3% type-I error and can move the reported effect size by a median 7.5 points on identical data

**SEVERE** · *verifier lowered severity* · surface: `bench-stats` · docs: `docs/07-statistics.md`, `docs/12-schemas.md`, `docs/10-integrity.md`, `docs/adr/0009-paired-core-and-fresh-probe-seeds.md`

**Defect.** Because both the McNemar comparison (07:294) and the sign-test detector (ADR-0009:36) require a bit and `task_score` is continuous, whoever implements `bench-stats` chooses a threshold. That choice is unconstrained, unrecorded, and not part of any schema, row key or replay artifact -- so it is invisible to T1 replay, to the public dump, and to independent re-derivation, which docs/README.md calls "the strongest integrity control the project has".

**Failure scenario.** Two IDENTICAL models over a 40-family core category, 4 seeds, 3000 trials. A fixed pre-registered cut gives a correctly-sized test (4.9-6.1% across nine cuts). An analyst who tries all nine and reports the one that reaches significance gets 23.3% type-I error -- 4.7x nominal. On effect size, at a true continuous gap of +5.0pp, the reported gap by cut ranges over a median of 7.50pp within a single dataset (95th percentile 13.12pp, maximum 21.88pp). The design's own claimability bar is that "Two models must differ by roughly 15 points before a core-category difference is claimable" -- an unrecorded analyst choice can manufacture most of that on its own. This also composes with the leaderboard's incentives: the submitter does not choose the cut, but the project does, once, for every published comparison, with no record of the alternatives.

**Evidence.** scratchpad/shop.py parts (a) and (b).

**Resolution.** The cleanest fix is to remove the degree of freedom entirely by adopting the continuous paired cluster bootstrap (see `mcnemar-applied-to-continuous-task-score`), which has no cut to shop. If any dichotomised statistic is retained -- the precomputation detector may need one -- the predicate must be (a) written into docs/12-schemas.md as a versioned constant, (b) included in `suite_version` or the row key so a change is visible, and (c) frozen before the epoch's data exists. Add a reporting rule to 07-statistics.md forbidding post-hoc threshold selection.

**Verifier.** Numbers REPLICATE under an independently written model. 2000 trials, 40 families x 4 seeds, nine cuts: fixed pre-registered cut 0.5 gives 3.4% type-I; sweeping all nine and reporting the best gives 14.5% - 4.3x nominal (reviewer measured 4.7x). Effect-size spread within a single dataset at a true 5.0pp continuous gap: median 7.50pp, p95 13.75pp, max 20.00pp (reviewer 7.50/13.12/21.88). Independent agreement is close. The architectural point is the durable one and is novel: the cut appears in no schema, no row key and no replay artifact, so it is invisible to T1 replay and to the independent re-derivation that README calls 'the strongest integrity control the project has'. Lowered to moderate because the failure scenario as written is contingent on an analyst actually sweeping cuts, and the design has a single analyst who writes bench-stats once - the reachable defect is the unrecorded, unversioned constant, not deliberate shopping, and that is the same root cause already carried by mcnemar-applied-to-continuous-task-score. Reporting it at severe would triple-count one root cause across three severe findings.

**Verifier correction.** Reframe from 'an analyst sweeping plausible cuts' to 'an unrecorded, unversioned constant that moves the published effect size by a median 7.5pp'. The shopping figure is the upper bound on the harm, not the expected case. Keep the resolution as written - the cut belongs in 12-schemas.md as a versioned constant inside suite_version - and note that if the continuous cluster bootstrap replaces McNemar per the companion finding, only the precomputation detector still needs a cut, which shrinks this to one predicate rather than two.

### `no-multiplicity-correction-anywhere` — There is no multiple-comparison correction anywhere in the repository, and the radar chart -- the product's headline feature -- carries a 94-99% family-wise error rate

**SEVERE** · *verifier lowered severity* · surface: `bench-stats` · docs: `docs/07-statistics.md`, `docs/15-profiles-and-divisions.md`, `docs/04-categories.md`, `docs/13-architecture.md`, `docs/adr/0008-core-and-probe-categories.md`

**Defect.** A grep for bonferroni, holm, sidak, multiplicity, family-wise, FWER, false discovery, FDR and per-comparison across all 25 documents returns zero hits. Meanwhile docs/07-statistics.md:293 explicitly licenses the comparisons: "Category comparisons within a model use the paired bootstrap, not overlapping-CI eyeballing", and :294 licenses model-vs-model comparisons, all at alpha 0.05. The leaderboard renders eleven per-category scores with CIs (15-profiles §10.2) and the design's stated purpose for the radar chart is claims of the form "better at traits than at lifetimes" (REVIEW.md S3).

**Failure scenario.** One model's radar chart licenses C(11,2) = 55 within-model category comparisons. At a correctly-sized 5% per-comparison rate the family-wise error rate is 94.05% and the expected number of false orderings is 2.8. At the per-comparison rate actually delivered by the specified estimator (8.5%, measured -- see `percentile-bootstrap-undercovers-at-small-cluster-counts`) the FWER is 99.24% and the expected count is 4.7. So the first radar chart the project publishes will, with near-certainty, contain at least one category ordering that is not real -- and this is the feature REVIEW.md S3 reshaped the entire category design to make supportable. Across the leaderboard it is worse: a 10-model board makes 45 x 11 = 495 category comparisons (24.8 expected false claims); a 20-model board makes 2,090 (104.5 expected false claims). The design has no mechanism that would ever notice.

**Evidence.** scratchpad/boot_fix.py part (C), with the 8.5% per-comparison rate taken from part (B) of the same script.

**Resolution.** Decide and document the inferential family, then correct within it. Concretely: (1) for the within-model radar, either apply Holm-Bonferroni over the 55 pairs or -- better for the product -- stop making pairwise ordering claims and render simultaneous confidence bands (Tukey-style, or a bootstrap max-t band over the 11 categories), which is what a radar chart should carry anyway; (2) for the leaderboard, control FDR across the displayed comparison set rather than FWER, and publish the correction used; (3) add the detector's alpha to the same budget, since it is a hypothesis test evaluated on every submission. Every one of these changes widens intervals, so it interacts with the sizing tables in 07-statistics.md and must be applied before the ADR-0008 family budgets are re-derived, not after.

**Verifier.** The DEFECT is real and novel - a grep for bonferroni/holm/sidak/multiplicity/family-wise/FWER/FDR/per-comparison across all 34 documents returns zero hits, while 07:293 explicitly licenses within-model category comparisons and 07:294 licenses model-vs-model, all at alpha 0.05. No prior round touches it. But BOTH headline numbers are wrong and I could not reproduce either. (a) 1-0.95^55 = 94.05% assumes independent comparisons. The 55 pairs share means and are strongly positively dependent; simulating 11 independent category means with all-pairs z tests over 200,000 draws gives FWER 67.6% at per-comparison 5% and 82.4% at 8.5% - not 94.05%/99.24%. (b) The design already forbids the comparisons that make up 45 of the 55 pairs: 07:243-244 states 'Probe category scores are never ranked... A +/-19.6% error bar cannot support an ordering and should not be presented as if it could', and REVIEW.md S3 defines probe as 'explicitly directional-only, never ranked'. The licensed radar set is the 5 core categories = 10 pairs, where simulated FWER is 28.6% at 5% and 41.9% at 8.5%, with 0.50 expected false orderings, not 2.8. REVIEW.md S3's own motivating example, 'better at traits than at lifetimes', is a core-core comparison. So 'the first radar chart the project publishes will, with near-certainty, contain at least one category ordering that is not real' is false as stated (28.6%). Survives at moderate on the corrected arithmetic, which still shows a real uncorrected multiplicity problem, largest on the leaderboard.

**Verifier correction.** Replace every number. Within-model radar: 5 rankable core categories, 10 pairs, FWER 28.6% at a correctly-sized 5% and 41.9% at the 8.5% the specified estimator actually delivers; expected false orderings 0.50 and 0.85. Leaderboard: a 10-model board makes 45 x 5 = 225 category comparisons (E[false] 11.25) and a 20-model board 190 x 5 = 950 (E[false] 47.5) - not 495 and 2,090. Drop the 'near-certainty' framing. The resolution (Holm over the licensed pairs, or simultaneous max-t bands on the radar, or FDR across the displayed leaderboard set) stands unchanged and is still worth doing.

### `percentile-bootstrap-undercovers-at-small-cluster-counts` — The specified percentile cluster bootstrap under-covers at every per-category cluster count -- 92% at a core category, 84% at idiom-refactor -- and doubles the type-I error of the ranking claim

**SEVERE** · surface: `bench-stats` · docs: `docs/07-statistics.md`, `docs/13-architecture.md`, `docs/12-schemas.md`

**Defect.** docs/07-statistics.md:268-273 specifies a plain percentile cluster bootstrap: resample clusters with replacement, report the 2.5th and 97.5th percentiles. It carries no small-cluster correction -- no t-multiplier, no G/(G-1) scaling, no BCa, no studentisation, no cluster-wild variant. The nonparametric cluster bootstrap is a large-G procedure; the design applies it at G = 16 (a core category's shapes, per R4-S5), G = 12 (a probe category), and G = 5 (idiom-refactor's measured transform catalogue, per R5-S3). This is ORTHOGONAL to R5's `two-level-bootstrap-undercovers`: it persists when the shape level is modelled perfectly, because it is a property of the resampling method, not of the clustering model.

**Failure scenario.** Simulating the exact specified procedure against a correctly-specified shape -> family -> seed generating process with ICC_family 0.30 and ICC_shape 0.10, 3000-4000 trials each, coverage of a nominal 95% interval measures: 94.8% at 152 shapes (the whole corpus -- correct), 92.7% at 20, 92.0% at 16 (a core category, the tier the leaderboard ranks on), 90.8% at 12 (a probe category), and 83.9% at 5 (idiom-refactor). Misses are roughly symmetric, so the intervals are too NARROW rather than mis-centred. The consequence for the actual leaderboard claim: the type-I error of "model A differs from model B on this core category", made with the specified paired cluster bootstrap on two identical models, measures 7.9% at G=16 and 9.1% at G=12 against a nominal 5% -- 1.6 to 1.8x. Every per-category CI the project publishes is labelled 95% and is 84-92%.

**Evidence.** scratchpad/boot_cov.py (coverage) and boot_fix.py parts (A) and (B) (corrections and type-I error).

**Resolution.** The fix is cheap and was measured to work. Scaling the percentile interval about the point estimate by t_{G-1,0.975}/1.96 * sqrt(G/(G-1)) restores coverage to 94.7-95.1% at every G tested (the factor is 1.011 at G=152, 1.123 at G=16, 1.173 at G=12, 1.584 at G=5). A cluster-wild bootstrap-t with Rademacher weights restores 94.6-96.0% and is the more standard answer. Specify one of them in 07-statistics.md's CI-computation block, and add the coverage check to the bench-stats property-test list in 13-architecture.md:102, which currently says only "property tests against synthetic data with known ICC and known effect sizes" -- known ICC is not the same as verified coverage, and no round has checked coverage.

**Verifier.** CONFIRMED three ways. Spec text verified: 07:268-273 is a plain percentile cluster bootstrap ('report 2.5th and 97.5th percentiles') with no t-multiplier, no G/(G-1), no BCa, no studentisation. My own simulation used a different outcome shape (logistic-squashed bounded outcome, shape->family->seed, ICC_shape 0.10 / ICC_family 0.30, 4000 trials, 800 bootstrap reps) and reproduced within ~1pp at every G: 94.2% at 152, 93.1% at 20, 91.7% at 16, 91.3% at 12, 84.7% at 5, against the reviewer's 94.8/92.7/92.0/90.8/83.9. Both match exact theory: the percentile bootstrap of a mean is the normal interval with the /G plug-in SD, so coverage = P(|t_{G-1}| < 1.96*sqrt((G-1)/G)) = 0.948/0.931/0.923/0.913/0.846. Their correction factor is exactly t_{G-1,.975}/1.96 * sqrt(G/(G-1)) (1.011/1.096/1.123/1.173/1.584) and restores 94.4-94.9% in my sim, so the proposed fix is verified, not asserted. Genuinely orthogonal to R5's two-level-bootstrap-undercovers: this persists when the shape level is modelled perfectly. Severity stays severe - it silently makes every published per-category 95% interval an 84-92% interval and inflates the type-I error of the leaderboard's central ranking claim by ~1.6x, and 13-architecture.md:102's test plan ('known ICC and known effect sizes') cannot detect it.

**Verifier correction.** Two caveats to add. (1) The G=5 row overstates: 07:88-90 already declares that idiom-refactor's clustering is crossed and 'no nested bootstrap is valid for it' (Q24 open), so 83.9% is coverage for an estimator the design has already withdrawn there - state the finding on G=11-16 (borrow-lifetimes publishes shapes: 11; unsafe-core measured ~16) and cite G=5 only as an illustration. (2) The magnitude is conditional on the bootstrap unit, which the same document contradicts itself about: at the family level still written at 07:266-272 a core category has G=40 and coverage is ~94%, a 1pp miss. So this finding and bootstrap-unit-contradiction-within-07 must be fixed together, and the coverage claim should be stated as 'once the shape-level unit at 07:84 is actually implemented'.

### `R6-S2` — The per-category context gate has two incompatible thresholds and a probe that measures the wrong quantity; applied consistently it refuses every run at the configuration the harness itself recommends

**SEVERE** · surface: `fix-created-holes` · docs: `docs/15-profiles-and-divisions.md`, `docs/04-categories.md`, `docs/05-hardware-and-calibration.md`, `docs/OPEN-QUESTIONS.md`

**Defect.** Three defects in one mechanism, all created by round 5's per-category gate. (a) The threshold is defined two ways 32,768 tokens apart: 04 §context-gate and 15 §2.4 derive `cross-module`'s `min_effective_ctx` as *source tokens + 32k completion budget = ~90k* (prompt **plus** budget), while 05's pre-run gate table says "Model context window smaller than the largest family's **prompt**" and "Effective context … below the suite's largest **prompt** → refuse" (prompt only, no budget term).
