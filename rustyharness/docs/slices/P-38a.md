# P-38a — Delegate capability: manifest fragment, policy registration, `plan_child`

## What landed

The delegate tool exists as declared, labelled and planned data (design note
§1, §9, §11). No loop code here: no one can call it yet, and nothing renders
it differently in context (the manifest fragment is the only new bytes the
model can see, which arrives with the P-38b loop slice and its
`rh-context` bump).

- **harness-manifest**: `builtin/task_delegate.rs` — the
  `harness.task.delegate {task}` fragment, byte-exact as cut from the design
  note: read / operational / own / none, `content: third_party`, no
  confirmation, schema `{task: string ≤ 2000}` with
  `additionalProperties: false`. Inserted in `builtin_manifest_json` between
  the checklist and the submit sentinel (before the sentinel, per the card).
  The built-in manifest digest moved, so `tests::builtin_manifest_bytes_unchanged`
  is re-pinned to the new digest (intended drift, P-38 §risk).
  A terse-doc entry (P-53 table, now 12 entries) covers the new id, since the
  P-53 tests require every built-in capability to have one.
- **harness-policy**: `DELEGATE_ID`, `ToolKind::Delegate` (`needs_workspace()`
  — a helper with nothing to read is waste), `is_builtin_delegate` (the exact
  label check; anything else under that id is not ours), `CHILD_ELIGIBLE`
  (the five built-in fs reads, fixed order — the caller appends the submit
  sentinel), `Active.delegate` (granted only explicitly, like edit/exec).
  `SessionRefused::DelegateScope` in `plan_with`: a granted delegate whose
  child scope could read above the delegate's own sensitivity is refused
  (D12) — the session's trifecta label must cover what a helper run reads.
  `Session::plan_child` with `SessionRefused::ChildScope` (D11): only the
  fs-read set and the submit sentinel plan into a helper run; a delegate
  grant on a child is refused, which is how the depth limit binds at grant
  time.
- **harness-tools**: the delegate joins the built-in dispatch table as
  `ProviderCtor::RunLoop` (run-loop state, not a provider — there is no
  `harness.task.delegate` constructor until the P-38b loop slice), and the
  registry cross-check test counts twelve.

## Decisions (fail-closed readings)

- The delegate is granted like any capability — explicitly in the session's
  grant list; nothing grants it implicitly, so without the grant a delegate
  call is the plain `NotGranted` deny. Once granted it is a read-class tool:
  under the default policy it decides allow through `allow.default.read` and
  authorize mints the approval with the same rule id
  (`delegate_allowed_by_default_read_rule_when_granted`).
- `CHILD_ELIGIBLE` is the five fs-read ids only. The todo tool is run-loop
  state a helper does not need; exec/edit are obviously out; the delegate
  itself is out (no recursion at grant time). Submit is appended by
  `plan_child`, not part of the constant, because a parent planning a child
  adds it; a profile listing `CHILD_ELIGIBLE` as grants does not get submit
  implicitly.
- Delegate scope check (D12): the child scope implied by the eligible grants
  must not read above the delegate's own sensitivity (`operational`). The
  fixture in `delegate_refused_when_child_scope_more_sensitive` plans via
  `plan_with` a delegate whose `harness.fs.read` grant (with
  `personal_data_granted`) can reach `personal` content — above
  `operational` → `SessionRefused::DelegateScope`; the same capability
  reached only through a non-eligible grant string plans fine (it is not the
  delegate's scope).
- Manifest digest drift is intended and pinned in the test (the card's
  "risk: low-medium"). The P-53 terse table text digest drifts with it; no
  separate pin exists for that text (P-53 pins coverage + arg names, not
  bytes), so nothing else needed re-pinning.
