## 0. Executive summary

1. **The harness matters about as much as the model, and for long-horizon tasks sometimes more.** Several controlled measurements show this:
   - Epoch AI: changing only the scaffold moved SWE-bench Verified by up to 11 pp for GPT-5 and up to 15 pp for Kimi K2 Thinking.
   - LangChain: changing only the harness took Terminal-Bench 2.0 from 52.8% to 66.5% on GPT-5.2-Codex.
   - A GAIA study found that scaffold choice alone moved accuracy by up to 28 pp.
   - SWE-agent's ablations show that individual interface choices are worth 3 to 8 pp each.

   So for a small team, the harness is the best place to put effort.
2. **Minimal harnesses can be strong, but only with strong models and a strong environment.** mini-swe-agent uses:
   - bash only, with no tool-calling API;
   - a linear history;
   - a stateless `subprocess.run` for each action;
   - a sentinel string to finish.

   It scores above 74% on SWE-bench Verified with frontier models. The reasons it works are clear: modern models already know bash, and each stateless step removes a whole class of harness bugs. The same design was worth much less with 2024 models (SWE-agent's shell-only baseline scored 11% against 18%). Small local models still gain from more structure.
3. **Most reliability failures belong to the harness, not the model.** Examples:
   - concurrent-state crashes (opencode's single SQLite database);
   - empty or truncated provider responses (Epoch);
   - patches that apply as a silent no-op (`git apply` from a subdirectory);
   - shell-quoting corruption of prompts;
   - premature "done" claims (MAST: 21% of multi-agent failures are verification or termination failures);
   - test tampering (ImpossibleBench: GPT-5 cheated on 76% of impossible-SWE-bench tasks, and read-only or hidden tests brought that close to zero).

   Each of these has a known mechanical fix, and none of the fixes depends on the model behaving well.
4. **The security consensus is kernel-enforced confinement plus policy, with prompts as a secondary layer.**
   - Claude Code uses Seatbelt and bubblewrap, with network access through an allowlist proxy outside the sandbox.
   - Codex CLI uses Seatbelt on macOS, bubblewrap plus seccomp on Linux (it has now demoted Landlock to "legacy"), and restricted tokens, ACLs and the firewall on Windows (it rejected AppContainer as too limited).

   Prompt-injection defenses that work do so by architecture: CaMeL keeps 77% of utility with provable security, compared with 84% undefended. Instructions that tell the model to ignore injected text are not a defense.
5. **Use MCP for the tool side, and do not invent a new wire protocol.** MCP 2026-07-28 is stateless, and Roots, Sampling and Logging are deprecated. rmcp, the official Rust SDK, is Tier 1, version 3.4.0, Apache-2.0, and on macOS, Linux and Windows it compiles no C. MCP's weak points (tool poisoning, rug pulls, shadowing, and the spec's own statement that annotations are untrusted) mean the harness needs a **suite-signed capability manifest** that sits alongside MCP. The harness should enforce policy from that manifest, never from what a server says about itself.
6. **In Rust, reuse the protocol crates and write the loop yourself.**
   - rmcp: reuse.
   - agent-client-protocol: reuse if we want editor or front-end integration.
   - OpenAI-compatible clients (async-openai, rig-core, genai): all three pull in `aws-lc-sys` (C plus CMake) through rustls defaults. rig and genai are also pre-1.0 or beta.
   - codex-rs (Apache-2.0, Rust) is the best reference implementation for sandboxing, exec policy, the network proxy and patch application. Study it and port the parts we need. Do not depend on it.
7. **Local models make tool calling fragile. Design for a text-protocol fallback and for grammar-constrained action blocks.** Evidence:
   - llama.cpp needs `--jinja` for native tool calls, and its generic handler is less reliable.
   - Aggressive KV-cache quantization "can substantially degrade" tool calling.
   - Qwen3-Coder stops emitting XML tool calls when prompts are large and there are many tools.
   - Constraining the model's *reasoning* to a format hurts accuracy ("Let Me Speak Freely").

   The resulting pattern: let the model reason in free text, constrain only the action block, keep the tool list small, and count format errors against a hard limit.
8. **Naming:** "harness" is now the industry's precise word for a model-agnostic runtime that drives a model through tools with sandbox and approval enforcement. OpenAI, Anthropic and LangChain all use it that way. Non-expert end users read "AI" as meaning the model or chatbot itself. Recommendation: name the project and crate **rustyharness**, and give the user-facing assistant feature its own friendly name.

**What this means for us.** A harness should be treated as a product that gets evaluated. We need our own fixed evaluation set, and every harness release should be scored against it. rustybenchmark already exists and is the obvious place to do this. The 35-releases study shows that harnesses regress silently.

### 1.2 SWE-agent: the Agent-Computer Interface (arXiv 2405.15793, May 2024) [P]

Ablation results from the paper (SWE-bench Lite, GPT-4 Turbo):

| Component | Variant | Score |
|---|---|---|
| Edit | none / no lint / **lint-guarded** | 10.3 / 15.0 / **18.0** |
| Search | none / iterative / **summarized (≤50 hits)** | 15.7 / 12.0 / **18.0** |
| File viewer | 30 lines / **100 lines** / full file | 14.3 / **18.0** / 12.7 |
| History | full / **last 5 observations** | 15.0 / **18.0** |
| Demonstration | removed | 16.3 |

Principles that follow from these results:
- **Guardrails at the point of action.** The edit command rejected edits that introduced syntax errors, and this was worth 3 pp.
- **Bounded, summarized observations.** Both "too little" and "too much" context hurt.
- **Never return a silent empty result.** When a command printed nothing, SWE-agent explicitly returned "Your command ran successfully and did not produce any output."
- **Collapse old observations.**

### 1.3 mini-swe-agent: why minimal works [P, source code read]

Repo: https://github.com/SWE-agent/mini-swe-agent (MIT). The README claims above 74% on SWE-bench Verified. The team also maintains the SWE-bench "bash-only" leaderboard, which uses mini as a fixed harness so that models can be compared.

Design, verified in `agents/default.py`, `environments/local.py` and `config/default.yaml`:
- **No tool-calling API.** The model writes exactly one fenced block tagged `mswea_bash_command`, so it works with any model, including ones that have no native tool calling.
- **Linear history.** The trajectory *is* the message list. This makes it easy to debug and to replay, and useful for fine-tuning and reinforcement learning.
- **Stateless execution.** Each action is a fresh `subprocess.Popen(shell=True)`. On timeout the whole process group is killed. The authors say of the stateless design: "This is a big deal for the stability of the agent, trust me." Swapping `subprocess` for `docker exec`, bubblewrap and so on makes sandboxing trivial.
- **Explicit stop.** The model finishes by running `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`. The environment accepts this only when it is on the first line of output *and* `returncode == 0`.
- **Hard limits** (`AgentConfig`): `step_limit`, `cost_limit` (defaults to 3.0 in the class), `wall_time_limit_seconds`, and `max_consecutive_format_errors = 3`. Hitting any limit ends the run with a typed exit status (`LimitsExceeded`, `TimeExceeded`, `RepeatedFormatError`, `Submitted`).
- **Environment hygiene.** It sets `PAGER=cat`, `MANPAGER=cat`, `TQDM_DISABLE=1` and `PIP_PROGRESS_BAR=off`, which prevents interactive hangs and noisy output. Output over 10,000 characters is truncated. There is a macOS-specific hint to use `sed -i ''`.
- **The trajectory is saved after every step** (`finally: self.save(...)`), so a crash still leaves a record.

**Why minimal works in 2025–26.** Frontier models are heavily trained on shell use and on agentic RL, and they need less of a custom interface. The mini docs say directly that the heavy ACI work of 2024 is "not needed" a year later [P]. Stateless execution also removes persistent-shell bugs such as hung prompts, lost working directories and leaked state.

**Caveats for us.**
1. The high score comes from frontier models. In 2024 the equivalent shell-only baseline scored 11%. Small local models sit somewhere between those two regimes (section 6).
2. bash-only gives the harness **no semantic view of actions**. Every action is an arbitrary shell string, so a permission policy has to parse shell (Codex's execpolicy does exactly this, section 3), or the sandbox has to carry the whole security load.
3. It is hard to make portable to Windows.

A good synthesis: keep a minimal core loop, and add a *small* set of typed tools (read, search, edit, run) where the typing gives security or reliability value.

### 1.4 Aider: edit formats, repo map, two attempts [P]

- **Edit formats** (https://aider.chat/docs/more/edit-formats.html): `whole`, `diff` (SEARCH/REPLACE), `diff-fenced` (for Gemini), `udiff`, and `editor-diff`/`editor-whole` for architect mode. Aider **picks the format per model**.
- **Unified diffs cut laziness about 3×** for GPT-4 Turbo. On the laziness benchmark the score went from 20% (SEARCH/REPLACE) to 61% (udiff) (https://aider.chat/docs/unified-diffs.html, Dec 2023).
- **Architect/Editor split** (2024-09-26): one model reasons, a second formats the edits. o1-preview with DeepSeek or o1-mini scored 85%. Sonnet 3.5 went from 77.4% to 80.5% and GPT-4o from 71.4% to 75.2% when paired.
- **Two-attempt protocol** (polyglot benchmark): if the first attempt fails, the model is shown the unit-test output and tries once more. The benchmark also reports "percent using correct edit format" as a separate metric, so format compliance is tracked on its own.
- **Repo map:** tree-sitter extracts symbols, the files are treated as a reference graph, and a personalized PageRank ranks them within a token budget (default `map_tokens=1024`). Source: https://aider.chat/2023/10/22/repomap.html. Note that tree-sitter grammars are C and are built with `cc`.

### 1.5 Edit-format evidence, across studies

| Study | Finding |
|---|---|
| Meta, *Agentic Program Repair from Test Failures at Scale*, arXiv 2507.18755, 2025-07-24 [P] | Llama-405B best solve rates: unified diff 30%, line diff 26%, **search-replace 53%**. Unified diff is "unnatural for LLMs". Adding static analysis and test-execution feedback to ReAct: 28.5% → 42.3%. |
| JetBrains, *Diff-XYZ*, arXiv 2510.12487, 2025-10 [P] | Search-replace is best for large models. Small open models show little difference between formats. Structured udiff variants come close. |
| Anthropic SWE-bench scaffold (Sonnet 3.5, 49% Verified), 2025-01-06 https://www.anthropic.com/engineering/swe-bench-sonnet [P] | `str_replace` with an **exact, unique** match. Zero or multiple matches return an error and a retry, which gave the "highest reliability". Absolute paths are required. They spent more effort on tool descriptions than on the prompt. |
| Codex CLI `apply_patch` (V4A format, `*** Begin Patch`) [P code; S format analysis] | A file-oriented envelope format that OpenAI models are trained on. It is sent as a "freeform" (grammar-constrained, non-JSON) tool. |
| *Output Format × Model Identity*, arXiv 2607.21674, 2026-07 [P, weak] | No single format was best across models (JSON Patch, udiff and full-file each won for a different model). Weak evidence: only 1 of 4 projects had any successes. |
| Multi-turn study, arXiv 2510.13859 [S snippet] | Whole-file output is more stable over multiple turns. |

**Synthesis.** Default to **search/replace with exact-unique matching**. Allow whole-file writes for new or small files. Make the format selectable per model, as Aider does. Always verify that an edit actually applied (1.7 and section 2).

A source-code taxonomy of 13 open agents (Rombaut, arXiv 2604.03515, 2026-04) [P, abstract] found:
- between 0 and 37 tools per agent;
- five loop primitives (ReAct, generate-test-repair, plan-execute, multi-attempt retry, tree search);
- 11 of the 13 agents combine several primitives;
- designs converge where there are external constraints and diverge on context management and state handling.

### 1.7 Design principles extracted

**Tools: few, typed, consolidated.**
- Anthropic's guidance (2025-09-11) [P]: consolidate tools (for example one `schedule_event`, not list plus create), use namespaced names, return semantic identifiers rather than UUIDs, offer a `response_format` of concise or detailed, and make truncation messages tell the agent what to do next.
- Tool definitions cost tokens and accuracy:
  - Anthropic reports 150k → 2k tokens (−98.7%) by exposing MCP tools as code that is discovered on demand, and says this needs a sandbox (2025-11-04) [P].
  - RAG-MCP: tool-selection accuracy went from 13.62% to 43.13% when only retrieved tools were shown (arXiv 2505.03275) [P, snippet].
  - "Less is More" (arXiv 2411.15399): fewer tools improves small or edge models' function calling [P, abstract].
  - MCP 2026-07-28 says servers SHOULD list tools in a deterministic order to improve prompt-cache hits [P].

**Context.**
- Context degrades as it grows: Chroma, 18 models, all got worse as input length grew (2025-07) [P, summary].
- Remedies: compaction or condensation, structured notes outside the context window (progress files, feature lists), subagents that return 1–2k-token summaries, and just-in-time retrieval (Anthropic 2025-09-29 [P]).
- SWE-agent's "last 5 observations" and OpenHands' condenser both show that history management pays off.

**Planning.**
- Aider's architect/editor split: +3 to 4 pp [P].
- Plan-then-execute is the most accurate *and* cheapest in some GAIA configurations [P].
- Plan/act mode separation (Cline, opencode, Claude Code plan mode) is a UX and safety gate as well as a performance technique. Plan-then-execute is also a prompt-injection defense (section 3).

**Verification loops.**
- External feedback is what matters. Huang et al. (arXiv 2310.01798, ICLR 2024) [P]: *intrinsic* self-correction does not help reasoning and sometimes hurts. Self-Debug (arXiv 2304.05128) [P] and Meta's static-analysis plus test feedback (+13.8 pp) [P] show that *execution* feedback does help.
- Aider's second attempt with test output [P].
- LangChain's largest gain came from a build-and-verify loop plus a deterministic "PreCompletionChecklist" middleware [P].

**Stop conditions.**
- An explicit sentinel, checked on exit code (mini) [P].
- Hard step, cost, wall-time and consecutive-format-error limits (mini) [P].
- Loop detection by counting edits per file (LangChain "doom loops") [P].
- Anthropic's long-running harness gives the agent a feature list with every item initially "failing", allows one feature per session, and requires explicit verification before an item is marked done. This counters agents that "declare the job done" (2025-11-26) [P].

**Cost and budget.**
- Per-run cost caps with typed exits (mini).
- Condensation gives linear rather than quadratic cost (OpenHands).
- The "reasoning sandwich" puts high reasoning effort on planning and verification and medium effort on implementation (LangChain).
- HAL found higher reasoning effort often *reduces* accuracy, so effort needs tuning rather than maximizing.

**Determinism and replay.**
- LLM inference is not deterministic even at temperature 0. Thinking Machines ran Qwen3-235B 1,000 times at T=0 and got 80 distinct completions, caused by batch-size-dependent kernels. Batch-invariant kernels fix this at about 2× cost (2025-09) [P, summary].
- So **replay must mean re-feeding recorded model outputs, not re-sampling the model**. Event sourcing (OpenHands), linear trajectories (mini) and rollout files (codex `rollout` crate) all follow this pattern.

## 2. Reliability failure modes and mechanisms

| Failure mode | Evidence | Mechanism that prevents it |
|---|---|---|
| **Crash on concurrent shared state** | opencode's single SQLite database: `SQLITE_BUSY` kills the prompt; corruption on NFS [S]. [local] Same crash in our GLM fleet. [local] A large DELETE ballooned the SQLite WAL file. | One state store per run, or an explicit single-writer actor. Never share a database file across processes by default. Retry on BUSY. Refuse network filesystems for the database. Keep an append-only JSONL event log per run (a crash then loses at most one line). |
| **Silent empty or truncated output** | Epoch: providers return "empty or truncated responses despite adequate token limits", advertise max_tokens they do not support, and rate-limit [P]. [local] About a third of GLM lanes died on rate limits, and completion had to be detected by an artifact (REPORT.md) rather than an END marker. | Treat an empty completion as an error, not as "done". Check `finish_reason` (length vs stop vs tool_calls). Retry with backoff and jitter, with a retry budget. Keep a fallback provider chain. Define completion as a **verified artifact plus exit status**, never as "the stream ended". SWE-agent's explicit "ran successfully, no output" message covers the tool-side version of the same problem. |
| **Malformed or no-op patches** | The git docs: "When running from a subdirectory in a repository, patched paths outside the directory are ignored" [P]. [local] `git apply` exited 0 and did nothing. Search/replace fails when the anchor text matches more than once [S]. | Apply edits in-process, not through the `git apply` CLI. Require **exact, unique** anchors, and return an error on zero or multiple matches (Anthropic str_replace [P]). After applying, **check that the file content changed and matches the intended result** (hash before and after; `git diff --stat` must be non-empty). Count edit-format failures (Aider's metric). Lint or parse the file after each edit (SWE-agent +3 pp). |
| **Prompt corruption through shell quoting** | [local] Backticks and `$` inside double-quoted `opencode run` prompts were command-substituted; zsh `interactive_comments` off meant `#` was passed as an argument. | Never build prompts or commands by string interpolation into a shell. Pass argv arrays (`Command::new().args()`), pass prompts through stdin or files, and use single-quoted heredocs only when a shell is unavoidable. Codex's execpolicy tokenizes commands with shlex before matching [P]. |
| **Stale context** | Context rot [P]. Agents act on files they read many turns earlier. | Record a content hash when a file is read. Refuse an edit whose anchor was read before the file's last modification ("file changed since read, re-read first"). Compaction keeps pointers (paths, hashes), not copies. |
| **Reward hacking, tests edited to pass** | ImpossibleBench (arXiv 2510.20270, 2025-10): GPT-5 exploited tests on **76%** of one-off impossible-SWE-bench tasks. Hiding the tests or making them read-only brought cheating "near zero" [P, summary]. METR (2025-06-05): frontier models modify tests and scoring code while knowing it is not what the user wants [P]. SWE-bench "future commits" leak through `git log --all` [S]. | Make test and gate files **read-only inside the sandbox** (Codex already re-binds `.git` and `.codex` read-only [P]; extend this to tests and gate definitions). Run the verdict **outside** the agent's sandbox. Diff-audit changes to test files and fail closed if they changed. Strip future history and remote refs from the workspace. |
| **Success claimed without evidence** | MAST (arXiv 2503.13657): verification and termination failures are 21.3% of multi-agent failures, including premature termination 6.2%, no or incomplete verification 8.2%, and incorrect verification 9.1% [P, snippet]. Anthropic's long-running harness post [P]. [local] The team's "two pairs of eyes" rule and "gates must check content, not presence" (27 fail-open bypasses found). | The harness, not the model, decides "done". It needs: (a) a gate command whose **exit code and output content** are checked; (b) an evidence bundle (commands run, exit codes, diffs, test logs) attached to every completion claim; (c) optional independent reviewer agent in a fresh context. |
| **Doom loops and runaway cost** | LangChain loop-detection middleware [P]. HAL cost analysis [P]. | Step, cost and time budgets with typed exits (mini). Per-file edit counters. Detect repeated identical actions. |
| **Orphaned processes and hangs** | mini kills the whole process group on timeout [P]; it disables pagers and progress bars [P]. [local] `pkill -f` matched its own shell over ssh. | Per-action timeout. Kill the process group (a Job Object on Windows). Non-interactive environment defaults. Close stdin. |
| **Harness regressions between releases** | 35-release Qwen Code study [P]. | Pin the evaluation set, run it on every harness change, and record the harness version and configuration hash in every trajectory. |

## 3. Security and confinement

### 3.1 What the leading harnesses actually do

**Claude Code** (Anthropic engineering, 2025-10-20, https://www.anthropic.com/engineering/claude-code-sandboxing) [P]
- Filesystem isolation (writes limited to the working directory) **and** network isolation, both enforced by the OS: Seatbelt (`sandbox-exec`) on macOS, bubblewrap on Linux.
- Network traffic goes over a unix socket to a **proxy outside the sandbox**, which enforces a domain allowlist.
- The post explains why both layers are needed: without network isolation a compromised agent can exfiltrate SSH keys, and without filesystem isolation it can escape.
- Sandboxing "safely reduces permission prompts by 84%".
- The runtime is open-sourced as `sandbox-runtime` (anthropic-experimental, "research preview"). Its README also describes Windows support using a WFP connect filter on a dedicated account [S].

**Codex CLI** [P, codex-rs source READMEs]
- **Linux:** bubblewrap is now the default filesystem sandbox, and "the legacy Landlock option is rejected ... because it cannot isolate app-server Unix sockets". Details:
  - `--ro-bind / /` with writable roots layered on top;
  - protected subpaths (`.git`, the resolved `gitdir:`, `.codex`) re-applied read-only;
  - `PR_SET_NO_NEW_PRIVS` plus a seccomp network filter;
  - WSL1 is unsupported and rejected;
  - if system `bwrap` is missing it falls back to a bundled copy and warns.
- **macOS:** Seatbelt.
- **Windows:** `windows-sandbox-rs`.
  - "Elevated" mode uses dedicated low-privilege users, ACLs and firewall rules.
  - "Unelevated" mode uses write-restricted tokens with synthetic SIDs plus ACLs, and only environment-variable network disabling.
  - OpenAI says AppContainer, Windows Sandbox and integrity labels each "covered only part of the job" (OpenAI blog, *Building a safe, effective sandbox to enable Codex on Windows*, c. 2026-05 [S summary]).
- **`execpolicy`:** Starlark `prefix_rule(pattern, decision=allow|prompt|forbidden, justification, match=[…], not_match=[…])`. The `match` and `not_match` examples are **checked as unit tests when the policy loads**. `host_executable()` pins which absolute paths a basename like `git` may resolve to.
- **`network-proxy`:** an HTTP and SOCKS5 proxy with an allow/deny list and a "limited" read-only mode that uses TLS interception. The global `*` wildcard is rejected. Local and private IPs are blocked unless explicitly allowed, including hostnames that *resolve* to private IPs. With no allow entries, **everything is blocked (fail-closed)**.
- **`process-hardening`:** disables core dumps, blocks ptrace attach, and strips `LD_PRELOAD` and `DYLD_*` before `main`.
- **`shell-escalation`:** a patched zsh intercepts `execve` and asks a server whether to Run (inside the sandbox), Escalate (outside, with approval) or Deny.
- **Modes:** `sandbox_mode` (read-only, workspace-write, danger-full-access) is kept separate from `approval_policy` (untrusted, on-request, never). Network is off by default in workspace-write [S].

**OpenHands** [P/S]
- A Docker runtime per session, with the sandbox UID matched to the host user.
- An LLM security analyzer rates each action's risk, and a `ConfirmationPolicy` pauses on HIGH.
- The SDK abstracts local, Docker and remote workspaces.

**Goose** [S]
- Permission modes; the default is Autonomous.
- Strips zero-width Unicode on load and detects prompt injection after the red-team exercise.
- No OS sandbox by default [UNVERIFIED].

### 3.2 Confinement primitives, by OS

| OS | Primitive | Notes for a Rust harness |

### 3.3 Prompt injection: defenses that work

- **Threat model:** Willison's "lethal trifecta" (2025-06-16) [P]: access to private data, exposure to untrusted content, and a way to communicate externally. Any agent with all three can be made to exfiltrate data. The only robust defense is **never combining all three in one context**. the personal-data app, rustyvault and the messaging app hold private data, which makes this the central risk for our suite.
- **Architectural patterns** (Beurer-Kellner et al., *Design Patterns for Securing LLM Agents against Prompt Injections*, arXiv 2506.08837, 2025-06) [P, summary]: action-selector, plan-then-execute, LLM map-reduce, dual LLM, code-then-execute, context minimization.
- **CaMeL** (Debenedetti et al., arXiv 2503.18813, 2025-03): a privileged LLM writes a program from the trusted query; a quarantined LLM parses untrusted data but has no tool access; data provenance is tracked with capabilities and checked by policy at each tool call. It solves **77% of AgentDojo tasks with provable security, against 84% undefended** [P, snippet].
- **AgentDojo** (arXiv 2406.13352) [P, snippet]: prompt-level defenses (sandwiching, delimiters) leave the attack success rate high (about 31%). Tool filtering drops it to about 7.5% but costs utility.
- **Real incidents that show "config-file writes = RCE":**
  - CVE-2025-53773 (Copilot, 2025-08): an injected prompt got Copilot to write `"chat.tools.autoApprove": true` into `.vscode/settings.json`.
  - CVE-2025-54135 "CurXecute" (Cursor, 2025-08): Cursor auto-started a newly written `.cursor/mcp.json` server *before* the user approved the edit [P/S].
  - **Rule: the agent must never be able to write its own harness configuration, permission policy, MCP server list, hooks, or gate definitions.** Codex's read-only `.codex` rebind implements this.
- **Invisible-Unicode injections** (Goose red team) → normalize and strip zero-width and bidi control characters from all untrusted inputs, including tool descriptions.
- **OWASP Top 10 for Agentic Applications 2026** (2025-12-09) [S]: ASI01 Goal Hijack, ASI02 Tool Misuse, ASI03 Identity & Privilege Abuse, ASI04 Supply Chain, ASI05 Unexpected Code Execution, ASI06 Memory/Context Poisoning, ASI07 Insecure Inter-Agent Comms, ASI08 Cascading Failures, ASI09 [probably Human-Agent Trust Exploitation, UNVERIFIED], ASI10 Rogue Agents. Useful as a checklist for our threat model.

### 3.4 Approvals and secrets

- **Approval gates.** Deny → ask → allow ordering with first match wins, and deny cannot be overridden (Claude Code) [S]. Separating the sandbox level from the approval policy (Codex) lets you run "read-only plus never ask" safely. Sandboxing is what makes fewer prompts safe (−84%), which matters for **non-expert usability**, because prompt fatigue leads people to approve everything.
- **Secrets.**
  - Never put secrets in the model's context or the child process's environment by default. Use an environment allowlist and strip everything else (Codex process-hardening strips loader variables [P]).
  - Resolve secrets at the tool boundary, inside the harness process, from rustyvault. The model sees only a handle.
  - Anthropic's code-execution post notes that PII can be tokenized before it reaches the model [P].
  - Keep API keys for hosted models in the OS keychain or rustyvault, never in config files that the agent can read.

## 4. Tool and plugin protocols, and modularity

### 4.1 MCP (Model Context Protocol)

- **Governance.** Donated to the **Agentic AI Foundation (Linux Foundation)** on 2025-12-09, together with goose and AGENTS.md. Platinum members include AWS, Anthropic, Block, Google, Microsoft and OpenAI [P].
- **Current spec: 2026-07-28** [P, changelog]:
  - **Stateless.** No `initialize` handshake. Every request carries its protocol version and client capabilities in `_meta`. A new `server/discover` RPC. No `Mcp-Session-Id`; cross-call state uses explicit server-minted handles.
  - **Multi Round-Trip Requests** replace server-initiated requests: the server returns `input_required`, and the client retries with the answers.
  - **Tasks** moved into an official extension. There is a formal **extensions** framework, negotiated through capabilities.
  - **Deprecated:** Roots, Sampling, Logging, the HTTP+SSE transport, and OAuth dynamic client registration (replaced by Client ID Metadata Documents). There is now a formal **12-month minimum deprecation window**.
  - `CacheableResult` with `ttlMs`/`cacheScope`. Deterministic tool ordering (SHOULD). JSON Schema 2020-12 for input and output schemas. OpenTelemetry trace propagation through `_meta`.
- **The spec's own security stance** [P]: "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server"; "Hosts must obtain explicit user consent before invoking any tool"; "MCP itself cannot enforce these security principles at the protocol level."
- **Strengths:** a universal ecosystem (every major client uses it), an official Tier-1 Rust SDK, stdio transport for local servers, JSON Schema tools, and the capability and extension negotiation we need.
- **Security criticisms** [P/S]:
  - **Tool poisoning:** hidden instructions in tool descriptions (Invariant Labs, April 2025).
  - **Rug pull:** a description changes after approval, and MCP has no re-verification.
  - **Tool shadowing:** a malicious server's description redirects calls meant for another server's tools.
  - **Confused deputy:** a server acts with the user's credentials for another principal (addressed by the auth hardening in 2025-06 and 2026-07).
  - A large-scale analysis of MCP ecosystem attacks: arXiv 2509.06572.
  - Mitigations in the literature: ETDI, signed tool definitions plus policy (arXiv 2506.01333); mcp-scan.

### 4.2 Other protocols

- **OpenAI function calling:** the de-facto wire format for OpenAI-compatible servers (llama.cpp, Ollama, vLLM). JSON Schema parameters. `tool_choice: auto/required`. "Freeform"/CFG tools (Codex apply_patch) are an OpenAI-specific extension. For our purposes this is the **model-side** protocol that the harness speaks to providers. It is not a plugin protocol.
- **A2A (Agent2Agent):** Google, now at the Linux Foundation. v1.0 on 2026-03-12 with **JWS-signed Agent Cards** at `/.well-known/agent-card.json`. v1.0.1 (2026-05) added extensions. SDKs exist for Python, JS, Java, Go and .NET, **not Rust** [S]. It is for agent-to-agent delegation across organizations. **Not needed for v1.** It could matter later if suite agents on different mesh nodes delegate to each other, and signed cards are a design idea worth borrowing for manifests.
- **ACP (Agent Client Protocol, Zed, 2025-08):** JSON-RPC over stdio between an editor or front end and an agent. It covers sessions, streamed turns, **permission requests**, and client-provided filesystem and terminal. About 50 agents support it, including Claude Code, Codex, Goose and Gemini CLI [S]. Rust crate `agent-client-protocol` 2.2.0, Apache-2.0, no C [P, cargo probe]. **Relevant:** this is the "front" side of a harness, so rustyfin's UI, the personal-data app's UI or an editor could all drive rustyharness through one protocol.
- **Codex App Server:** OpenAI's own front-end protocol (JSON-RPC; thread, turn and item primitives; server-initiated approval requests that pause the turn). This is evidence that serious harnesses split things into a **front-end protocol** (for UIs) and a **tool protocol** (MCP).

### 4.3 How harnesses let third parties add capability

- **MCP servers** are the universal mechanism (Goose extensions, Claude Code, Codex, OpenHands).
- **Skills and instruction files:** AGENTS.md (now AAIF), Claude skills, "Skills over MCP" (an MCP working group).
- **Hooks and middleware:** Claude Code PreToolUse and PostToolUse; LangChain middleware; Codex `hooks`.
- **Versioning:**
  - MCP protocol version per request plus a formal deprecation policy.
  - rmcp commits to SemVer 2.0 with Rust-specific breaking-change rules (VERSIONING.md, cited in the Tier-1 promotion) [S].
  - The suite should be at least that strict.

### 4.4 Recommendation: MCP on the wire, suite manifest for trust

Short version: **be MCP-native for tools, ACP- or App-Server-style for front ends, and add a signed suite capability manifest as the trust root.** Do not create a suite-native wire protocol. A new protocol would cost the ecosystem and the Tier-1 SDK and would buy no security, because the weaknesses are in *trust and policy*, not in the wire format.

Proposed model (a design sketch, not evidence):

1. **Each rusty app ships `capabilities.toml`**, versioned and **signed by the suite release key**. rustyvault holds the key; the harness verifies the signature. It declares:
   - the app id, the manifest schema version, the app SemVer, and the MCP protocol versions supported;
   - for each tool: name (namespaced `rustyfin.library_search`), a JSON Schema 2020-12 for input and output, and a **hash of the description text**;
   - an **effect class** per tool: `read` / `write-local` / `destructive` / `network-egress` / `external-comms` / `secrets-use`;
   - **data labels**: `private-data` / `untrusted-content` / `exfil-channel`, which let the harness compute the lethal trifecta *before* a session starts;
   - required sandbox grants (filesystem paths, hosts, secrets by handle), default approval policy, and minimum harness version.
2. **The harness enforces the manifest and ignores self-description.** At connect time it compares `tools/list` against the manifest (names, schemas, description hashes). Any drift means the tool is quarantined and the user must re-approve, which is the **rug-pull defense**. Unlisted tools are dropped. Name collisions across servers are rejected, which is the **shadowing defense**.
3. **Adapters behind one internal trait.** A single `ToolProvider` / `Capability` trait inside the harness has three implementations:
   - (a) an in-process Rust adapter (a feature-gated crate, for zero IPC in trusted suite code);
   - (b) an MCP stdio adapter using rmcp, for suite apps and third parties;
   - (c) an MCP Streamable-HTTP adapter for remote servers, off by default.

   Future apps add a manifest and an MCP server. The harness core does not change.
4. **Third-party (non-suite) MCP servers** work in an "unsigned" tier: always sandboxed, always ask-before-use, no private-data labels allowed, and no combination with suite private-data tools in the same session. That combination would complete the lethal trifecta.
5. **Front end:** expose the harness to apps (rustyfin assistant, the personal-data app diary search, suitectl) through ACP, or a thin JSON-RPC modelled on ACP / Codex App Server, so that each app is only a UI.
6. **Put suite-specific metadata in MCP's sanctioned places** (`_meta` keys under a reverse-DNS prefix such as `dev.rustysuite/…`, or a declared MCP extension), so that suite servers remain valid MCP servers that any MCP client can use.

**The C tax in the LLM HTTP clients is really TLS.**
- rustls ≥0.23 defaults to `aws-lc-rs`, which needs a C toolchain and CMake, and NASM on Windows [P, rustls docs].
- `ring` also contains C and assembly.
- `rustls-rustcrypto` is pure Rust but "experimental".
- **Local-first observation:** talking to `127.0.0.1` llama.cpp, Ollama or vLLM needs **no TLS at all**. A plain-HTTP localhost client built on hyper, or a minimal HTTP/1.1 client, is pure Rust. TLS, and its C, is only needed for hosted providers or remote MCP.

  This matches the suite's existing C-tax lens (MEMORY: candle over ort). It suggests putting hosted-provider support behind a cargo feature, and **writing our own thin OpenAI-compatible chat and tool-call client**, about 1–2k lines: request and response types, SSE streaming, `finish_reason` handling, and tool-call parsing, including the text-protocol fallback. That is small, it is the part we most need to control (section 2's empty-output and retry rules), and it avoids pre-1.0 churn.

**Summary:** reuse rmcp, agent-client-protocol, landlock, seccompiler, and possibly sandlock-core. Write the agent loop, the provider client, the policy engine (port execpolicy's design), and the manifest verifier ourselves.

## 6. Local-model realities

- **Serving-layer fragility** (llama.cpp docs, `docs/function-calling.md`) [P]:
  - `llama-server` needs `--jinja` for OpenAI-style tool calls.
  - Native handlers exist for Llama 3.x, Qwen 2.5 and 2.5-Coder, Hermes 2/3, Mistral Nemo, Functionary, Firefunction, Command R7B and DeepSeek R1. Other models fall back to a generic handler that "may consume more tokens and be less efficient".
  - Parallel tool calls are off by default.
  - "Beware of extreme KV quantizations (e.g. `-ctk q4_0`), they can substantially degrade the model's tool calling performance."
- **Model-specific formats break.** llama.cpp issue #26530 (2026-08-03) [P]: Qwen3-Coder-family GGUFs **stop emitting XML tool calls with 20+ tools or 10K+-token prompts** and answer in plain text instead. The lazy grammar is generated but never triggered. It works with `tool_choice: "required"`. An older parser bug that accidentally fell back to a JSON grammar was *more* reliable. The issue was closed as "not planned".
- **Small models are fine for short, structured tool use and weak at long horizons.** AgentFloor (arXiv 2605.00334, 2026-05-01) [P]: 16 open models from 0.27B to 32B plus GPT-5, 16,542 runs. Small and mid-size open models are "already sufficient" for short-horizon structured tool use, and the best open model matched GPT-5 there. The gap appears on long-horizon planning with persistent constraints. The authors recommend routing: small models for routine actions, frontier models for planning.
- **Coding-specific open models.**
  - Qwen3-Coder-30B-A3B-Instruct: Apache-2.0, 30.5B total / 3.3B active, 256K context, non-thinking only, with its own function-call format [P, model card].
  - Its SWE-bench Verified score of about 50% is reported by third parties [S, UNVERIFIED; the harness used is not stated].
  - Qwen3-Coder-Next: 80B total / 3B active (arXiv 2603.00729, 2026-02) [P].
  - Devstral Small (24B, Apache-2.0), built with All Hands for OpenHands [S].
- **Benchmarks for tool-calling quality.** BFCL v4 (2026-04) weights agentic 40% and multi-turn 30%. Epoch's review found defects in 48% of a 50-task sample, so treat it with caution [S].
- **Grammar-constrained decoding.**
  - llama.cpp supports GBNF grammars and JSON-Schema→grammar conversion through `response_format`/`json_schema` [UNVERIFIED from memory, but standard]. Ollama offers `format` with a JSON schema; vLLM offers guided decoding (xgrammar/outlines).
  - JSONSchemaBench (arXiv 2501.10868) [P, abstract]: constrained decoding can speed up generation about 50%, but schema-feature coverage differs a lot between engines (llama.cpp, Guidance, Outlines, XGrammar, OpenAI, Gemini). Keep action schemas **simple**: no exotic keywords, shallow nesting.
  - "Let Me Speak Freely?" (arXiv 2408.02442) [P, summary]: strict format constraints **degrade reasoning**. A two-step approach (reason in natural language, then format) recovers most of the loss.

**What this means for harness design.**
1. **Two protocol backends from day one.**
   - (a) Native tool calls, when the server and model pair is known to be good.
   - (b) A **text protocol**: a fenced, tagged action block (like mini's `mswea_bash_command`, or a small XML or JSON block), parsed by the harness, with **grammar-constrained decoding applied only to the action block**. Use llama.cpp lazy grammars triggered by the opening tag, so reasoning stays free text.

   Pick the backend per model profile, and let an eval result switch it automatically.
2. **Keep the active tool list small for local models** (about 5–8), and load the rest via retrieval (RAG-MCP) or by listing tools on demand.
3. **Model profiles** as data: context size, tool-call format, whether `tool_choice: required` works, preferred edit format, safe KV quantization, max tools. Validate each profile with a smoke eval before use; rustybenchmark can produce these.
4. **Format-error budget:** after N consecutive malformed actions (mini uses 3), stop with a typed error rather than looping.
5. **Route long-horizon planning** to a stronger model when policy allows (an architect/editor split, as in AgentFloor and Aider). Under a local-only privacy policy, split tasks into short, verifiable steps instead.
6. **Detect server misconfiguration at startup:** check that `--jinja` is on, the template is recognized, and the KV cache type is acceptable. Fail closed, with a plain-language fix, for non-expert users.

## 7. Naming: "rustyharness" vs "rustyAI"

**How the industry uses the words (2025–26):**
- **"Harness"** has become the precise term for the runtime around a model: context assembly, tool invocation, sandbox and approval enforcement, streaming, and carrying work across turns. Examples:
  - OpenAI talks about the "Codex harness" and "harness engineering" and defines the harness in exactly those terms (*Codex as a platform*, 2026-08-19 [P]; App Server post, 2026-02 [S]).
  - Anthropic uses "harness" for long-running agent support (2025-11-26 [P]).
  - LangChain distinguishes framework (LangChain), runtime (LangGraph) and **harness** (Deep Agents, "batteries-included") [P, snippet].
  - Academic titles now use it routinely ("Stop Comparing LLM Agents Without Disclosing the Harness", "Don't Blame the LLM: How Agent Harness Evolution…").
  - It is **model-agnostic by definition**: the whole literature is about swapping models under a fixed harness.
- **"Agent"** is the harness plus a model plus a task: what users interact with. It is overloaded, since "agent" is also used for a single subagent or a whole product.
- **"AI"**: to non-expert end users, "AI" means *the intelligence itself*, meaning the model or chatbot. "rustyAI" implies that the suite ships or *is* a model, which over-promises (we ship a runtime, and the model is pluggable) and is too vague for developers. It is also a crowded, low-distinctiveness name.
- **Collision notes.**
  - In classic software, a "test harness" is what *drives* code under test. This fits our "dev/test engine" story, but could be confused with suitectl's test role.
  - "Harness" is also a CI/CD company's brand. The compound "rustyharness" is distinct, but this is not legal advice.

**Recommendation.** Name the repo, crate and CLI **rustyharness**, because it describes a model-agnostic, security-enforcing runtime accurately. If a user-facing name is needed inside rustyfin or the personal-data app, give the *assistant feature* a friendly product name ("Rusty Assistant" or similar) that is backed by rustyharness. Do not name the runtime after "AI". This matches how OpenAI separates "Codex" (product) from "the Codex harness" (runtime).

## 8. Ranked design principles for rustyharness

1. **The harness decides "done", not the model.** Completion means a gate command's exit code *and checked output content* plus an evidence bundle (commands, exit codes, diffs, logs). Evidence: MAST's 21% verification and termination failures; LangChain's PreCompletionChecklist (+13.7 pp together with verify loops); Anthropic's "declare the job done" problem; [local] gates-check-content.
2. **Kernel-enforced confinement by default, fail closed on every OS.** Filesystem *and* network isolation, with network through an allowlist proxy that has no allow entries until the user adds some. If the sandbox cannot start (for example WSL1 or no user namespaces), refuse to run rather than run unconfined. Evidence: Claude Code (both layers are needed; −84% prompts); Codex bwrap/seccomp/Seatbelt/restricted tokens; Codex rejects WSL1.
3. **The agent cannot modify its own trust base.** Harness config, policies, manifests, MCP server lists, hooks, gate definitions, tests-under-evaluation and `.git` are read-only inside the sandbox. Evidence: CVE-2025-53773, CVE-2025-54135; ImpossibleBench (76% cheating, near zero once tests were read-only or hidden); Codex's `.git`/`.codex` read-only rebind.
4. **Avoid the lethal trifecta by construction.** Every capability carries data labels (private, untrusted, exfil). The harness refuses sessions that combine all three unless a plan-then-execute or dual-LLM (CaMeL-style) path is used. Evidence: Willison 2025-06; the design-patterns paper; CaMeL 77% vs 84%; AgentDojo showing that prompt-level defenses fail.
5. **MCP on the wire, signed suite manifest as the trust root.** Pin tool description hashes, namespace tools, reject shadowing, re-approve on drift. Evidence: MCP spec (annotations untrusted; cannot enforce security); Invariant tool-poisoning, rug-pull and shadowing attacks; rmcp Tier 1 with no C.
6. **Small, typed, consolidated tool surface on top of a minimal loop.** Keep a mini-style linear loop, and add only tools whose typing buys security or reliability: read with hash, search with bounded hits, a search/replace edit, and a run with timeout. Evidence: mini-swe-agent at 74%+; SWE-agent ACI +7 pp; Anthropic tool guidance; RAG-MCP; Less-is-More.
7. **Edits: exact-unique search/replace, per-model format, verified application.** Return an error on zero or multiple matches, lint or parse after the edit, and hash before and after to prove the change landed. Never use the `git apply` CLI for agent edits. Evidence: Meta 53% vs 30%; Diff-XYZ; Anthropic str_replace; SWE-agent lint +3 pp; git docs on the subdirectory no-op; [local].
8. **Execution feedback loops, not self-reflection.** Run build, test and lint and feed the results back, with a bounded number of retries (Aider-style two attempts as the default). Evidence: Huang et al. (intrinsic self-correction fails); Self-Debug; Meta +13.8 pp from static analysis plus tests; Aider polyglot.
9. **Stateless, argv-based execution with process-group kill.** No persistent shell. No string-built shell commands or prompts (use argv and stdin). Kill the process tree on timeout (a Job Object on Windows). Non-interactive environment. Evidence: mini ("big deal for stability"); [local] shell-quoting and pkill self-match incidents.
10. **Hard budgets with typed exits.** Steps, cost, wall time, consecutive format errors and per-file edit loops; every exit has a machine-readable status. Evidence: mini `AgentConfig`; LangChain loop detection; HAL cost findings.
11. **Two model-protocol backends, chosen from a model profile: native tool calls and a grammar-constrained text protocol.** Constrain only the action block and let the model reason freely. Evidence: llama.cpp `--jinja` and KV-quantization warnings; Qwen3-Coder #26530; "Let Me Speak Freely"; mini works with any model; AgentFloor.
12. **Empty, truncated or ambiguous output is an error, never a success.** Check `finish_reason`. Retry with backoff under a budget, then fall back to another provider. Tools always return an explicit status even when they print nothing. Evidence: Epoch (empty or truncated responses, rate limits); SWE-agent's "ran successfully, no output"; [local] REPORT.md-based lane detection.
13. **One writer per state store; an append-only per-run event log; replay from recorded outputs.** Never share a database file across concurrent runs. Record the harness version and configuration hash in every trajectory. Evidence: opencode SQLite `BUSY` and NFS corruption; [local]; OpenHands event sourcing; Thinking Machines (T=0 is still non-deterministic).
14. **Context is a budget.** Bounded observations, collapsed old outputs, compaction with pointers (paths and hashes) rather than copies, stale-read detection, and subagents returning 1–2k-token summaries. Evidence: SWE-agent (100-line window, last-5 history); Chroma context rot; OpenHands condenser (≤2× cost, linear growth); Anthropic context engineering.
15. **Evaluate the harness as a product.** A pinned evaluation suite runs on every harness change (rustybenchmark), with results reported per model and harness pair. Evidence: Epoch 11–15 pp scaffold variance; GAIA 28 pp; the 35-release regression study; "Stop comparing agents without disclosing the harness".
16. **Safe defaults for non-experts.** The sandbox removes most prompts. The prompts that remain are plain-language and effect-classed ("will send data to X"). Start in plan (read-only) mode with checkpoints (shadow git) so every act step can be undone. Evidence: −84% prompts; Cline and opencode plan/act split; Cline checkpoints; Goose defaulting to Autonomous is the counter-example to avoid.
17. **Secrets never enter model context or the child environment.** Pass handles resolved by rustyvault at the tool boundary, use an environment allowlist, and apply process hardening. Evidence: Codex process-hardening; Anthropic's PII-tokenization note; OWASP ASI03.

## 9. Open questions (for the owner)

1. **Is hosted-model support in v1 at all?** If it is local-only, the harness can skip TLS and have almost no C. If it is hosted, accept the rustls C tax (aws-lc-rs or ring), or evaluate the experimental pure-Rust `rustls-rustcrypto`.
2. **Linux sandbox backend:** require a bundled `bwrap` (C, proven, Codex's choice), or go pure Rust with Landlock, seccomp and user-notify (sandlock-core: newer, unprivileged, less proven)? What about hosts without unprivileged user namespaces?
3. **The macOS Seatbelt profile language is undocumented and deprecated.** Do we accept that risk, as Claude Code and Codex do, or also support an Apple Containerization VM mode for high-risk tasks?
4. **Windows depth for v1:** port Codex's unelevated restricted-token design, or require an elevated one-time setup (dedicated user, firewall rules)? Either way, is Windows v1 or v2?
5. **Manifest signing:** does rustyvault hold the suite signing key, and what is the approval path for third-party (unsigned) MCP servers?
6. **The trifecta policy for the assistant layer:** the personal-data app and the messaging app hold private data. Is a CaMeL-style dual-LLM path required for any session that reads untrusted web or chat content, or do we simply forbid mixing those capabilities per session?
7. **Front-end protocol:** adopt ACP (multi-vendor, Rust crate exists), copy the Codex App Server shape, or make ACP plus our own extensions the front API for rustyfin, the personal-data app and suitectl?
8. **Default edit format per local model:** should rustybenchmark generate the model profiles (tool-call format, edit format, max tools, safe KV quantization) automatically?
9. **Routing:** may a local-only privacy policy ever escalate planning to a hosted model, and with what data-minimization rules?
10. **Review:** should the independent-reviewer requirement (owner rule: "two pairs of eyes") be built into the harness as a completion gate, meaning a fresh-context reviewer agent with read-only tools?
11. **How far to go with determinism:** is trajectory-replay determinism (recorded outputs) enough, or do we also want batch-invariant local inference for reproducible evaluations (about 2× cost)?
12. **Naming:** confirm rustyharness for the runtime and decide the end-user assistant's product name.
