# P-35 — the `acp` verb: Agent Client Protocol v1 over stdio

New crate `harness-acp` (pure-library bridge, stdio only) and the
`rustyharness acp` verb: a baseline ACP v1 agent speaking
newline-delimited JSON-RPC 2.0 on stdin/stdout. The pinned wire spec,
message shapes and mappings are in `docs/slices/P-35-acp-spec-notes.md`
(ACP v1, `protocolVersion` integer 1, fetched 2026-10-03). No new
third-party dependencies: the wire is built and parsed as
`serde_json::Value`s by hand.

## What was built

- `crates/harness-acp`: `serve(ServeParams, reader, writer)` — one
  reader thread parses the client's lines into a shared inbox; the
  caller's thread runs the JSON-RPC dispatch and, inside an ACP
  session, exactly one `harness_run::run_session` whose three seams are
  the bridges:
  - `AcpInput` (`UserInput`): prompts arrive as `session/prompt`
    requests; a prompt's response (`stopReason`) is written at the
    turn boundary after its turn (or by the server when the session
    stops at a session-level cause, or by the input immediately for a
    queued prompt the client cancelled before it started).
  - `AcpSink` (`EventSink`): `ModelReplied` → `agent_message_chunk`
    (text before `<action>`, blob-resolved, sanitized, bounded 8 KiB);
    `ToolStarted` → `tool_call` (`toolCallId` `c<seq>`, kind derived
    from the capability); `ToolFinished` → `tool_call_update`
    (`completed`/`failed`, text preview of the output). Every other
    record is left to the notes — the protocol has no shape for it.
  - `AcpApprover` (`Approver`, kind `embedded`): an ask becomes a
    `tool_call` (`ask-<n>`, pending) plus a `session/request_permission`
    request (`allow-once`/`reject-once`; `allow-always`/`reject-always`
    offered only when the run allows session grants, P-23). Mappings:
    `allow-once`→`Yes`, `allow-always`→`AllowSession`,
    `reject-once`→`No`, `reject-always`→`DenySession`, and a
    `cancelled` outcome, an error response, or silence at the deadline
    → `No` (§5.3: never an auto-approve). The ask's tool call is
    updated `completed`/`failed` with the answer.
  - `session/cancel` (notification): fail-closed semantics (below).
- Error codes: `-32700` (not JSON, id `null`), `-32600` (bad
  envelope), `-32601` (unknown method / not-advertised capability /
  re-`initialize`), `-32602` (bad params: missing/relative `cwd`,
  non-empty `mcpServers`, unsupported content block, empty-or-oversize
  prompt text), and the server range `-32000` (busy: a second
  `session/new` or a run that refused to start), `-32001` (unknown
  session), `-32002` (not initialized).
- `rustyharness acp` (harness-cli): reads its inputs exactly as `chat`
  (task, policy, profile, presets, locality-checked state root,
  config-file defaults, run-bundle fill), builds the backend from
  `--endpoint` (or takes a library-given one), then serves stdio.
  Options are `chat`'s minus everything that names or reshapes a
  workspace — there is no `--workspace` and no `--workspace-mode`:
  each ACP session's workspace is its own `session/new` `cwd` (the
  spec's own rule). `SessionConfig` is the P-05 defaults with the
  task's session-grants flag applied (the task file's budget section is
  not applied to sessions, as in `chat`).

## Decisions and fail-closed readings

- **At most one ACP session at a time**; a second `session/new` is
  refused `-32000`. The loop is synchronous: one `run_session` runs on
  the serving thread, so concurrent sessions could not be answered in
  time. After a session ends (its stdin idle-timeout, its client's
  EOF, or a refusal), a new `session/new` is accepted on the same
  connection.
- **Cancellation** (the hard one): the loop has no mid-turn cancel
  input (P-05 O-7) and the journal's record kinds are closed (P-10), so
  a cancel never interrupts a running turn. A `session/cancel` marks
  the pending prompt response `cancelled`; a queued prompt that has
  not started is answered `cancelled` and not run; a cancel while
  nothing is pending is ignored. The turn itself ends naturally within
  its own budgets, the journal is unaffected, and the session still
  audits clean. A cancel during an ask is the client answering the
  pending `session/request_permission` with `outcome: cancelled` —
  that denies the call (journaled `ApprovalDenied`).
- **stopReason mapping**: turn reasons `answered`/`submitted`/
  `submitted_checks_failed` → `end_turn`; `turn_steps`/`format_errors`/
  `loop:*` → `max_turn_requests`; `input_refused` → `refusal`; session
  stops `budget`/`context_exhausted` → `max_tokens`;
  `model_unavailable`/`policy_abort`/`sandbox_lost`/
  `journal_unavailable` and anything unknown → `refusal`; a seen
  cancel → `cancelled` (overrides the turn's own reason).
- **No capabilities advertised**: no `loadSession`, no MCP, no
  `session/resume`/`close`/`delete`; those methods are refused
  `-32601`. `resource_link` content blocks are baseline, so a prompt
  may carry them (one bracketed line each in the turn's message);
  `image`/`audio`/`resource` blocks are refused `-32602`.
- **Untrusted text never raw**: reply text, tool arguments and tool
  output are resolved out of the journal's blobs (`inline` unescape /
  blob read) and pushed through `harness_core::display`'s sanitizer,
  bounded, before they go on the wire; unresolvable payloads become
  less text, never raw bytes.
- **The gate report goes to stderr** (`emit_err` in `cmd_acp`): stdout
  belongs to the protocol for the whole life of the stream, so the
  gate-child "last stdout line is the GateReport" contract cannot hold.
  This is a deliberate deviation, flagged as a **design question for
  the manager** (options seen: a `--report-file`, or keeping stdout
  clean until after EOF and writing the report then; this build chose
  stderr, which is never parsed by the ACP client). The exit code is
  the usual outcome mapping; a run that refused to start maps
  Confinement→3, Presubmit→4, else 5, as in `chat`.

## Verification

- `cargo test -p harness-acp`: the seven required tests
  (`acp_initialize_handshake`, `acp_prompt_streams_updates`,
  `acp_permission_request_roundtrip_yes_no`,
  `acp_cancel_ends_turn`, `acp_session_journal_audits_clean`,
  `acp_rejects_malformed_json_rpc`, `acp_never_binds_a_socket`) run the
  real server over injected pipes (no sockets) against the real
  session loop and the real audit replay (`assert_session_audit_clean`).
- `cargo fmt --all`, `cargo clippy --locked --workspace --all-targets
  -- -D warnings`, `cargo test --locked -p harness-acp -p harness-cli`
  (harness-core was not touched, so no workspace-wide test run).
- `scripts/ci/gates.sh` was NOT run (cargo-deny needs the network).

## Open questions for the manager

1. The stderr GateReport (above) — is a report file the better
   contract for protocol-serving verbs?
2. Cancellation granularity: a real mid-turn cancel needs a journaled
   input kind (a `cancelled` `InputEnd` variant or similar), which
   P-10 closed. If the journal reopens its kind set, the ACP cancel can
   stop the loop at the next step instead of at the turn's natural end.
3. `session/new` refusing a second session (`-32000`) is the simplest
   fail-closed reading; concurrent ACP sessions would need either one
   thread per session (with a serialized journal writer per state
   root) or an explicit multiplexing design.
