# P-32 — Session fork: `chat --fork RUN@STEP`, `/fork` in the REPL

## What landed

- `crates/harness-run/src/replay/fork.rs` (new): `fork_session(ForkSession)`
  — a child run that continues a parent journal from `parent_step`.
  - `ForkSession` mirrors `ResumeSession` plus `parent: &RunId` and
    `parent_step: u64`.
  - Parent selection is the same as resume: the LATEST attempt with a
    header (`attempts_desc`/`has_header`), opened with
    `JournalReader::open_expecting`; header and approver checks re-run
    against the live inputs. No fork at or after a session end: the first
    record at/before the fork point may not be `RunStopped`/`InputEnded`,
    and the fork point must exist (at least one record at exactly
    `parent_step`).
  - The kept prefix re-uses resume's kept rule (drop the trailing
    in-progress step unless a `ToolFinished`/`TurnEnded` lands there).
    The child's `ForkedFrom` records `parent_step` as the last KEPT step
    and `parent_chain_head` as the hash of the last kept record (the
    header hash when the prefix is header-only).
  - Workspace: the current tree is measured at prepare; it must already
    hold the kept tree or the fork attempts a strict P-26 undo of the
    parent's post-fork edits (`restore_workspace`): `RestoreMark::Edit`
    marks after the fork point are undone newest-first with
    `restore_file` (expect_current = the recorded after-digest) /
    `uncreate_file` / `recreate_file`, blobs read from the parent
    attempt's blob store. Any file not holding its recorded digest, a
    missing blob, or a final re-measured tree different from the target
    refuses the fork — nothing is journaled, the workspace is left as the
    strict undo left it. There is deliberately NO "undo across a
    restore" guard: `RestoreMark::Tree` marks are checkpoints that every
    continued turn produces, so the strict per-file digest checks plus
    the final tree equality are the safety boundary.
  - The child run gets a fresh id and directory, a normal header
    (`resumed_from: None`, session turn limits recorded), then a
    `ForkedFrom` record at step 0 carrying `parent_run`, `parent_step`,
    `parent_chain_head` — before anything else. The loop then runs
    exactly like a resume: `Chain` backend replays the kept prefix and
    goes live after it, approvals/nonces/walls/carried wall time re-fed
    from the prefix.
  - A research task refuses (`RunRefused::Research`); fork is a session
    feature.
- `crates/harness-run/src/replay/feed.rs`: `Recorded` gains
  `fork: Option<RecordedFork>`; the `ForkedFrom` arm parses the record
  in session journals only (step 0, exactly the three fields; a second
  `ForkedFrom` is "not the shape the loop writes"). A `ForkedFrom` in a
  non-session journal still refuses (fail closed).
- `crates/harness-run/src/replay/audit.rs`: after the replay journal is
  created, a recorded fork re-derives the parent prefix head via
  `fork::parent_prefix_head(state_root, parent, parent_step)` (same
  directory/attempt/kept rules). A parent that does not verify is
  divergence `the forked parent's prefix does not verify`; a head that
  differs from the recorded one is `the forked parent's prefix does not
  match the recorded chain head`. On success the audit re-appends the
  identical `ForkedFrom` record to the replay journal so the record
  comparison still matches byte-for-byte.
- `crates/harness-journal/src/canon.rs`: `ForkedFrom` leaves the
  "reserved, no code writes them" list; canonical body keys
  `parent_chain_head`, `parent_run`, `parent_step` (policed by the
  writer like every other journaled kind) and a doc paragraph.
- `crates/harness-cli/src/cmd_chat.rs`: `chat --fork RUN@STEP`
  (`parse_fork`: `run@step`, run id and step parsed, usage refusal
  otherwise; cannot combine with `--resume`/`--continue`). `run_sessions`
  pops a pending fork before each session: a fork run reuses the same
  inputs, config, approver, sink and input feed as a normal chat session;
  after a forked session ends (not on exit) the chat loop offers a new
  session as usual.
- `crates/harness-cli/src/repl.rs`: `/fork RUN@STEP` sets
  `ChatState.fork` (a display-state request like `/clear`/`/exit`) and
  ends the current session; the next session in the chat loop is the
  fork. A `/clear` queued during a forked session defers one session
  (same deferral rule as resume).

## Ambiguity resolution (fail-closed)

- The card's "STEP" is the parent's step number; the recorded
  `parent_step` is the last KEPT step (a fork at a step whose trailing
  work was incomplete keeps the same step number as resume would).
- Workspace conflict: restore-or-refuse, never guess. The strict undo
  touches only files with an `EditApplied` mark after the fork point and
  only when the current bytes match the recorded after-digest.
- The audit reads the parent at the LATEST attempt-with-header at audit
  time. KNOWN LIMITATION: if the parent is resumed after the fork, its
  newest attempt re-writes the journal and the kept prefix may differ
  from what the child recorded — the child audit then diverges. Fail
  closed by design (a forked child cannot silently follow a rewritten
  parent); a fork pinning an attempt number is a conductor question,
  not something this slice decides.
- `context_format` NOT bumped: a fork re-uses the parent's records, adds
  no new context block.

## Loop visibility (§4.1)

- Journaled: the child's `ForkedFrom` at step 0 (fsynced with the
  header); the parent journal is untouched by a fork (verified
  byte-for-byte in tests).
- Replay: `recorded()` re-feeds `ForkedFrom` into `Recorded.fork`; the
  audit re-derives the parent prefix head and re-appends the record to
  the replay journal, so `compare` sees an identical record stream.
- Context: no rendered-context change.

## Tests (named as the card requires)

harness-run/tests/fork.rs (two-turn scripted parent that edits a file):

- `fork_child_audits_clean_and_links_parent` — the child's first record
  is the `ForkedFrom` with the right parent run, the kept step, and the
  last kept record's hash; the child audit is clean (no divergence).
- `fork_parent_unchanged` — the parent journal bytes and run-directory
  entries are identical after the fork.
- `fork_at_missing_step_refused` — a fork point with no records is
  refused by name.
- `fork_requires_workspace_digest_match_or_restore` — forking at the
  step before the parent's edit undoes the edit (strict restore) and the
  child audits clean; an externally overwritten file refuses the fork,
  the overwrite stands, and the parent journal is untouched.
- `fork_parent_tampered_refused` — a flipped byte in the parent journal
  makes the child audit diverge, naming the forked parent.
