# P-53 — Chat robust for small models: terse tool docs, parallel calls opt-in

Slice card: profile fields `tool_docs: "full"|"terse"` and
`parallel_tool_calls` (default false), a fixed terse-description table in
`harness-manifest`, the `max_active_tools` cap honoured against the
declarations, and the loop's handling of a second call in one reply.
Crates touched: `harness-manifest`, `harness-model-core` (declaration
rendering only), `harness-run`, `harness-cli`. Deps: P-21, P-18.

## What landed

- **The terse table** (`harness-manifest::builtin`):
  `terse_summary(id)` is a fixed one-line description per builtin tool
  (one sentence plus the argument names), `terse_table_text()` renders
  the whole table. Both are pure functions over the builtin list, so the
  table cannot drift from the manifest without a test failing.
- **Profile fields** (`harness-model-core::profile`): `ToolDocs`
  (`Full` | `Terse`) and `parallel_tool_calls` on `ProfileWire` and
  `Profile`, parsed from JSON with the usual refusals
  (`parallel_tool_calls: true` under the text protocol, and under a
  profile whose wire cannot carry it). Both enter the profile's
  `content_sha256` only when non-default, so existing profiles keep
  their digests. `Profile::with_tool_docs` is a builder for the loop
  (it drops any stamp, like the other builders). `profile_stamp_
  changes_with_tool_docs` pins the stamp behaviour.
- **The header**: `HEADER_INPUT_KEYS` gains `tool_docs` (17 keys). A run
  with terse docs journals `"tool_docs": <sha256 of terse_table_text()>`
  after the main input chain; a full-docs run journals nothing extra.
  `terse_table_sha256()` is re-exported from the driver and reused by
  the replay comparer, so a terse run's replay expects exactly the
  digested table.
- **Declarations**: `plan` builds every `ToolSpec` with
  `.with_tool_docs(profile.tool_docs())`, and `ToolSpec::with_tool_docs`
  swaps the long description for the terse summary. Before anything
  runs, a grant set whose active tools (the sentinel included) exceed
  `max_active_tools` is refused with `RunRefused::TooManyTools
  { active, max }` — the cap now bites the declarations, not just the
  loop's bookkeeping.
- **A second call in one reply** (`driver/step.rs`): the reply is a
  `SeveralActions` format error. Without the opt-in, the existing path
  stands: neither call runs, the reply is withheld, a `FormatError`
  record is journaled and the repair text says to make exactly one tool
  call per reply. With the opt-in (native protocol only), the loop
  keeps the first call, drops the rest, and journals nothing wrong: the
  turn carries a harness notice —
  `Notice: your reply made N tool calls; the first one ran and the
  other M were dropped. Make exactly one tool call per reply.` —
  joined with any loop-detector notice. `HarnessText::from_facts` (new,
  `harness-model-core`) carries the counts as trusted harness-side
  text.
- **The wire mirror**: a native request body for an opted-in profile
  carries `"parallel_tool_calls": true`, so the model knows its habit
  is allowed; the CLI's `profile show` prints both fields only when
  non-default, and `profile init` builds local small-model profiles
  with terse docs.

## Decisions

- **The terse table lives in `harness-manifest`, not the profile
  crate.** The manifest is the single source of tool identity; a
  summary next to the definition it summarizes cannot disagree with it,
  and the header's digest of the table makes any edit a visible input
  change rather than a silent context shift.
- **The opt-in keeps the first call instead of failing the reply.**
  The sketch rejected a surplus call "with a clear tool error"; but the
  first call of a parallel pair is usually the one the model meant, and
  small models re-issue it anyway. So: refusal (with repair) by
  default, run-first-drop-rest (with a counted notice) on opt-in. The
  notice names both counts so the model can tell what happened to its
  second call.
- **The dropped call is shown nowhere.** The shown reply is truncated
  to the first call before parsing, so no later request ever contains a
  `tool_calls` entry without its `tool` answer — the replay-valid
  history shape holds byte for byte.
- **`content_sha256` covers the new fields only when non-default** and
  the header covers only terse docs: full-docs, serial profiles (every
  existing journal) keep their digests and headers untouched, so old
  runs audit and resume exactly as before.
- **`rh-context` is untouched.** Only the tool declarations in the
  request and the profile change; the rendered context text and its
  version stand.

## Deviations from the sketch

- The opt-in path is "first call runs, rest dropped, notice shown",
  where the sketch's card only named the refusal and the opt-in. The
  refusal is the default, so the card's promise holds without opting
  in.
- The refusal is journaled as the ordinary `several_actions` format
  error (with the P-53 repair text) rather than a new record kind: no
  new `EventKind`, and audit/replay need no changes.
